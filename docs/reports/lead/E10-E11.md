This is the epic whose v1 version failed the team's first defence: the timer stayed open and
students saw answers. Both failures were architectural, so both fixes are structural rather than
careful, and everything below is arranged around them.

---

## 1. The two rules, and where they actually live

### The server owns time

- **The deadline is derived, never stored**: `startedAt + (durationMinutes + extraMinutes)`, in
  `AttemptRecord.deadline(...)`, and that is the only place the arithmetic exists. An extension
  therefore writes **one number on the execution** and every live deadline moves with it —
  including for a student who is offline, who gains the time the instant she resumes (E11.4) with
  nothing to migrate and nothing that can go stale.
- **Every write re-checks status *and* deadline inside its own transaction.** That shape is
  enforced by the seam: `ExamStore.inTx` hands out an `ExamData` valid for exactly one call, so
  "read here, decide there, write later" is the awkward thing to write rather than the easy one.
- **An answer arriving after the bell force-submits the attempt** rather than merely bouncing.
  A rejection alone would leave the row `IN_PROGRESS`, which is precisely the v1 bug wearing a
  different hat.
- **`TimerService` ends exams with the client gone.** One scheduled task per live attempt on a
  daemon executor; expiry is a database transaction. Re-armed from the database at boot, with a
  30-second backstop sweep for a task lost to a pause or a saturated executor.

### No correctness on a student's wire

`ExamQuestion` has four options and nowhere to put an answer key; it is mapped from the existing
no-correctness projection, whose query never selects `correct_answer`. `ExamWireLeakGuardTest`
scans every record in `common/dto/exam` and fails the build on a component name that reads like a
key, with a "has teeth" case (`AnswerReviewRow` really does trip the same predicate) so the guard
cannot rot into a test that passes because it stopped recognising anything.

## 2. Design decisions worth your review

### 2.1 The transaction seam (`ExamStore` / `ExamData`)

Services reach the database through `ExamStore.inTx(work)`, which hands the unit of work an
`ExamData` — the repositories bound to that transaction's session, valid for that call only.

**Why:** the subtle version of the v1 bug is a server that reads state, thinks, and then writes
against a world that has moved. Making the transaction the unit a rule is written *inside* removes
the gap. It also gives every rule two homes: fast unit tests against an in-memory double, and
`JpaExamStore` driven against H2 **and** real MySQL so the production data path is executed rather
than reasoned about.

### 2.2 Race resolution: the compare-and-set, and who may tell the grader

Finalisation is the status-guarded atomic UPDATE ARCHITECTURE §5 mandates, and `ExamAttempt` still
has no `@Version`. Three things follow, and the third is the one I would look at hardest:

1. **The loser reads the final state and answers with it.** A student whose submit lost to the
   expiry timer gets `TIMED_OUT` with `isOk() == true`, not an error. She did nothing wrong.
2. **A submit after the deadline is recorded as `TIMED_OUT` at the deadline**, not as `SUBMITTED`
   at the moment she pressed the button, because that is what actually happened.
3. **Only the winner calls the grading seam.** The first version of this double-graded every race:
   the losing submit reached the "attempt is closed, answer with its outcome" path and called
   `AttemptFinalizedListener` on the way out. Two unit tests caught it. The fix is a `won` flag
   threaded out of the transaction with the row it describes — see `Saved`/`Closed` in
   `AttemptService`, and `submitIsIdempotent` / `submitLosingTheRaceStillAnswers`.

### 2.3 The double start ends its transaction rather than swallowing the violation

`createAttempt` throws `DuplicateAttemptException` instead of answering empty. A flush that fails a
constraint leaves the Hibernate session marked for rollback, so continuing to read or write in it
is not safe; answering "empty" and carrying on would look like it worked. So the violation rolls
its transaction back and `start` re-reads the winner in a **second, clean** one. To the student
this is indistinguishable from having clicked once (F6.7), which the MySQL concurrency test proves
with two real threads.

### 2.4 Timer scheduling model

`TimerService` holds a `Map<attemptId, Task>`; `arm` replaces, `disarm` forgets, `sweep` is the
idempotent backstop. Two details worth naming:

- **A generation token fences a stale task.** Cancellation cannot close the window where the old
  task had *already started running* when the extension landed. Without the token, extending an
  exam at T-minus-ten-seconds would end it anyway. `staleTaskIsFenced` is that test.
- **An expiry that throws leaves the attempt armed** for the next sweep. A timer thread that died
  on one bad row would silently stop ending every other exam in the building.

Both the clock and the scheduler are injected, so every timing case is exact rather than timed:
"one millisecond after the deadline", "the timer fires while she is pressing submit", "extend at
T-10s".

### 2.5 Monitor pushes are whole snapshots, not deltas

A screen that patches rows from events drifts the first time one is missed, and a monitor showing a
student as still working ten minutes after she handed in is worse than no monitor, because a
teacher acts on it. Snapshots are one class of students; correctness is worth the bytes.

Watchers are whoever asked — the same mechanism `EditLockService` uses, dropped through the one
`SessionManager` detach hook that already covers logout and a dead socket.

### 2.6 Verb naming

`EXAM_JOIN` / `ATTEMPT_START` / `ATTEMPT_RESUME` / `ANSWER_SAVE` / `ATTEMPT_SUBMIT` /
`EXECUTION_EXTEND` / `EXECUTION_MONITOR_GET`, plus one new push verb `PUSH_MONITOR_UPDATED`.
Full semantics in **`docs/contracts/EXAM_WIRE_CONTRACT.md`** (marked DRAFT for you to freeze).
`Routes.TAKE_EXAM.id()` is `"attempt"` and `Routes.MONITOR.id()` is `"monitor"`, matching
`NotificationCatalog.ROUTE_ATTEMPT` / `ROUTE_MONITOR` so the time-extended and integrity-alert
notifications are clickable; a test pins both spellings.

## 5. Integration points left open

### For E12 (grading) — `AttemptFinalizedListener`

```java
class GradingService implements AttemptFinalizedListener {
    public void attemptFinalized(FinalizedAttempt a) { autoCheck(a.attemptId()); }
}
// then in HSTSServer.registerExamFeature, in place of AttemptFinalizedListener.NO_OP
```

Two things Member B needs to know, both documented on the interface: it is called **exactly once
per attempt** (behind the compare-and-set, so only the winner reaches it), and **after the
transaction has committed**, not inside it — a slow or failing grader must not be able to roll back
a submission the student has already been told succeeded. `FinalizedAttempt` carries
`examVersionId` so §6's "mark against the PINNED version" needs no second lookup. The no-op logs
rather than being silent, so during a demo it is visibly "not wired yet" rather than "wired and
broken".

### For E16 (study bot) — `AttemptTracker`

`AttemptService` implements it. Two branches of C-4:

- same course → `activeAttemptFor(studentId, courseCode)` returns the sitting, so the bot can say
  *which* exam and therefore when the lock lifts;
- another course → after the student confirms the notice,
  `reportCrossCourseBotUse(studentId, courseCode, courseName)` raises the `INTEGRITY_ALERT`
  notification to the executing teacher **and** flags her monitor row, pushed live. Repeat reports
  keep the first time. A report for a student who is not mid-attempt does nothing and is not an
  error, so the bot does not have to check first.

Lifecycle callbacks (`AttemptTracker.Listener`) exist so a bot chat already on screen locks the
moment its exam starts, rather than at the next message.

### For E9 (release manager) — `ExecutionCloseService.close(executionId)`

The seam E9's "close early" verb calls. Force-submits every straggler through the same path an
expiry takes (F5.5: "behaves like time expiry"), then freezes the derived counts into
`participation`. Idempotent. **No verb is registered for it here** — closing is E9's to own.

## 6. Known limitations / decisions you may want to overrule

1. **The attempt deadline is not capped by `close_at`.** A student who starts five minutes before
   the window closes still gets her full duration. My reading of "start + allocated duration + any
   execution extensions" (and of what a student would expect); the alternative is one line in
   `AttemptRecord.deadline`. Worth an explicit lead decision because a demo could show either.
2. **`ExecutionCloseService` has no verb.** Deliberate — E9 owns release/close — but it means E11.5
   is only reachable from code until E9 lands. Its tests drive it directly.
3. **Solving minutes round to nearest**, so 44m50s records as 45. Truncation would say 44, which no
   teacher would accept. S-19 says "minutes" and nothing more.
4. **The monitor pushes on every autosave.** Correct and cheap for a class, and it costs nothing
   when nobody is watching (the snapshot is not built unless there are watchers). At several
   hundred concurrent students it would want coalescing.
5. **`AttemptService` is large** (963 lines, 581 of them code and 312 javadoc). I kept the five
   verbs together because they share the deadline / compare-and-set / `afterFinalized` machinery,
   and splitting them would have meant exporting that machinery to a second class. Say the word and
   I will split resume+expire into an `AttemptClosureService`.
6. **The C-4 registry is in memory**, rebuilt at boot from `exam_attempts`. Same reasoning as
   `EditLockService`'s map, and nothing security-relevant is decided from it alone — but it means a
   restart mid-exam briefly unlocks a course bot until `rearmFromDatabase()` runs (it runs during
   `HSTSServer` construction, so the window is milliseconds and closed before the listener opens).
7. **Integrity flags never expire.** They outlive the attempt on purpose so the teacher sees them
   after the exam; they are cleared only by a restart or `clearFlags()`.
