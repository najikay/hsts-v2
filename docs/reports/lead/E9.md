## What shipped

Taking an exam out of the drawer, and putting it back: five verbs, one scheduled check, one
screen. The feature is `server.features.release` on the server, `common.dto.release` on the
wire and `client.features.release` on the client, plus one route and one rail item.

| Piece | Where | What it owns |
|---|---|---|
| `ReleaseService` | `server/features/release` | the five verbs, and every rule behind them |
| `ReleaseScheduler` | same | opening, the "opens soon" notice, and closing by the clock |
| `ExecutionCodes` | same | generating a code, and the shape rule shared with the wire |
| `ReleaseStore` / `ReleaseData` / `JpaReleaseStore` | same | the transactional seam, mirroring `ExamStore` |
| `ReleaseMessages` | same | every sentence the feature can say |
| `ReleaseRows` | same | the derived state, and the row every answer and push carries |
| `ReleaseManagerSession` | `client/features/release` | the whole screen's behaviour, FX-free |
| `ReleaseManagerView` + `CreateReleaseDialog` | same | the rendering, excluded from the gate by name |
| `ReleaseCopy` | same | every sentence the screen says |
| `ReleaseCreateRequest` / `ReleaseCodeIssue` / `ReleaseWindow` | `common/dto/release` | the two rules both tiers run: the window, and the code's shape |

## Decisions

### 1. The code is the teacher's; the check is the server's (revised 2026-08-23 on the coordinator's ruling)

**Superseded decision, recorded because the reasoning moved.** E9 first shipped with the code
generated server-side and no field at all, arguing that §5's partial-uniqueness rule can only
be answered inside the inserting transaction. The coordinator reversed it: §4's own sentence
("the teacher defines a 4-character execution code") and acceptance case 5.3 are the letter we
defend against, and the uniqueness argument justifies **server-side validation**, not taking
the field away. That is right, and it is now what ships.

`ReleaseCreateRequest.code` is a **nullable** component:

- **She types one** → validated in two stages. The shape (C-1's wide `[A-Za-z0-9]{4}`) is a
  rule about a string, so it is checked outside any transaction and by the dialog as she types,
  which is exactly acceptance case 5.3's `12` and `ABCDE`. Whether it is *free* is checked
  **inside the inserting transaction**, because uniqueness is partial (a code is released again
  once its sitting is over, and MySQL has no partial unique index), and a clash comes back as
  `ReleaseCodeIssue.TAKEN` naming the way out.
- **She leaves it blank** → the server rolls one, re-rolling on collision. Blank and absent are
  collapsed to `null` in the compact constructor, so there is one representation of "you pick
  one" and every later check is a null test.

Codes are stored upper case and compared case-insensitively (C-1): `ab7q` and `AB7Q` are one
code, for a student joining and for the uniqueness check alike.

The generator's alphabet stays 32 symbols, digits and capitals **without `O`/`0` and `I`/`1`**,
because a code *we* invent is read out loud (S-17) and "oh or zero?" costs a student minutes.
That narrowing constrains generation only. A teacher who types `4821` or even `IO01` gets it:
the accepted shape is C-1's wide one, which is what the seed, the demo and T-5.3 all use.

**The dice clears the field rather than filling it**, and the button says "Generate for me".
Filling it would mean either rolling on the client — which cannot know whether the code is
already held by a sitting students could still enter — or asking the server for a preview,
which either hands out a code somebody takes a moment later or holds a reservation nobody asked
us to build. Clearing promises exactly what happens, and the hint under the field changes to
say it, so the button never appears to do nothing.

### 2. Closing early is `ExecutionCloseService`, whole

F5.5's "behaves exactly like time expiry for active students" is not implemented in E9 at all:
`RELEASE_CLOSE_EARLY` checks role, ownership and liveness and then hands the release to the seam
E11 built for it, which force-submits every straggler **through the expiry path** and freezes
the counts. The scheduled check calls the identical method when a window runs out, so a release
ended by the clock and one ended by hand produce identical rows and identical attempts. There
is no second force-submit implementation to drift.

`ReleaseCloseIntegrationTest` (MySQL) proves it on rows: stragglers end `TIMED_OUT` (not
`SUBMITTED`), each reaches the **grading seam** — which is the evidence it went through the
expiry path rather than a bespoke UPDATE — each online student gets `PUSH_FORCE_SUBMITTED`, an
already-submitted attempt is untouched, and the execution ends `CLOSED` with its participation
frozen.

### 3. The DTOs are `common.dto.release`, not `common.dto.exam`

`common.dto.exam` is documented by one sentence: everything in it is safe to send to a student
sitting an exam, enforced by a package scan. `ReleaseRow` carries the entry code, which S-17
says students never see in the app. Putting a teacher-only record that carries an exam code into
that package would weaken the sentence the package exists for.

The two packages meet in one place deliberately: `MonitorCounts` is **reused**, because a
release row's participation and the monitor's three numbers are the same derived counts (S-21).
A parallel `ReleaseCounts` would be a second definition of one thing.

### 4. The state is derived, asymmetrically

A release carries a status column *and* a window, and they disagree for up to thirty seconds at
either end because the transition is scheduled work. The rule: **never show a release as more
open than the server will treat it.**

- `SCHEDULED` whose opening moment has passed still reads **Scheduled** — students are refused
  until the column flips, and a teacher reading the code out to a room that cannot enter is the
  worst thing this screen can do.
- `LIVE` past its effective close reads **Closed** — joins are already refused (the window is
  compared, not only the column) and every attempt's timer has fired; offering "close early"
  there would offer a button whose work is done. Extensions move that boundary (S-20).

### 5. `NOT_FOUND`, not `FORBIDDEN`, for a release that is not hers

A deliberate divergence from E11, and the reasoning is written on the constant. The monitor
answers `FORBIDDEN` because a teacher who reached it already knows the execution exists, and
naming the owner is what lets her ask the right colleague. The release manager lists exactly
what she may act on, so an id from anywhere else did not come from this screen; cancel and close
early answer `NOT_FOUND` with one sentence for "does not exist" and "not yours" alike. Tested as
an equality between the two answers, not as two separate assertions.

### 6. Polling, not a timer per release

`ReleaseScheduler.tick()` runs every 30 s on the exam-timer thread, beside the attempt sweep. A
scheduled task per release would mirror `TimerService` and be wrong here: an attempt's deadline
lives inside one process's lifetime and there are as many as there are students in a room, while
a release's window is set weeks ahead, survives every restart, and there are a handful. A sweep
means a release opens within half a minute of its time, which nobody in a classroom can tell
from exact.

Everything it does is guarded and idempotent: the transition is a compare-and-set, so a release
a teacher cancelled a second earlier is not reopened; the "opens soon" notice is deduplicated in
memory and the set is pruned every tick against what is still pending. A window that passed
entirely while the server was down is opened and then closed in one pass, which lands it where
it would have been.

### 7. The "opens soon" notice goes to the students **and** the releasing teacher

PRD F11.1 lists `RELEASE_OPENING_SOON` as the teacher's; the brief asked for enrolled students.
Both get it, 30 minutes ahead: the students are who
`NotificationCatalog.releaseOpeningSoon`'s sentence is written for, and the teacher is the one
who has to be in the room with the code. The catalogue's `NavRef` points at the release manager,
which a student's client does not know and therefore renders as a plain non-clickable row — the
documented, safe degradation.

### 8. Scope of the list: everything she can act on, and nothing she cannot

`RELEASE_LIST_GET` is scoped in SQL to "she released it **or** she wrote the exam", which is
exactly the predicate the two action verbs gate on (S-35). Matching them means no row on screen
is un-actionable and no actionable release is invisible. **Cancelled releases are included**,
unlike on E14's results picker, because "I called that one off" is the fact the release manager
is being asked for; they remain excluded from the report corpus (PRD §6), which is E9's rule and
is enforced by `findContextsByExamAuthor` staying as it was.

## Repository additions ⚑ for Member A

Added under TEAM_SPLIT rule 5 (repositories grow with their callers), in style, with named
consumers, and **contract-tested on both engines** — directly in
`ExecutionRepositoryContract` (H2 + MySQL) and again through the seam in
`JpaReleaseStoreContract` (H2 + MySQL).

| Repository | Method | Why it is worth reading |
|---|---|---|
| `ExecutionRepository` | `isCodeInUse(session, code)` | **The partial uniqueness rule.** Scheduled and live only; a closed or cancelled release does not hold its code. No constraint behind it, so this `where` clause *is* the rule |
| `ExecutionRepository` | `create(session, …)` | Always inserts `SCHEDULED`, even when the window opens in the past: there is exactly one place a release goes live, and it announces itself |
| `ExecutionRepository` | `findContextsForTeacher(session, teacherId)` | Her list, scoped to `created_by OR exam.author`, cancelled rows included |
| `ExecutionRepository` | `findScheduledOpeningBy(session, limit)` | One read for both halves of the scheduled check |
| `ExecutionRepository` | `findLiveClosingBy(session, limit)` | Filters on **stored** close time; extensions are re-checked by the caller, because no portable HQL adds a column of minutes to a timestamp |
| `ExecutionRepository` | `transition(session, id, from, to)` | **Status-guarded atomic UPDATE.** Not optimistic locking: the question is "is it still SCHEDULED", and the guard that answers it belongs in the statement |
| `ExecutionRepository` | `CONTEXT_SELECT` constant | The four release reads share one projection expression, as `ExamRepository` does |
| `AttemptRepository` | `countParticipationByExecution(session, ids)` | The three counts for a whole list in one grouped read. Absent-not-zero, on the existing convention |
| `ExamRepository` | `findReleasableForTeacher(session, teacherId)` | **F5.1 as a `where` clause**: `APPROVED` plus a join to `course_teachers`. PRD §6's "impossible (not listed)" lives here |
| `ExamRepository` | `hasAnyExamInTaughtCourses(session, teacherId)` | Tells "nothing approved yet" from "nothing written yet", which are two different next steps |
| `CourseRepository` | `findEnrolledStudentIds(session, courseCode)` | Ids only: the read that answers "who" cannot become one that loads a table of students |

**Nothing existing was modified.** `findContextsByExamAuthor`'s cancelled-exclusion is untouched,
and `countParticipation` (the per-execution triple) is still what the monitor uses.

## Honest limits

- **E9.4's "per-execution stats snapshot" is the participation record**, not the score
  statistics. The three counts are frozen at close (S-21) and shown on every row; average,
  median and σ are E12's, computed when the last grade is approved, and rendered by E14. The
  release list says how many sat it, never how they did.
- **E9.6's "extend" action is not a button on this screen.** Extending is E11's verb and lives
  on the monitor, which every live row links to. Two buttons for one action in two places is how
  one of them ends up wired to the wrong execution.
- **The create dialog is not driven end to end by TestFX.** It is a modal `showAndWait` that
  blocks the FX thread by design, exactly as `WarnConfirm` and `RejectDialog` are; its rules are
  asserted deterministically instead (`ReleaseWireTest` for the window, `ReleaseManagerSessionTest`
  for the local validation), and the interaction test covers the flow either side of it.
- **The version picker shows no question count.** `ExamVersionContext` does not carry one and
  E7 owns the exam list; the count would be a second query per row for a label. The duration and
  the version number are shown instead.
- **E9.8 (acceptance vs T-5) is not ticked.** It is a manual pass and stays open.
- **Acceptance case 5.3 stands exactly as written.** "Set the execution code. Try `12`, then
  `ABCDE`, then `4821`" is the flow that ships: the first two are refused with
  `ReleaseCodeIssue.MALFORMED` and the third is accepted and stored. All three are automated
  (`ReleaseWireTest`, `ReleaseServiceTest`, and through the toolkit in
  `ReleaseManagerInteractionTest`). The dice is **additive** to the case and does not change
  any of its steps. Cases 5.1, 5.2, 5.4, 5.5 and 5.6 are unaffected and all covered.
