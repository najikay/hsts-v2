### 2.1 E20.1 — how the submission build is produced

One line, and the group number never enters a commit:

```powershell
.\mvnw -B -Djar.prefix=G13 clean package     # -> target\G13_Server.jar + target\G13_Client.jar
.\mvnw clean package                         # -> target\hsts-server.jar + target\hsts-client.jar
```

The shade `finalName`s now read `${jar.server.name}` / `${jar.client.name}`, which default to
`${jar.prefix}-server` / `${jar.prefix}-client`. A profile activated **by the presence of the
`-Djar.prefix` switch** overrides them with `${jar.prefix}_Server` / `${jar.prefix}_Client`.

The activation mechanism is the point. Maven's property activation reads user and system
properties, never the POM's own `<properties>`, so the committed `<jar.prefix>hsts</jar.prefix>`
cannot activate it: an ordinary build keeps the lower-case dev names every doc and habit in this
repo already uses, and the underscore-and-capital submission names exist only for the build that
asked for them. The alternative — edit the property, build, remember to revert — is one forgotten
revert away from a submission named after last week's placeholder.

Verified by running it: `target/G13_Server.jar` (89 MB) and `target/G13_Client.jar` (14 MB), and
a plain `package` still yields `hsts-server.jar` / `hsts-client.jar`.

### 2.2 E20.3 — the defence's log stream

```
%gray(%d{HH:mm:ss.SSS}) %highlight(%-5level) %cyan(%-28.28logger{30}) %msg%n
```

Rendered (escapes stripped):

```
08:54:25.395 INFO  server.core.HSTSServer       Listening on 192.168.1.42:5555
08:54:25.395 WARN  s.features.exams.ExamService Client 10.0.0.7 dropped mid-exam
08:54:25.396 ERROR f.q.QuestionCatalogueService Seed failed
```

Three decisions worth recording:

1. **logback's own converters, no library.** `%highlight` / `%gray` / `%cyan` emit plain ANSI.
   Windows Terminal and PowerShell 5+ render them, which is what the demo machines run. Jansi
   would have added a dependency and a native library to solve a problem the demo terminal does
   not have. A terminal with no ANSI support prints the escapes literally, and the documented fix
   is the terminal, never a rebuild.
2. **Width modifiers inside the colour converters**, `%cyan(%-28.28logger{30})`, never outside.
   Padding applied around a colour counts escape characters as letters, and the message column
   drifts by nine characters per line. `TerminalLogFormatTest` asserts two loggers of very
   different lengths put the message at the same column.
3. **`%logger{30}`, not `{20}`.** Logback shortens leading packages only as far as it must, so 30
   keeps `s.features.exams.ExamService` where 20 gives `s.f.e.ExamService` and every line starts
   to look alike from the back of a room.

The E19.4 ring buffer is untouched, and the test proves it rather than asserting it: `RING`
formats events itself and never sees this pattern, so no escape code can leak into the console
window's log pane.

### 2.3 E20.4 — properties beside the JAR

**The gap that was there.** Both config classes resolved exactly one external candidate: the file
beside the JAR when packaged, the working directory otherwise. So a packaged run started from a
directory that is not the JAR's — a shortcut, a service wrapper, `java -jar C:\hsts\G13_Server.jar`
typed from a home directory — ignored the `server.properties` the operator was standing in and
started on the bundled defaults, silently.

Resolution is now, in `common.config.ExternalConfig`:

1. beside the running JAR (wins when both exist: a file shipped next to the JAR was put there for
   this installation),
2. the same file name in the working directory,
3. the copy bundled in the JAR,
4. hard-coded defaults (`root`/`root`, `localhost:5555`).

Steps 1 and 2 are one shared class rather than two copies, because a client that searches one list
while the server searches another is a support conversation nobody can have over the phone. The
two config classes keep their own logging voice and their own bundled resource.

`ConnectPrefs` needed nothing: it persists to `~/.hsts/connect.properties` (remembered endpoint,
pinned server) which is per-user state, deliberately not beside the JAR, and it already treats a
missing or unusable file as "nothing remembered".

**First-run defaults.** `package` now has two executions in sequence:

- `copy-deployment-properties` (resources plugin, unchanged) copies the machine's real, gitignored
  `server.properties` / `client.properties` from the project root into `target/`;
- `seed-deployment-properties` (antrun, new) copies `*.properties.example` for whichever of the two
  is **still absent**.

So a fresh clone or a CI checkout gets a `target/` that runs out of the box, and a machine with real
credentials never has them overwritten. Ant rather than a second resources execution because
`copy-resources` can only express "copy when the source is newer" — a timestamp comparison that
would decide whether somebody's edited demo config survives a rebuild by which file git checked out
last. `<available>` makes it a fact about existence instead of about clocks.

Verified by simulation on this tree: with the root properties moved aside, `package` seeded both
files from the examples; with a hand-edited `target/server.properties` in place, re-running left it
byte-for-byte alone.

| § | Covers | Contains |

| 3 | **E20.6** | MySQL 8 install → password in `server.properties` → first boot creates `hsts_db` and migrates V1–V7 → seed button, with a budget/measured table and the three startup-failure sentences mapped to fixes |
| 4 | **E20.5** | TCP 5555 + UDP 5556 firewall rules, the Private-profile requirement, the discovery path, the manual-IP path, the hotspot plan, the smoke script |
| 5 | day-of gates | stale-JAR rule, rebuild-then-rehearse order, the defence view, the E16.17 live-key checklist, the room |

Three things in there that are worth the lead's eye:

**The platform note in the README was wrong, and it mattered.** It said the server JAR has no
native dependencies. That stopped being true at E19: the server console is a JavaFX window, so the
server JAR carries JavaFX natives too. **Both** JARs are platform-baked, and both must be built on
Windows. Corrected in README §9 and stated as a hard gate in DEMO_DAY §1.2.

**Discovery needs more than an inbound rule.** The reply is a unicast UDP answer to a broadcast
question, so machine B depends on Windows' "allow unicast response to multicast/broadcast"
behaviour, and both machines depend on the network profile being **Private** rather than Public.
Neither is an inbound rule anybody would think to add, and both are silent when wrong. §4.2 checks
them explicitly, and §4.5 rehearses the manual-IP path for the network where they cannot be fixed.

**The group number is a gate, not an assumption.** §1.0 is the first box in the document: confirm
the official number in the course system before anything is built with it in its name. The group
split off from G12 and *requested* 13, and a requested number is not a registered one. Everything
downstream carries it in a file name, and the mechanism is a command-line switch, so confirming it
late costs one rebuild and getting it wrong costs the cover of the submission. It is repeated as
the first box of the day-of gates in §5.1.

**The stale-JAR rule has an order, not just a warning.** commit → `clean package` on Windows →
delete every other copy → copy out → rehearse on the demo machines → zip **last**. Rehearsing
before the final build proves nothing about what is handed in; zipping before the rehearsal means
the zip holds an untested pair.

## 5. Open for the lead

1. **`G13` is the example value everywhere, and it is not yet confirmed.** The group requested 13
   after splitting from G12; the registered number has still to be read off the course system.
   Nothing is hard-coded to it (README, DEMO_DAY and this report all use it as an example, and the
   build takes it as `-Djar.prefix=`), so confirming it is a five-minute job and one rebuild.
   DEMO_DAY §1.0 is the gate that makes somebody do it.
2. **`maven-antrun-plugin` is a new build-time dependency** (3.1.0, plus Ant). It exists solely for
   "copy only when absent". If you would rather not carry it, the alternative is the resources
   plugin's timestamp behaviour, which is right most of the time and silently wrong the rest.
3. **The colourised pattern applies to both JARs**, since the CONSOLE appender sits on the root
   logger and the client shares `logback.xml`. Harmless (the client is normally double-clicked and
   has no terminal), and splitting the config per tier costs more than it buys.
