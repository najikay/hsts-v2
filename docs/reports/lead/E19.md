## 3. Decisions worth your review

### 3.1 Interface ranking (E19.1)

Five tiers, best first: the **default-route address**, then site-local on a **physical-looking**
interface, then site-local on a **virtual-looking** one, then anything else routable, then
**link-local (169.254)** last. Ties keep enumeration order, so two refreshes on an unchanged machine
agree.

The tier that is a judgement call is the virtual demotion. A Windows laptop with Hyper-V, VirtualBox
or Docker installed offers two or three RFC 1918 addresses that no other machine in the room can
reach, and they frequently sort ahead of the one that works. Demoting by **interface name**
(`vEthernet`, `VirtualBox`, `VMware`, `docker`, `veth`, `tap`, `tun`, `wsl`, `vpn`, `tailscale`,
`zerotier`) is a heuristic and it is the heuristic that fixes the actual failure. The default-route
probe outranks it, so a machine whose real route genuinely goes through a virtual adapter is still
answered correctly.

The probe itself: a `DatagramSocket` `connect`ed to **203.0.113.1** (RFC 5737 TEST-NET-3, guaranteed
to host nothing) on the discard port. **No packet is sent** — connecting a UDP socket only fixes its
peer, and the side effect exploited is that the kernel consults the routing table at that moment to
choose a source address. Chose a documentation address over a public resolver so that nothing in
this product ever looks, in a firewall log or in a code review, like the server phoning home.

### 3.2 Fingerprint persistence (E19.8/E19.9)

Random UUID, generated on first boot, written to **`server-id.properties` beside
`server.properties`** (and gitignored: committing it would give every clone the same identity, which
is the collision the id exists to prevent).

It survives restarts and does not survive a reinstall onto a clean machine. That asymmetry is the
design: a reinstalled server genuinely *is* a different machine, and every pinned client should be
told so once. `regenerate()` is the deliberate version, for an operator who cloned a disk image and
now has two servers claiming one id; it is **not** reachable from the console, because a button that
invalidates every client's pin does not belong beside the ones people press during a demo.

An unwritable file is **not** fatal. The server runs with a per-run id, logs one line saying exactly
that, and every pinned client sees a mismatch on the next boot. Refusing to start over a file
permission would be a much worse failure than the one avoided.

**The wording, verbatim, for the defence** (it is in `ServerFingerprint`'s javadoc, in
ARCHITECTURE §8, and in the mismatch dialog's own text): the fingerprint provides **disambiguation
and change detection, not impersonation resistance**. It travels in cleartext to anyone who asks, so
anyone who has heard it can repeat it. What it genuinely buys is that two servers in one room are
told apart, and that a client finding a *different* id at an address it used yesterday has learned
something real. Cryptographic binding means the id becoming a TLS certificate fingerprint, which is
E19.12's gated decision and changes no UX. The mismatch dialog deliberately says "reinstalled or
replaced" and never "attacker" — a security claim the product cannot keep is worse than none.

### 3.3 The ring buffer (E19.4)

Declared in `logback.xml`, **not** attached from Java. An appender added programmatically only starts
collecting once that code runs, which here would be after config loading, after Flyway and after the
pool comes up — exactly the lines an operator wants when a first boot goes wrong. Configured with
the framework, it is capturing before the first line of `ServerMain`. The console finds it through
`RingBufferAppender.buffer()`, which answers an empty never-filling buffer when logback has none, so
headless and misconfigured both degrade to an empty pane rather than a null.

2000 lines, already formatted. Keeping live logback events would pin 2000 argument arrays — every
DTO anybody logged — for the life of the process.

**Pause freezes the view, never the capture.** The obvious implementation stops feeding the buffer
and is wrong for the exact reason people press pause: something interesting scrolled past and they
want to read it. Stopping capture would destroy the evidence the button was pressed to preserve. So
the buffer keeps filling, the pane holds a frozen snapshot, and the resume button says how many
lines are waiting.

### 3.4 Start/stop semantics (E19.2)

Stop calls OCSF's `stopListening()`, **never** `close()`. `close()` also drops every client already
connected, and one of them may be a student mid-exam. So stopping means: the process stays up, the
pool stays up, timers keep running, attempts keep their deadlines, existing clients stay connected,
and **new** connections are not accepted. The console says all of that in the status line
(`"Not listening. New clients cannot connect. Exams already in progress keep running and their
timers keep counting."`) so an operator never has to guess.

> **2026-08-30, B-49.** That paragraph described the intent; two lines of code contradicted it.
> `stopListening()` did not close the socket, so "new connections are not accepted" was false at the
> port (they were accepted by the kernel and then ignored), and `HSTSServer.serverStopped()` called
> `shutdownNow()` on `examTimers` and `lockSweeper`, so "timers keep running, attempts keep their
> deadlines" was false from the first press. Both fixed; the teardown moved to `serverClosed()`. The
> status line's wording needed no change, which is the useful part: the copy was right and the code
> was wrong.

Closing the console **window** does stop the server, with an explicit `System.exit(0)` after
`Platform.exit()`. The JavaFX default would leave the process alive with no window and no way to get
one back.

### 3.5 The seed button (E19.6)

Confirmed against the loader's owner mid-pass and matches: entry point is
`SeedLoader.standard(sessionFactory).load(mode, confirmation)`; the console implements the
`Confirmation` as a **WarnConfirm** dialog and shows **the loader's own prompt** verbatim, so the CLI
and the button cannot describe the same destructive action differently; the result is rendered from
`SeedSummary.toText()`; `LOAD_IF_MISSING` goes straight through with no dialog because it destroys
nothing. Nothing in the loader was reimplemented.

`WarnConfirm` is the **one** place server code imports a client UI component. Flagged deliberately in
`ConsoleTheme`'s javadoc so it stays an exception rather than a precedent: the console's most
destructive button should get the product's one answer to "read the consequence first", not a
different one. Everything else the console draws is plain JavaFX with the shared style classes.

### 3.6 E19.11, the connect flow

The whole ruling is one pure function, `ConnectFlow.decide(pin, found)`:

| pinned? | discovery result | step |
|---|---|---|
| yes | pinned address answered, same id | **connect silently** → Login |
| yes | pinned address answered, other id | confirm changed server |
| yes | nothing answered at all | **connect silently** (blind) |
| yes | others answered, pinned one did not | picker |
| no | exactly one answered | connect, then pin (TOFU) |
| no | several answered | picker |
| no | none answered | manual entry |

Row three is the one to challenge me on. A pinned client that hears nothing still tries the pinned
address, because "discovery found nothing" and "the server is gone" are different facts, and the
common cause of the first is a network that filters broadcasts — client-isolation Wi-Fi is normal in
schools. If the connect then fails, `afterFailedConnect` produces manual entry with a sentence naming
the address. That is the "pinned server unreachable" branch of your ruling.

`ConnectPrefs` gains four **additive** keys (`connect.pin.host`, `.port`, `.fingerprint`, `.name`).
An older `connect.properties` has none of them and reads as "never connected before", which is
correct. Nothing existing was renamed, and a test asserts a pre-E19 file still resolves its
remembered endpoint and is not rewritten by pinning.

### 3.7 E18.8 — one shape decision

`LOCKS_SNAPSHOT` answers `Map<Long, LockHolder>` rather than `Map<Long, String>` as the brief's
wording suggested. `LockHolder` is `{userId, displayName}` and it is the same value type
`LockChange` and `LockResponse` already carry. Two reasons: the chip on the holder's **own** row must
read differently from a colleague's, and a viewer decides "is this me?" by id (two teachers called
Dana Cohen is a real possibility and a name comparison merges them). Say the word and it is a
one-line change.

Also added: a `MAX_IDS = 500` cap on the request, refused as `VALIDATION` rather than silently
truncated. Truncating would answer "nobody is editing rows 501 and up", which is a wrong answer
dressed as a right one.

## 4. Console manual-test checklist (for the demo rehearsal)

Run: `java -jar hsts-server.jar` (no arguments) with MySQL up.

**Header**
1. The address reads big and matches what `ipconfig` / `ip addr` says for the Wi-Fi or Ethernet
   adapter — **not** a VirtualBox or Hyper-V address. If it is wrong, that is the ranking to report.
2. `ID XXXX-XXXX` shows beside it. Note it down.
3. Click **Copy**, paste somewhere: it is exactly `<ip>:<port>`, the same string on screen.
4. Pick the other address in "Show a different address": the big header changes.
5. Type `10.0.0.99` into it and press Enter: the header changes, and a client told that address
   fails to connect (proving the override is honest, not cosmetic).
6. Type `1.2.3.4:5555` into it: refused with "Enter the address only. The port is set separately."

**Listener**
7. **Stop listening**: the sentence says exams in progress keep running. Confirm a client already
   signed in stays signed in, and a *new* client cannot connect.
8. **Start listening**: a new client connects again.

**Cards**
9. Database reads **Up**. Stop MySQL, wait ~2s: it goes **Down** with "Check MySQL is running…", and
   the console does **not** fall over. Start MySQL: back to Up within a second or two.
10. Clients count matches the number of signed-in clients, not the number of open sockets.
11. Study bot reads "0 of N answering" or "None configured" depending on whether keys are set.

**Clients table**
12. Sign in on a client: a row appears within a second with the person's real name, their role, the
    client machine's IP and "just now", ageing to "4 min" without the table reshuffling.
13. Kill the client process: the row disappears.

**Log pane**
14. Lines are arriving. Set the level to **WARN**: the INFO lines go.
15. Type `login` in the filter: only matching lines remain, and the status line says so.
16. **Pause**, sign a client in and out, watch the status count "N new lines waiting" climb while the
    pane stays still. **Resume**: the held lines appear. Nothing was lost.
17. **Clear** empties it.

**Discovery**
18. The **Answer discovery broadcasts** box is ticked. Launch a fresh client (delete
    `~/.hsts/connect.properties` first): it lands on **Login** without ever showing a host/port form,
    with "Connected to &lt;name&gt; · change server" under the card.
19. Click **change server** on Login: the host/port editor appears.
20. Untick the discovery box, delete the client's `connect.properties` again, relaunch: the client
    finds nothing and shows manual entry with "No server answered on this network."
21. Re-tick it, and with a second server also running on the same network, launch a fresh client: the
    picker appears with both, showing name, address and id.

**Fingerprint change (the ⚑ one)**
22. With a client pinned to this server, stop the server, delete `server-id.properties`, restart, and
    relaunch the client. It must show the prominent warning naming the **old** and **new** ids and
    refuse to connect until confirmed. Confirm: it connects and re-pins, and the next launch is
    silent again.

**Headless**
23. `java -jar hsts-server.jar --headless`: no window, the banner and the address print to the
    terminal, discovery still answers, a client still connects.
24. `java -jar hsts-server.jar --port five`: warns and starts on 5555 rather than refusing to start.

**Seed**
25. **Load demo data if missing** on a fresh database: per-table counts appear. Press it again:
    "Seed already present, nothing inserted."
26. **Reload demo data**: the dialog shows the loader's own DELETE-every-row prompt. Cancel: "Nothing
    was deleted." Confirm: per-table counts, and execution 4821 is live again.

## 5. Limitations, and what to double-check

1. **The port is not editable in the window.** E19.2 lists a "port editor"; the port is set with
   `--port` and displayed in the header. Changing it live means rebinding the listener while clients
   are connected, and I did not want to invent that semantics unilaterally. Your call.
2. **`ServerMain` is assembly glue and coverage-excluded**, so the *wiring* (which seam is connected
   to which real object) is not under test — only every seam's behaviour is. The manual checklist
   above is what covers the wiring. This matches the existing treatment of `HSTSServer`.
3. ~~**Stop-listening leaves the port bound.**~~ **Fixed 2026-08-30, B-49.** It was not cosmetic:
   somebody did demonstrate it. `stopListening()` now closes the `ServerSocket` and leaves connected
   clients attached, so a client dialling a stopped server is refused at once. Two things found in
   the same pass and fixed with it: the client's `openConnection()` had no timeout on the
   serialization handshake, so it blocked forever rather than reporting the refusal (the actual
   cause of the endless `Connecting...`); and `HSTSServer.serverStopped()` was calling
   `shutdownNow()` on the exam timers and the lock sweeper, so one press of Stop listening killed
   every exam deadline in the process permanently while the button's own sentence promised that
   exams in progress keep running. That teardown moved to `serverClosed()`. See
   `docs/contracts/CONNECT_WIRE_CONTRACT.md` for the `HELLO` verb added above it.
4. **Discovery uses broadcast, not multicast.** Directed per-interface broadcasts plus
   255.255.255.255. Some enterprise Wi-Fi filters both. The manual path is always one click away and
   E20.5's "test on the actual demo network, bring a hotspot" note still stands.
5. **The default-route probe can be blocked.** Some hardened environments refuse the socket. It
   degrades to the name tiers, which is fine; on a machine where it matters, check item 1 of the
   checklist.
6. **E3.6 is still not finished.** The ring appender landed here and is wired in `logback.xml`; the
   colorized console pattern and the rolling file appender did not. I deliberately did not add the
   file appender, because it would write a `logs/` directory on every test run of this single-module
   build. Noted on the E3.6 line in TODO.
7. **The console has no theme switcher** and no light mode. E19.7 asked for dark by default; I read
   "by default" as "the console's look" rather than as a preference to persist.
8. **Two TODO items are both numbered E19.11.** The UX ruling and the discovery tests. Both are
   ticked; the second carries a note saying so. Worth renumbering when you next touch that section.
9. **Three new classes are below the house bar, all for the same reason: real I/O.**
   `NetworkDetector` 90.1% (the `enumerate`/`collectFrom` branches need a machine with a down
   interface and one that refuses to be read), the client-side `DiscoveryTransport`'s real UDP
   implementation 74.1% (the broadcast fan-out over several interfaces; the loopback test covers the
   server side of the same shape), and `DiscoveryClient` 94.9%. All three sit inside the range the
   existing codebase already occupies for I/O-adjacent classes (`DbBootstrap` 86.5%, `ServerConfig`
   89.7%, `ClientConfig` 88.8%). The *rules* in all three are fully covered; what is not is the
   plumbing to a network card.
10. **`ConsoleView`'s address picker splits on the first space** to turn `"192.168.1.42 (Wi-Fi)"` back
   into an address. Free text with a space is rejected by `ConsoleModel.validateAddress` before it
   gets there, so this is safe, but it is the one piece of parsing left in a thin view.
