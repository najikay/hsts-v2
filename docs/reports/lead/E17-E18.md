## 1. What shipped

### E17 — Notifications

A persist-then-push notification subsystem, its two verbs, and the navbar bell that renders them.

- **`NotificationService`** (`server/features/notify/`) implements **`Notifier`**, the single interface every
  other feature will depend on. `notify(userIds, type, title, body, ref)` writes one row per recipient and
  *then* asks `PushGateway` to deliver, so an offline recipient is never skipped — their notification is
  waiting in the bell at their next login.
- **`NotificationStore`** is the persistence seam (the same shape `UserDirectory` is for auth).
  `InMemoryNotificationStore` is the real, contract-complete implementation the server runs on today;
  see §4 for the E2 handover.
- **`NotificationCatalog`** holds every sentence the product can send, one factory per PRD emit point.
  This is what makes the copy rules testable: one test checks all eight for em dashes, sentence shape,
  and a non-null click-through destination.
- **Verbs** `NOTIFICATIONS_GET` and `NOTIFICATIONS_MARK_READ`, both authenticated. Neither carries a user
  id — the recipient is the session on the socket, always.
- **Client**: `NotificationsModel` (state) + `NotificationsSession` (server conversation) +
  `NotificationPresenter` (icon/toast/age) are all FX-free and fully unit-tested; `NotificationsPanel` is
  the thin view. The unread count rides in `LoginResult`, so the badge is correct on the first frame.

### E18 — Edit locks & concurrency

- **`EditLockService`** (`server/features/locks/`): in-memory, server-authoritative, `Clock`-injected,
  40s TTL, sweep-on-access plus a scheduled sweep. Acquire / renew / release, takeover on an expired
  lock, and a `PUSH_LOCK_CHANGED` to everyone watching the entity.
- **Verbs** `LOCK_ACQUIRE` / `LOCK_RENEW` / `LOCK_RELEASE`, all authenticated, all carrying only an
  `EntityRef` — a client cannot name anyone but itself.
- **Disconnect** releases every lock a session held, via one `SessionManager` hook. Logout and a dropped
  socket both arrive there, because `detach` is the single path out of a session; both are tested.
- **`LockAwareEditor`** (client): the reusable helper a screen composes. Acquires on open, heartbeats
  every 12s, releases on close (best effort), and drives four UI states out of `EditLockState`, a plain
  state machine with full unit tests.
- **Optimistic versioning**: a stale write answers `ErrorCode.CONFLICT`; the client shows a `WarnConfirm`
  offering to reload. Wired through the legacy question editor as the working proof.

## 3. Design decisions

### Lock TTL 40s, heartbeat 12s

Both live in `common/dto/lock/LockTiming`, read by both tiers, because the *ratio* is the design and a
server TTL raised without the client following would silently turn every slow moment into a lost lock.

- **40s TTL** — long enough that a GC pause, a slow LAN, or a laptop lid closing briefly does not steal an
  editor from under someone; short enough that a colleague waiting on a crashed client waits well under a
  minute, which is roughly when a person concludes the app is broken.
- **12s heartbeat** — a third of the TTL, so **three consecutive renewals** must be lost before a live
  editor loses its lock. One dropped packet must never cost a teacher their session. A test asserts the
  ratio stays ≥ 3, so nobody can tune one number without the other.

A lock has a TTL at all because the alternative is a lock that outlives its holder: a client killed with
the power button sends no release, and an entity nobody can ever edit again is worse than an occasional
double edit.

### Watch mechanism: acquire registers interest

**`LOCK_ACQUIRE` doubles as the watch registration** — granted or refused. No `LOCK_WATCH` verb.

The reasoning: a screen that cares about an entity's lock is exactly a screen that tried to take it. A
refused caller is precisely the one who needs to hear the moment it is released, and a granted caller is
the one who needs to hear about a takeover. Registration is dropped on `LOCK_RELEASE`, on logout, and on a
dropped socket. Pushes exclude the actor, who already has the answer in their response.

**Documented limitation:** a purely read-only viewer that never attempts an acquire receives no
`PUSH_LOCK_CHANGED`. No screen in the product is in that position today (a read-only viewer is one that
*was* refused). If E7's exam preview ever wants live lock status without contending for the lock, add a
`LOCK_WATCH` verb that calls `watch()` without `compute()` — about six lines.

**Renewals raise no push.** A heartbeat per open editor every twelve seconds would be a push storm
carrying no news, and the only thing a watcher would learn from it — "still held" — it already assumes.

### Sweep: on access *and* scheduled

Every acquire/renew/release expires the touched key first, so an answer is never based on a stale hold.
That alone is not enough for the case the TTL exists for: a client that crashed while holding a lock is
touched by nobody, so the colleague waiting for it would keep a banner naming someone who has left the
building. `HSTSServer` therefore runs `sweepExpired()` on one daemon thread every **20s** (half the TTL).
The service itself owns no thread, which is what keeps it unit-testable.

### Migration number: **none used**

`V7__notifications.sql` already exists and already has the right shape. No `V8` was added.

Note for anyone reading the brief: the column is **`ref_type`**, not `ref_route`. `NavRef.route()` maps to
`ref_type` and `NavRef.entityId()` to `ref_id`. A route id *is* the type of thing being pointed at, so the
existing column name is honest and needs no migration.

### Notifications persistence: a seam, not a second JPA stack

`server/db/entities/Notification` is already written on Member A's E2 branch, along with `HibernateUtil`
and `Transactions.inTx`. Building a parallel entity, `SessionFactory` and repository here would have
created a duplicate to reconcile at merge. Instead the service depends on **`NotificationStore`**, whose
five methods are deliberately scalar and DTO-shaped — no entity, no `Session`, no `Optional<Notification>`
leaks through — so the JPA implementation is a drop-in, not a refactor. See §4.

### CONFLICT on the legacy question editor: value-based, not a version column

`ErrorCode.CONFLICT` needed a real producer to prove the client half, and the only editor that exists
today is the legacy one. The prototype's `Questions` table is the one table *outside* the Flyway schema
and has no `lock_version` to compare, so `QuestionUpdate` carries the values the client read and the
guarded `UPDATE` matches on them (`<=>`, MySQL's null-safe equality, so a question with no answer is not
permanently unsaveable). This is the technique Hibernate calls `OptimisticLockType.ALL`.

The **client half is generic**: the CONFLICT branch, the dialog copy in `LockCopy`, and the reload
behaviour are written against the error code, not against this DTO. When E6 lands the real bank editor on
the Flyway `questions.lock_version` column, it swaps the server-side guard and inherits the client
unchanged.

`UPDATE_QUESTION` still accepts a bare `Question` and writes it unguarded, so nothing that exists today
breaks.

### Notification rows: one per recipient

Read state is per person. A shared row with a read-by set would make "unread count" a join and "mark read"
a race; a row each makes both a primary-key operation.

### Ownership refusals are silent, not errors

Marking somebody else's notification read changes nothing and answers a **normal, unchanged page**. An
`ERROR` there would confirm that the id exists — a small enumeration oracle. Same reasoning as
`AuthService`'s single failure message. Two tests pin this down from both directions.

### A refused lock is `OK`, not `ERROR`

"Someone else is editing this" is an ordinary, expected answer that the screen turns into a read-only mode
with a banner. Reserving `ErrorCode` for real failures keeps client error handling honest: an `ERROR` on a
lock verb means something actually went wrong.

## 4. Integration points left for E7 / E8 / E12 / E16

**Everything routes through one interface.** A feature takes a `Notifier` in its constructor and calls it:

```java
public ApprovalService(ExamRepository exams, Notifier notifier) { ... }

notifier.notify(List.of(coordinatorId),
        NotificationCatalog.approvalRequested(examName, authorName, examVersionId));
```

Wire the real one in `HSTSServer` (`notificationService` is already constructed there). Unit tests take a
Mockito `Notifier` and assert "these users, this type" with no socket, session or store.

| Epic | Types to emit | Catalog factory |
|---|---|---|
| E8 approvals | `APPROVAL_REQUESTED`, `APPROVAL_APPROVED`, `APPROVAL_REJECTED` | `approvalRequested/Approved/Rejected` |
| E12 grading | `GRADE_PUBLISHED` | `gradePublished` |
| E11 extensions | `TIME_EXTENDED` | `timeExtended` |
| E9 release | `RELEASE_OPENING_SOON` | `releaseOpeningSoon` |
| E16 bot | `BOT_SOURCE_CHANGED`, `INTEGRITY_ALERT` | `botSourceChanged`, `integrityAlert` |

**Two rules for those epics:**

1. **The text is not yours to invent.** Titles and bodies live in `NotificationCatalog` so the wording is
   written once, reviewed once, and checked by one test against PRD §4.1. Add a factory there if yours is
   missing; do not inline a string.
2. **Recipients are yours to decide.** Notifications routes to the ids it is given and to nobody else.
   Working out who the coordinator of a subject is, or which students are mid-attempt, is your feature's
   business — and the negative tests in E17.6 exist to prove a wrong answer there cannot leak into another
   user's bell.

**Other editors (E18.5).** `LockAwareEditor` is generic; the integration recipe is in its class javadoc
(four calls and one callback). Exam builder, bot sources, release schedule and grading review compose it
with their own `EntityRef` type constant — `EntityRef.EXAM_VERSION`, `BOT_SOURCE`, `EXECUTION`, `GRADE`
are already defined — and their own entity noun for the banner.

**For E2 (Member A).** `JpaNotificationStore implements NotificationStore` is about thirty lines: each
method becomes one `Transactions.inTx(...)` block over the existing `Notification` entity. Swap the one
line in `HSTSServer.defaultRouter`. No line of `NotificationService`, and no test of it, changes.

**Client routes.** `NotificationCatalog`'s route-id constants (`approvals`, `exams`, `grades`, `monitor`,
`attempt`, `bot.manager`, `release`) are what the panel hands to `Navigator`. They are string literals on
purpose: an id the client does not know renders as a non-clickable row rather than failing, so a route
arriving one epic before its screen is safe. As each screen lands, register the matching route id.

## 5. Known limitations

1. **No production emit call yet.** None of the eight PRD emit points has a producer in the merged tree —
   they all belong to E7/E8/E12/E16. The service, the verbs, the badge and the panel are live and the
   `LoginResult` count is real; the first `notify()` call from a feature will light the whole path up with
   no further work here. Nothing was faked to make a demo look busy. Until then the bell demos from seed
   data (PRD §5 lists seeded notifications; that is E2.15).
2. **In-memory store is not durable.** Restarting the server empties notifications. That is exactly the
   gap `JpaNotificationStore` closes; it is documented as temporary on the class, not offered as an option.
3. **No pagination.** "Last N" with a clamped limit, no offset. Nothing in the product pages back through
   notification history, and an offset would be a parameter with no caller and one more thing to get wrong
   under a concurrent insert. The unread *count* is always the full table.
4. **Locks are in memory and per-server.** Correct for a single-server deployment, which is what this
   product is. A second server instance would need shared state; out of scope and not a direction the
   architecture claims.
5. **Read-only viewers do not receive lock pushes** unless they attempted an acquire — see §3.
6. **Legacy `CONFLICT` guard is value-based**, not `lock_version` — see §3. It is a genuine optimistic
   guard, not a placeholder, but E6 should move to the column when the real bank editor lands.
7. **`LOCK_RELEASE` on close is fire-and-forget.** If the message never lands, the TTL cleans up within
   40s and the disconnect hook covers a dead client. Deliberate: a user leaving a screen must never wait
   on the network.

## 6. What the lead should double-check

1. **`LoginResult` gained a component.** The 5-arg constructor is retained so every existing caller and
   test compiles unchanged, and `serialVersionUID` stays `1L` — client and server ship together, so this is
   safe, but it is a wire-shape change and worth a conscious sign-off. Four tests in `DtoSerializationTest`
   pin the new behaviour.
2. **`UserDirectory` gained a `default findById(long)`** returning empty. Kept `default` so the interface
   stays a `@FunctionalInterface` and existing lambdas still compile; `InMemoryUserDirectory` overrides it
   with a real id map. **E2's `RepositoryUserDirectory` must override it too**, or every lock banner will
   read "Another user".
3. **`Verb` constants were inserted before the push section**, not appended at the end, to keep the
   per-feature grouping the class documents. Java serializes enums by name, so ordinals are irrelevant to
   the wire — but the class javadoc says "never reordered", and this shifts existing constants' ordinals.
   Confirm you are happy with that reading; appending at the end instead is a two-minute change.
4. **`HSTSServer` now starts a daemon thread** (`hsts-lock-sweeper`), shut down in `serverStopped()`.
   Worth a look when E3.8 (graceful shutdown) lands so it is not shut down twice or missed.
5. **A CSS trap I hit and fixed** — worth knowing about, because it will catch the next person:
   `.hsts-popover-layer` originally carried `-fx-background-color: transparent`, which made the full-size
   overlay swallow every click on the content beneath it. `pickOnBounds(false)` does *not* help. This is
   the same defect `GalleryInteractionTest` was written for. The selector now sets no background property
   at all, and there is a comment saying why. **Rule: overlay layers in the shell paint nothing.**
6. **An ordering bug in `QuestionsView` worth remembering for the other editors:** `showSelected` set
   `saveButton.setDisable(!hasSelection)` *after* the lock state had already disabled it, silently
   re-enabling Save on a read-only question. The lock render now runs last, with a comment. Any editor
   composing `LockAwareEditor` needs the same ordering — the lock has the last word.
7. **`docs/TODO.md` is not ticked.** E17.1–E17.6 and E18.1–E18.4, E18.6, E18.7 are done; E18.5 is done for
   the question editor only (the other four editors do not exist yet). E17.2's emit points are *ready*, not
   *wired*, for the reason in §5.1. I left the checkboxes for you rather than claiming items that span
   other people's epics.
