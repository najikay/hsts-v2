## A gap this closes

`MyGradesSession.onGradePublished()` existed, was documented as "the hook the push bridge calls",
and **nothing called it**. There was no push bridge for `PUSH_GRADE_PUBLISHED`; the method had
been dead since PR 6.

`subscribeTo(ClientEventBus)` wires it, and it lives on the **session** rather than on the view
on purpose. The view is a thin renderer excluded from the coverage gate, so a live-refresh path
wired there would be behaviour that nothing measures. In the session it has five tests, including
the one that matters: **the pushed payload is ignored**. The push carries the published row and
appending it would be cheaper — and would be the only code path in the product capable of putting
a grade on this screen that the server did not just list. Re-querying costs one round trip and
removes the possibility.

## The screen

Exam, course, grade, approval date, teacher's note, and a marker when a teacher set the score.
`DataTable` already carries the loading, empty and error states, so the view renders and decides
nothing.

**`MyGradesCopy` is a separate file from `ResultsCopy`, and that is the design.** They describe
the same rows for two audiences. A teacher reads a class and wants the exception to stand out —
her marker is the bare word "Adjusted". A student reads her own transcript, where "Adjusted"
alone reads as though a correction had been needed; hers says *"Reviewed by your teacher"*. Two
audiences, two files, so a convenient reuse cannot quietly put teacher wording in front of a
student. There is a test asserting the two strings differ, which is the sort of test that looks
silly until someone consolidates the classes.

**The marker keys on the difference between scores, not the presence of a final one.** `Grade.approve`
sets `finalScore` to the auto score when nobody overrode anything, so *every* approved row has one.
A marker driven by presence would tell every student in the class that their paper had been
changed by hand. `adjustedMarkerIsAboutTheDifferenceNotThePresence` is the test.

**v1.1 pays off immediately.** Every row carries its own `examName`/`courseCode`, which is exactly
why the amendment existed — unlike a teacher's table, every row here is a different exam. A row
whose labels did not resolve shows `(exam unavailable)` and **still shows its grade**: losing a
grade over a missing label would be the worse failure.

## Wiring

The rail item was already there as `soon(ROUTE_MY_GRADES, "My Grades", …, 13)` — a disabled
placeholder reserving the slot since E5.4. Enabling it was a swap plus a route declaration, with
no rename anywhere, which is the same path E14 took for Results. `Routes.MY_GRADES` uses the id
the rail has always spelled.

Three exact-set guards failed when I added the route, which is them doing their job:
`AppArgsAndRoutesTest` (the routes table), `SessionRoutesTest` (the student's list) and
`RoleNavTest` (enabled labels). All updated. I also added `Routes.RESULTS` to the student's
`doesNotContain` list — a student's grades and a teacher's results are different routes and only
one of them is hers.

## ⚑ A contract gap, for your ruling

**Acceptance case 9.5 cannot pass as the contract stands.** It says: *as `omer.katz` (the seeded
TIMED_OUT attempt), open his result — the attempt is shown as timed out, with his actual solving
time in minutes (S-19)*.

`StudentGradeRow` carries neither `attemptStatus` nor `actualMinutes`. My own acceptance case
asks for data the frozen wire does not have, and I wrote both.

I have **not** amended the contract. Additive changes are allowed by its own terms, but this one
has a design choice in it and it is yours:

| Option | Argument |
|---|---|
| Put them on `CheckedForm` (E13.4) | "Open his result" most naturally means the marked paper, and solving time belongs beside the answers. Costs nothing on the list wire |
| Add them to `StudentGradeRow` as v1.2 | The list itself could then show "timed out", which is arguably what a student wants to see without opening anything |

My preference is `CheckedForm`, because the list is a transcript and a transcript does not
usually explain itself. Either way it lands in the E13.4 PR, so a ruling before tomorrow evening
is enough.
