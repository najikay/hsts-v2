## ⚑ B-4 — and the fix I got wrong

Select-all updated the **session's** selection and not the **table's**: the button enabled and the
confirmation counted correctly, so the right rows were approved, but a teacher could not *see*
what she was about to approve.

**My first fix made it worse, and I am recording that rather than quietly replacing it.** Driving
the table's selection from the session inside `render()` broke row selection outright — clicking
a row did nothing and every button stayed disabled. The listener clears the session before
rebuilding it; that clear triggers a render; and the render wiped the table's selection **out
from under the listener's own iteration**. The re-entrancy guard I relied on stops the *listener*
re-entering. It does not stop `render()` mutating the table while the listener is still running.

A second cause sat underneath. `DataTable.setItems` is a clear-then-add, and JavaFX drops the
selection when a backing list is cleared — so refilling the list on every render wiped the
selection even without my helper. I would not have found that one by reasoning; it surfaced only
because the first fix failed and I went looking again.

**The actual fix.** Selection flows **one way**: table → session, never back. Select-all sets the
table's own selection and the existing listener mirrors it. `render()` refills the queue and the
table only when their contents actually changed. There is no loop, so there is nothing to guard.

`GradingQueueSession.selectAllApprovable` is **removed** rather than left unused — the rule it
expressed lives in `GradingCopy.canOverride`, which both callers now use and which
`GradingCopyTest` already covers.

**The verify was green for the broken version, twice.** That is the honest headline of this PR.
A screen fix is verified by clicking it or it is not verified.

## B-5 — My Grades truncated the date *(fixed here)*

The Approved column read **"23 Au…"**. The table divided its width evenly, so a date got the same
room as a two-character course code — and the column a student reads to know when her grade
arrived could not show a date. The "Teacher's note" header was clipped for the same reason.

Preferred widths per column, sized to content, still adaptive to the window.

Found by **looking at the rendered screen**. `MyGradesCopyTest` asserts the date formats to
"20 Aug 2026" and passes — it never sees a column. That is the honest limit of testing copy in
isolation, and worth saying out loud rather than treating the green tests as coverage of the
screen.

## B-3 — `teacherComment` had no wire *(reported here, already fixed by the lead)*

**Read everywhere, written nowhere.** It was on the student wire, the teacher wire, both copy
classes and both screens. The only thing that ever set it was the seed loader: no request DTO
carried a comment field, and no service called `Grade.setTeacherComment`.

So **S-22 had no path through the application** — a teacher could not leave a student the one
piece of free text the student is allowed to read, and acceptance case 8.4 could not pass.

**The seed masked it.** `yael.azulay` has a seeded comment, so every screen rendered one and
looked finished. It was visible only on trying to *write* one.

**Already fixed while this branch sat uncommitted.** The lead landed GRADING amendment A3 —
option A of the two put forward, the comment riding `GradeOverrideRequest`. `main` is merged into
this branch, so his comment box and my selection fix now sit in the same dialog. The register
records B-3 as Fixed and credits A3.

**Case 8.4 is left ⚠, not ticked.** The wire exists, but nobody has watched a comment travel to a
student. Marking it passed on the strength of the code existing would defeat the point of a table
whose whole claim is that somebody saw it work. It wants a re-walk, which is minutes.

## B-6 — `results-print` was a style class with no rules

The checked form's print toggle did nothing. `.results-print` is added to the root in Java by
**two** screens — my checked form (E13.5) and **your teacher results screen (E14.4, ticked
done)** — and nothing in `hsts.css` matched it. Both toggles were silent no-ops.

E15's print rules describe themselves as *"the same modest thing E14.4 built"*, which is what
sent me looking: the idiom was written for E15 and never back-filled to `results-print`.

Rules written in that same style — flatten the cards, drop the chrome — covering both screens
from the one class. **This touches the appearance of your screen as well as mine**, so it wants
your eye at the review even though the change is small.

No test can see a stylesheet that matches nothing.
