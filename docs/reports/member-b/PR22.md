## Case 9.4 — passes

> *Try to reach another student's grade — via the UI, and by replaying the request with a
> different student id. Refused **server-side**, not just hidden in the UI.*

Run against the reseeded database through the production `CheckedFormService` — the gate itself.
**A UI with no link to another student's paper proves nothing about the server**, so the probe
replays the read directly rather than looking for a missing button.

| # | Probe | Result |
|---|---|---|
| a | `yael.azulay` replays `maya.levi`'s grade id | refused |
| b | `noam.peretz`, enrolled in neither course, replays it | refused |
| c | the reverse — `maya.levi` replays `yael.azulay`'s id | refused |
| d | each still opens **her own** paper (60, 55) | served |
| e | `MY_GRADES_GET` for `yael.azulay` | one row, hers |

**(a) is the probe that matters.** A stranger being refused is weak evidence. `yael.azulay` sat
the *same* Algebra paper, in the *same* sitting, and holds a legitimate grade of her own in it —
that is where a leak would actually be, and she is refused too.

**(d) is there so the case cannot pass by over-refusing.** A gate that refused everybody would
satisfy every negative probe in this table and would have broken the feature. Refusing correctly
and serving correctly are one property, not two.

Every refusal is the same empty answer, so none of them reveals *which* of the three conditions
stopped her.

**Method stated in the record:** this exercises the service, the repositories and the database —
not the socket layer. That the handler takes the student id from the **session** and never from a
payload is covered by `ResultsHandlersTest`, and the request DTO has no student id in it to
begin with.

## A correction to case 9.1

The probe printed `maya.levi`'s score as **60**. The acceptance table said **71**.

§9.1 and the database both say 60. The 71 came from a fixture value in `ResultsServiceTest` that
I carried into an observation record without checking it against the seed.

That is precisely the *derived-data-written-down-by-hand* hazard `SeedArithmeticTest` exists to
catch — except an acceptance record is a document **no test guards**. The seed document now
checks its own arithmetic; the table of what we observed does not, and cannot, because its
correctness depends on what was actually on screen.

Corrected in place with the reason visible in the cell, because that row had already been
reviewed and approved and a reader deserves to know the number moved.

**Worth noting for the manual pass:** this is a small error, but it is the class of error most
worth catching in this table specifically. The table is a claim about what a human saw, and it is
defended as such.
