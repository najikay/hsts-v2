## 2. The design worth reviewing: this is not `ExamRepository`

`ExamRepository` is the drawer's read side, shared by E8's queue, E9's release, E14's results and
E15's data browser. Its history is four of your commits, one of mine, one of Amjad's.

E7 is the only **writer** of these three tables. Putting the writes beside a dozen readers owned by
other epics makes one file the meeting point of four lanes, and it is the file most likely to
conflict on any given day. So the split is **by direction and owner, not by table** — which makes a
reader in this class the mistake, not the writes. Where E7 needs a read that exists, it calls the
existing one: the exam list's per-version question counts come from
`ExamRepository.countQuestionsByVersion`, not from a second count of my own that could disagree
with the queue's.

**Reversal cost if you disagree: one merge, mechanical.** Move nine methods into `ExamRepository`
and delete this class. No caller changes, because there are no callers yet. That is the other half
of why this PR is separate.

### The answer key

`PinnedQuestion` and `PinCandidate` are built by constructor expressions that never name
`correct_answer`, so the column is not fetched and no caller can reach it — E2.12's shape applied to
the authoring side. **No method here takes a sanctioned `ForAuthoring` suffix**, deliberately: that
suffix licenses a read that really does carry a key, and spending it on one that does not would make
the licence mean less. The auditor confirmed `CorrectnessLeakGuardTest` scans
`target/classes/server/db/repos` and `.../projections` by directory, so all six new types are
inspected rather than accidentally out of scope.

| 2 | A test comment described a flush I had already removed, contradicting the javadoc that removed it | Rewritten |
| 3 | **`lockVersion` was never asserted at a non-zero value**, and on `AuthoredVersionRow` never at all | **Planted it.** Swapping `v.lockVersion` and `v.durationMinutes` in the `EXAM_LIST` query passed all 45 tests |

| 8 | *Suspected:* a bulk delete does not evict from the persistence context, so a second call in one transaction would collide | Now measured, see round 2 |

**Finding 3 is the one that would have cost something.** It does not throw. It makes a stale save
succeed — F10.3's lost update, arriving as a teacher's edit vanishing. Contract §6 makes `CONFLICT`
conditional on `expectedLockVersion`, and every row on `EXAM_LIST` would have carried a duration in
that field.

### Round 2, on the fixed state: all eight closed, two more found

The auditor re-derived finding 3 against **every** wrong-column substitution it had listed — the
duration swap, a literal `0`, `e.lockVersion`, `v.versionNo` — not only the one I planted, and
confirmed each now fails. Then:

**9. I stated an unverified mechanism as fact, directly beneath a paragraph advertising that the
claim above it was measured.** My fix for finding 8 asserted what would happen on a second call in
one transaction. Nobody had run it. Two claims, formatted identically, one measured and one assumed,
nothing marking the difference.

Measured instead of softened: it throws `EntityExistsException` wrapping `NonUniqueObjectException`
on both engines, before any SQL —
*"A different object with the same identifier value was already associated with the session."* The
claim was right; it had not been checked. It is now
`twoCompositionWritesInOneTransactionAreRefused`, and the javadoc points at it.

**10. Five constraint tests asserted `assertThatThrownBy(...).isNotNull()`, which passes for any
throwable.** Nothing was masked on the day — the auditor checked the surefire XML and each fired the
constraint it names — but the path to it going live is short: the fixture helpers return `Long`
unboxed into a `long` inside the lambda, so any drift throws NPE and the test passes. On the
duplicate test the *second* assertion agrees, because nothing was written either way.

All five now name their constraint. **One failed immediately**: `pointsAreBoundedByTheSchemaToo` was
passing on something other than what its name claims. Hibernate's MySQL dialect maps unique and
foreign-key errors to `ConstraintViolationException` but leaves a CHECK violation as
`GenericJDBCException`. That test now asserts the shared supertype plus the constraint name, with
the reason recorded in place.

### Two things the auditor called weaker than they read, which I have not changed

- `examListIsOrderedByDisplayId` cannot distinguish `order by e.displayId` from
  `order by e.courseCode`: both exams are subject `10`, serial `01`. The mutation it exists to catch
  — a deleted `ORDER BY` — is genuinely closed, and no reachable behaviour separates the survivors.
- `editDraft`'s javadoc says `rejectedReason` is "deliberately untouched", but it was null before the
  edit, so the clause is **unfalsifiable** rather than unfalsified. §5.4 makes a savable version a
  DRAFT and a DRAFT has no reason by construction, so the state where it would matter is one the
  contract forbids.

Recorded rather than fixed, because fixing either would be motion.

## 4. What the tests catch, planted rather than assumed

**57 tests: 26 in the contract on both engines, 5 more in the MySQL leaf.**

Ten mutations planted. Eight failed exactly the test meant to catch them:

| Planted | Caught by |
|---|---|
| delete targets the wrong version | both replacement tests, both engines |
| `order by evq.ordinal` dropped | `compositionIsOrdered`, `replacingAtNewOrdinals…` |
| author scope defeated in `findAuthoredExams` | `examListIsAuthorScoped` |
| author scope defeated in `findAuthoredVersions` | **nothing — see below** |
| `max` → `min` on E7.7's correlated subquery | `pinnedVersionIsComparedAgainstTheLatest` |
| `hasImage` inverted | `hasImageIsReportedWithoutFetchingIt` |
| soft-delete flag inverted | `pinCandidatesResolveWhatTheClientDidNotSend` |
| `versionNo desc` → `asc` | `versionListIncludesDraftsNewestFirst` |
| `lockVersion` / `durationMinutes` swapped | **nothing, before finding 3's fix** |

**Two plants came back negative and both were worth more than the eight that passed.**

The author-scope plant defeated the filter in *both* list reads and only one test failed:
`findAuthoredVersions` — the read that returns every version of every exam — had its scope removed
with nothing noticing, because every other list test seeds one author. `versionListIsAuthorScoped`
closes it; re-planted, it fails.

And I had a paragraph in `replaceComposition` claiming a flush between the delete and the inserts
was load-bearing: that Hibernate orders inserts before deletes, so a re-pin would trip the unique.
I removed the flush to watch a test fail. **It passed.** I removed the second flush. Still green, all
43. A bulk `createMutationQuery` delete is not queued the way `session.remove` is — it executes at
`executeUpdate`, so the rows are gone before the first insert is enqueued. Both flushes were doing
nothing and the paragraph was wrong. The code and the comment now say what was measured, including
that an earlier version claimed otherwise.

**What planting could not reach.** Both expensive findings were structurally outside it: the
`lockVersion` swap was a mutation I did not think to plant, and the H2 claim was something I
believed. That is rule 6 stated exactly — the plants I choose are bounded by what I already
understand — and it is the argument for the audit not being optional on the next PR either.

## 8. What is not in here

**The service rules. All of them.** `ExamValidator`, `ExamService`, `AutoComposer` and `ExamHandlers`
do not exist. `docs/TODO.md` now names the five rules that are consequently enforced by nothing on
disk, with their contract sections, because this PR is the last artefact reviewed before they get
assumed done:

1. No soft-deleted question (§5.2, assigned to E7 by name in ARCHITECTURE §5)
2. No duplicate question through two versions, as a **named** refusal rather than a constraint
   violation (§5.2, T-3.9)
3. Points summing to exactly 100, both directions, quantified (§5.1)
4. Every question in the exam's own course (§5.2)
5. Only a DRAFT is savable; REVISE refuses a DRAFT (§5.4)

The MySQL leaf's `softDeleteHasNoDatabaseBackstop` **deliberately asserts that pinning a
soft-deleted question succeeds.** That is not a bug pinned as behaviour: soft delete is an `UPDATE`
and no foreign key fires on one, so nothing below the service refuses it. The test stands in for the
constraint that cannot exist, and says so in its own comment so nobody "fixes" it.

No screens, no auto-composer, no `EXAM_LIST` consumer. E7.4's infeasibility report is PR 3.
