## 1. What it does

`QUESTION_CREATE` and `QUESTION_UPDATE` behind a form: the stem, four answer boxes, a
`RadioGroup` naming which is correct, topic, difficulty, and an `ImagePicker`. E6.11's live rules
run while she types, and every server `VALIDATION` sentence lands under the box it names, which is
T-2.2's three-bad-saves case.

Three files on the house shape: `QuestionEditorCopy` (the editor's own words),
`QuestionEditorSession` (every decision, FX-free), `QuestionEditorView` (nodes only).

**`QuestionEditorCopy` deliberately contains none of the refusal sentences.** Every rule the
editor checks live is a rule the server also checks, and the server's wording is in
`BankMessages`. Restating one would give a teacher two accounts of one rule: told while typing
that two answers are too similar, then told something differently worded on save.

## 2. The design worth reviewing: the editor calls your validator instead of copying it

E6.11 has to reach **the same verdict as the server** while she types. Two ways to get that, and
only one survives contact with time: copy the rule and test that the copies agree, or call the
rule.

It calls it. `QuestionValidator.sameAnswer` is public for exactly this consumer and its javadoc
says so; the four length constants come from the same class, so the numbers the editor refuses at
cannot drift from the columns they stand in for.

**This is the decision in the PR I most want a yes or no on, and it is item 1 of section 5.**

The deployment risk was checked before the code was written, not after, and then independently by
the cold read: the client jar's `artifactSet` includes the whole project artifact, so server
classes ship in it, and the closure of these two imports is the JDK plus
`server.db.entities.Difficulty` and `server.db.projections.ReferencingExam`, both annotation-free.
Nothing pulls Hibernate, MySQL, Hikari, Flyway, PDFBox, POI or the Anthropic client. **There is no
`NoClassDefFoundError` waiting on defense day.**

There is a documentation trap behind it, though, and it is yours: see section 6.

## 3. The cold audit, which is again the substance

Run after the code existed, against the code. Seven confirmed findings and one suspected, all
fixed, each with a test, each test planted.

**3.1 The image gate did not exist, and this class's javadoc said it did.** ⚑

The headline, and it is about me. `forEdit` takes the illustration's bytes as a required
argument, and the javadoc claimed that made the bad state unreachable: *"There is no ordering for
a screen to get right, because there is no way to build the editor in the wrong order."*

Requiring the **parameter** is not requiring the **bytes**. Passing `null` for a question that has
a picture was accepted in silence, and my own test file constructed that state inside a nested
class titled "an editor cannot open without the illustration it is about".

`forEdit` now throws on it. The test asserts the refusal instead of narrating the harm.

**And the harm is not what either of us wrote down.** COMPONENTS-E6 §4.2 and my javadoc both said
a blind save "writes KEEP-of-nothing over her own picture". `QuestionService.imageFor` is
`case KEEP -> previous.getImage()`, so KEEP copies the blob forward and **the picture is not
lost.** The real damage is that the editor says "No illustration" about a question that has one,
and that a **Remove she presses is silently discarded** — she asks for the picture to go, the
server is told to keep it, and nothing anywhere says no.

**3.2 A save settling after she left the editor acted on wherever she was.** No liveness guard, and
the stale-edit path opens a modal and then navigates. A `CONFLICT` arriving while she was on the
grading queue would have thrown a dialog over it and dumped her on the bank list, about a question
she had stopped looking at. Now guarded by `navigator().isCurrent`.

**3.3 `baseVersionNo` never moved after a save.** `adopt` re-baselined every field except the
staleness token, so a second save from the same editor would cite the version before her own
previous save, get `CONFLICT`, and be told **"somebody else edited this question"** about herself.
Latent only because the screen navigates away on success, which is one feature request from being
live.

**3.4 A comment claimed a duplicate refusal marked both boxes.** It returns one, and the shape
only allows one. Worse, it named the earlier position while `QuestionValidator.answersDistinct`
reports `answerField(j)`, the later one. Now matches the server, and the comment says what the
code does. The **live** rule still marks both, which is where "both" was ever true.

**3.5 Two of your javadocs promise something the wire does not carry.** `Violation.field` exists so
"E6.11's editor can highlight the right box **without matching on message text**", and
`BankMessages` says the client "never has to match on text". `BankHandlers.fieldProblem` keeps only
the message, so the field has never reached the wire and E6.11 **does** match on text — by exact
equality against the catalogue, which is sound because both tiers ship in one artifact. Both
javadocs corrected in this PR. Whether to put the field on the wire is section 6.

**3.6 The principal must never be offered this screen.** F9.3 gives her zero mutating verbs and she
is on the bank's four reads only, so an editor would be a screen whose every Save is refused. That
is now a guard rather than a note, and it is the one row of contract section 2's table a client can
get wrong on its own.

**3.7 Three of my own assertions could not fail.** In the nested class named for the gate, three of
four tests survived removing the gate entirely. Replaced.

## 10. The lock consult: the commit this PR was waiting on

Landed 2026-08-24 on your wave-1 `EditLockGuard`, in the sequence you set: your guard on `main`,

### 10.1 What a teacher sees change

Before: two teachers could both have question 11007 open, both press Save, and both writes went
through. The second one won and nobody was told. The "Rina Barak is editing this" banner on the
other screen was decoration - the mutual exclusion E6.14 draws was enforced by the client alone,
and `BankMessages.lockedBy` was a sentence with no issuer. After: the second save comes back
`CONFLICT` naming her, and the same is true for deleting a question somebody has open, which is
BANK section 5's "a delete racing an edit is a CONFLICT rather than a coin toss" made true on both
halves of the race rather than one.

### 10.2 The key had no home on the server, and that is why a class moved

`EntityRef` is a `(type, long id)` pair; somebody has to decide which number identifies a question,
and your 2026-08-23 ruling is `displayId5` rather than the primary key. That rule lived in
`client.features.bank.BankLocks`, package-private, because the editor was its only caller. The
consult gave it a second caller on the other side of the wire, and **the server has to arrive at
the same key or it reads an empty map and refuses nothing.**

Two ways: copy the parse into `QuestionService`, or move the rule. Copying reintroduces two
implementations of one numbering rule, which is the precise hazard your ruling exists to prevent.
So it moved to `server.features.bank.QuestionLockKey` (public), `BankLocks` is deleted, and the
editor calls the moved class - the same direction you accepted twice for `QuestionValidator`, and
the closure is one annotation-free record. **Reverting is one file move and restoring
`package-private`.**

The plant that justifies the move is in the table below: keying the server on the primary key
leaves `QuestionLockKeyTest` **green** while four service tests fail. A server deriving its own key
wrongly is invisible to the key's own unit test, which is exactly what a copied parse would have
been.

### 10.3 Where the consult sits, and what that ordering is actually for

`reachableForWriting` then the **lock consult** then the version check, on both verbs. The version
check after, as you ruled: the lock is the polite refusal, `baseVersionNo` is the correctness
guarantee.

The consult after the **scope** check is my call, and the reason is disclosure rather than locks.
Consulting first answers "Rina Barak is editing this" about a question in a course the caller does
not teach - confirming the question exists **and** naming a colleague, straight through the hole
section 2 folds three conditions into one answer to prevent. The hoist plant proves it:
`outOfScope` flips to `LOCKED`.

**I also had a second reason in that javadoc and it was wrong.** I wrote that an early consult
would throw on the socket read thread, citing E1.11. The cold read checked: `MessageRouter:162`
catches every handler exception and answers `INTERNAL`. It would have been an ugly error, not a
dead thread. Corrected in place, because an overstated hazard is how the real one gets skipped.

### 10.4 The second cold audit, which again is the substance

Run after the code existed, against the code, with named claims to reproduce rather than reason
about. Five confirmed, one suspected. **Two changed code.**

**A partial update is how a fact rots.** I updated `BankMessages`'s "this has no caller" note and
left the same fact stated in two other places - `QuestionEditorSession`'s javadoc and a
`QuestionEditorInteractionTest` assertion message - both still saying flatly that the server does
not gate this and that `lockedBy` has no caller anywhere. The javadoc even closed the door behind
itself ("Raised with the lead, whose call it is"), so the next reader concludes the gap is open and
unowned and stops looking. Both rewritten. **This is P-6 with my own name on it**, and what makes
it worth recording is that I had already fixed one copy of three.

**My plant family was incomplete, on the half that would have been copied.**
`outOfScopeBeatsTheLock` exercised `update` only. Hoisting the consult in `delete` alone survived
all ten tests and would have shipped the existence oracle above on `QUESTION_DELETE`. The two verbs
are separate call sites and neither one's ordering is evidence about the other's. I picked those
five mutations while holding the check in my head, which is why I am the wrong person to judge the
family complete.

**The consult now takes the stored row, not the request.** The auditor suspected a collation hole:
`findActiveByDisplayId` compares under `utf8mb4_unicode_ci`, which calls strings equal that
`Long.parseLong` rejects - so "it matched a row" does not imply "it parses", and my invariant was
stated too strongly. Rather than settle the collation question I took the fix that makes it moot:
`lockHolderOtherThan` is handed the `Question` the scope check already resolved and keys off
`question.getDisplayId()`. **The invariant is now true by construction, and the hoist mutation
became unconstructible** - there is no signature a raw request id fits into. I planted the
realistic regression instead (a request-keyed consult reintroduced) and it is caught.

**Two comments of mine were false and are corrected.** The width check does *not* separate the key
space from legacy primary keys - course codes may lead with a zero, so `01003` keys
`question#1003`, and my own test measures it. What separates them is the legacy screen taking no
lock at all. And the E1.11 claim in 10.3.

Two claims I had flagged as my likeliest mistakes, which it tested and found sound: the
`LOCKED`-without-holder state is genuinely unconstructible (it checked the delegating constructors,
the factories, reflection and record deserialization), and the `FxTestHarness` swap is strictly
stronger than what it replaced.

### 10.7 What E7 inherits, and the one thing worth your attention

`EditLockGuard`'s javadoc says E7's `EXAM_VERSION_SAVE` copies this consult shape. **Two of the
findings above would have been copied with it:**

- the untested half of the ordering, which on an exam version is the same existence oracle over a
  different table;
- keying off request data rather than the stored row, which carries the same collation question
  wherever the id is a string compared under `_ci`.

Both are cheap to carry forward correctly and expensive to find twice. When I build E7's consult it
will take the resolved entity and pin the ordering on every verb that has one, unless you would
rather rule otherwise.
