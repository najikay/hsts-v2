## 1. What it does

`QUESTION_CREATE` and `QUESTION_UPDATE` behind a form: the stem, four answer boxes, a
`RadioGroup` naming which is correct, topic, difficulty, and an `ImagePicker`. E6.11's live rules
run while she types, and every server `VALIDATION` sentence lands under the box it names, which is
T-2.2's three-bad-saves case.

Three files on the house shape: `QuestionEditorCopy` (the editor's own words),
`QuestionEditorSession` (every decision, FX-free), `QuestionEditorView` (nodes only).

**`QuestionEditorCopy` deliberately contains none of the refusal sentences.** Every rule the
editor checks live is a rule the server also checks, and the server's wording is in
`BankMessages`. Restating one would give a teacher two accounts of one rule: told while typing
that two answers are too similar, then told something differently worded on save.

## 2. The design worth reviewing: the editor calls your validator instead of copying it

E6.11 has to reach **the same verdict as the server** while she types. Two ways to get that, and
only one survives contact with time: copy the rule and test that the copies agree, or call the
rule.

It calls it. `QuestionValidator.sameAnswer` is public for exactly this consumer and its javadoc
says so; the four length constants come from the same class, so the numbers the editor refuses at
cannot drift from the columns they stand in for.

**This is the decision in the PR I most want a yes or no on, and it is item 1 of section 5.**

The deployment risk was checked before the code was written, not after, and then independently by
the cold read: the client jar's `artifactSet` includes the whole project artifact, so server
classes ship in it, and the closure of these two imports is the JDK plus
`server.db.entities.Difficulty` and `server.db.projections.ReferencingExam`, both annotation-free.
Nothing pulls Hibernate, MySQL, Hikari, Flyway, PDFBox, POI or the Anthropic client. **There is no
`NoClassDefFoundError` waiting on defense day.**

There is a documentation trap behind it, though, and it is yours: see section 6.

## 3. The cold audit, which is again the substance

Run after the code existed, against the code. Seven confirmed findings and one suspected, all
fixed, each with a test, each test planted.

**3.1 The image gate did not exist, and this class's javadoc said it did.** ⚑

The headline, and it is about me. `forEdit` takes the illustration's bytes as a required
argument, and the javadoc claimed that made the bad state unreachable: *"There is no ordering for
a screen to get right, because there is no way to build the editor in the wrong order."*

Requiring the **parameter** is not requiring the **bytes**. Passing `null` for a question that has
a picture was accepted in silence, and my own test file constructed that state inside a nested
class titled "an editor cannot open without the illustration it is about".

`forEdit` now throws on it. The test asserts the refusal instead of narrating the harm.

**And the harm is not what either of us wrote down.** COMPONENTS-E6 §4.2 and my javadoc both said
a blind save "writes KEEP-of-nothing over her own picture". `QuestionService.imageFor` is
`case KEEP -> previous.getImage()`, so KEEP copies the blob forward and **the picture is not
lost.** The real damage is that the editor says "No illustration" about a question that has one,
and that a **Remove she presses is silently discarded** — she asks for the picture to go, the
server is told to keep it, and nothing anywhere says no.

**3.2 A save settling after she left the editor acted on wherever she was.** No liveness guard, and
the stale-edit path opens a modal and then navigates. A `CONFLICT` arriving while she was on the
grading queue would have thrown a dialog over it and dumped her on the bank list, about a question
she had stopped looking at. Now guarded by `navigator().isCurrent`.

**3.3 `baseVersionNo` never moved after a save.** `adopt` re-baselined every field except the
staleness token, so a second save from the same editor would cite the version before her own
previous save, get `CONFLICT`, and be told **"somebody else edited this question"** about herself.
Latent only because the screen navigates away on success, which is one feature request from being
live.

**3.4 A comment claimed a duplicate refusal marked both boxes.** It returns one, and the shape
only allows one. Worse, it named the earlier position while `QuestionValidator.answersDistinct`
reports `answerField(j)`, the later one. Now matches the server, and the comment says what the
code does. The **live** rule still marks both, which is where "both" was ever true.

**3.5 Two of your javadocs promise something the wire does not carry.** `Violation.field` exists so
"E6.11's editor can highlight the right box **without matching on message text**", and
`BankMessages` says the client "never has to match on text". `BankHandlers.fieldProblem` keeps only
the message, so the field has never reached the wire and E6.11 **does** match on text — by exact
equality against the catalogue, which is sound because both tiers ship in one artifact. Both
javadocs corrected in this PR. Whether to put the field on the wire is section 6.

**3.6 The principal must never be offered this screen.** F9.3 gives her zero mutating verbs and she
is on the bank's four reads only, so an editor would be a screen whose every Save is refused. That
is now a guard rather than a note, and it is the one row of contract section 2's table a client can
get wrong on its own.

**3.7 Three of my own assertions could not fail.** In the nested class named for the gate, three of
four tests survived removing the gate entirely. Replaced.

## 6. The five items, all now answered

**6.1 `ARCHITECTURE.md` describes a client jar we do not build.** Line 251 says it *"excludes
DB/Hibernate/bot/server code via shade filters"*. The pom has never done that: the client
`artifactSet` includes the whole project artifact. Nothing depended on the difference until now,
and E6.11 is the first code whose correctness rests on the pom rather than on that sentence. An E20
packaging pass that "restores" the documented behaviour breaks the editor on open, and **no test
can see it**, because tests run on the full classpath. One clause in your file.

**Answered 2026-08-23: accepted, and the cross-tier import stands.** One rule with one home has won
twice in this codebase already, the closure was measured (JDK plus two annotation-free classes), and
both tiers ship in one artifact by deliberate pom shape. The condition it rests on now gets written
where it was wrong: you are fixing `ARCHITECTURE.md` line 251 yourself, and the E20 packaging
checklist gains a line saying the client jar ships the full artifact **on purpose** and the editor
depends on it, so no future "cleanup" restores a sentence at the cost of a screen. Nothing further
from me: neither file is mine to edit.

**6.2 Should `Violation.field` go on the wire?** Section 3.5. Today the client maps by exact
equality against `BankMessages`, which works and is tested, but it means **no sentence in that
class may be reworded without checking `QuestionEditorSession.locate`**. Putting the field on the
error payload would remove that coupling. The contract is FROZEN v1, so it is an amendment and
therefore yours. I have not done it; the javadocs now say what is true either way.

**Answered 2026-08-23: no for v1, recorded as the v2 shape.** Putting `Violation.field` on the wire
means widening the protocol's error envelope, and a protocol change three days out loses to a
coupling that is exact-equality tested and safe precisely because both tiers ship together. So the
coupling stands as documented, and the corrected javadocs are the record of it: no sentence in
`BankMessages` may be reworded without checking `QuestionEditorSession.locate`.

**What that binds in E7**, written here so it is not re-derived from scratch: with no structured
field slot on the envelope, a refusal names its field inside the sentence or not at all. E7's
`ExamBuildMessages` is written that way from the first line rather than retrofitted when the wire
does not widen, which is what `EXAM_BUILDER_WIRE_CONTRACT.md` section 6 already asks for.

**6.3 The taught set is an approximation, and the client has nothing better.** `canWriteIn` gates
on `LoginResult.courses()`, which is `CourseRepository.findForUser`: teaching **union enrolment**.
`Authorization`'s own javadoc warns against exactly that substitution, and `enrollments` carries no
role constraint, so a teacher enrolled in a colleague's course would be offered Edit and Delete on
it. **Unreachable today only because the seed enrols nobody but students** — P-7's shape exactly.
Nothing on the wire carries a taught-only set, so the comment now states the approximation instead
of denying it. A taught-only field on `LoginResult`, or a narrow lookup, would let the offering
match the rule. Your DTO, your call.

**Answered 2026-08-23: deferred to hardening day, with the fix named.** `LoginResult` grows an
additive `taughtCourses` component (your DTO, your E5 feature), `canWriteIn` switches to it, and the
approximation is gone. Unreachable today because the seed enrols only students, and the comment
stating the approximation rather than denying it is the right interim.

**What that binds in E7:** your ruling says E7's course picker lives with the same approximation
until `taughtCourses` lands, so `requireTeachesCourse` on `EXAM_CREATE` and `EXAM_AUTO_COMPOSE`
rides it too. E7 therefore resolves the taught set at **one** point in `ExamService` rather than at
each of the two verbs that carry a course, with a comment naming this fix. When the component
lands, the approximation leaves E7 in one edit instead of two.

**6.4 Two corrections to the rulings you sent, both from the code rather than from an opinion.**

**Both accepted, and this section is now the record rather than a request.**

*On the hop.* You wrote that a second one would be a no-op either way.
`PlatformFxThreadPoster.run` is an unconditional `Platform.runLater` with no
`isFxApplicationThread` check, so once yours lands inside `publish`, mine would be a second
deferral rather than a no-op: the lock state would apply a pulse later than the code around it.
**I drop my call-site fix when I pull yours** rather than keep both. Your publish() routes through the poster regardless of calling thread, so an FX-originating snapshot arrives a pulse deferred; you have documented that as deliberate and it is invisible for a banner.

*On the lock consult.* Locks are a `ConcurrentHashMap` in `EditLockService`, not a table. So there
is no repository read, and two-engine tests do not apply to state that never reaches a database.
The guard consults a live service instance, which means `QuestionService` needs it injected and
`HSTSServer` needs a constructor change rather than the one registration line my opening covers.
Worth writing down while we are here: **the guard is therefore per-process and not durable.** That
suits the semantics you ruled, and it is better said now than discovered during the two-machine
rehearsal.

**6.5 Answered before this report reached you, and kept as the record.**

The question was where a shared `EditLockGuard` could live: `server/features/locks` is E18's and
not open to me, `server/core` is closed except `Authorization` and `HSTSServer`, and putting it in
`server/features/bank` would make E7's call a cross-feature import of internals, which TEAM_SPLIT
rule 4 calls a review-reject. There was no legal home for it.

**You answered by writing it yourself** in `server/features/locks`, and by opening the
`QuestionService` construction line in `HSTSServer` to me for this PR and `ExamService`'s for E7.
That settles both halves at once: the semantics live in one place under their own owner, and the
callers get the opening they need without the package changing hands.

Semantics as ruled, recorded so nobody re-derives them: an unexpired lock held by another answers
`CONFLICT` with `BankMessages.lockedBy` — the sentence finally gets its caller — an expired one
does not block, your own never blocks, and `baseVersionNo` stays the final arbiter **after** the
consult. The lock is the polite refusal; the version check is the correctness guarantee.
