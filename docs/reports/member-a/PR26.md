## 3. The decision you should push back on if you disagree

**A missing image fails the seed load, loudly and by name, behind a build-time guard.**

The runtime question ("what does the loader do when the file is absent?") is the wrong place to
spend the guarantee. The real fix is making the state unreachable at build time. `SeedImagesTest`
resolves every flagged question's image **through `getResourceAsStream`, the same call the loader
makes** — resolving through the classpath rather than checking the filesystem is the point, since
a filesystem check passes from a working copy and proves nothing about the jar, and "worked
locally, missing from the jar" is the failure that drove your ruling 2.

Behind that guard the runtime branch refuses rather than loading NULL, because a seed that quietly
ships without illustrations is the gap B-8 was filed about.

### What the guard does NOT do

**It does not check that a committed PNG is what the generator would draw today.** I intended
byte-equality and dropped it after measuring: four of the ten carry text, and Java2D maps
`SANS_SERIF` to whatever physical font the host has, so bytes differ between a Windows author and
CI's Linux. That test would pass for whoever generated the images and fail for everyone else.
**Consequence to accept knowingly:** edit a drawing, forget to regenerate, and nothing catches it.

**A limit found by planting.** Deleting `q11007.png` and running *without* `clean` failed only the
source-tree test — Maven had copied the old file into `target/classes`, so the classpath lookup
found a stale copy and passed. After `clean`, both fail. The classpath half answers "will the
packaged jar have this?" and is trustworthy on CI, which runs `clean verify`; on an incremental
local build it may be reading yesterday's resources. Both halves are kept; the javadoc says which
is which.

## 4. What the cold read found ⚑

### 4.1 The guard class never read the seed, and three documents said it did

`SeedImagesTest.illustratedIds()` returned **`SeedImageGenerator.drawings().keySet()`**. So:

- `generatorMatchesTheSeed` compared that expression **to itself**. There was no input for which
  it could fail.
- `flaggedQuestions()`, the source for `everyFlaggedQuestionHasAnImage`, was also generator ids.
- The only seed-side thing the class touched was `illustratedCount()` — a **number**, which cannot
  say *which* ten.

**Move the `img` flag from `21006` to `21007` and every test stayed green on a seed that throws at
load.** The count is still ten, `q21006.png` still resolves, and the drift test is a tautology.

Three durable records asserted otherwise: the class javadoc sold it as a distinct drift axis,
`QuestionBankSection`'s javadoc said "the build-time guard in SeedImagesTest is what should catch
this first", and §3 of this report said a disagreeing flag and file "fail the build". They agreed
with each other and differed from the code — P-6 exactly.

**Root cause, and why the fix is in production rather than in the test:** the seed had no way to
say which ten. `QuestionBankSection.illustratedIds()` now exists, and all three tests read it.

**Planted:** moving the flag from `21006` to `21007` now fails **three** tests — the resource
lookup, the orphan check, and the drift check. Before the fix it failed none.

### 4.2 Six of ten narrowed their own answer, and one handed it over

The generator's javadoc stated a rule — *"an illustration that answers its own multiple choice is
worse than none at the defence"* — and applied it to the two text diagrams (`21006`'s "Map",
`21010`'s "base case", both now `?`). **The six plots were never checked against it.**

`11007` is the outright failure: it asks *how many* x-axis intercepts `y = x² + 2x + 5` has, the
answer is "None", and I drew that parabola sitting clear of the axis. The count is readable
straight off the picture with no algebra, and `11007` is on the demo paper. **Redrawn** as a
reference figure showing all three cases — two intercepts, one, none — with no indication which
applies.

The other four (`11005`, `11006`, `11010`, `12007`) narrow but do not resolve: no tick labels, so
she can see two positive roots close together and still has to compute them. That is what a
textbook figure does, and the rule is now stated at class level with that boundary explicit rather
than implied by one method's javadoc.

### 4.3 The stale sentence survives in two files that are not mine

`TakeExamQuestion`'s equals javadoc predicted content-based equality would start mattering "the day
real assets land". Corrected there. The same claim is live, verbatim, in **`common/dto/exam/
ExamQuestion.java:88`** and **`src/test/java/common/dto/exam/ExamDtoTest.java:186`** — both state
that every seeded question has a null image, which is now false, and `ExamQuestion` is the wire
type that carries these exact bytes to a student. Both are outside my paths. **Item 2 below.**

## 9. The lesson

**A guard is only as good as the list it reads.** §4.1 was not a wrong assertion — every assertion
in that class was correct. It was a correct assertion about the wrong list, and the name, the
javadoc and this report all described the list I meant rather than the one in the code. Planting
would have caught it, and I planted the resource-missing case and the v2 case and not the
flag-moved case, because I was planting the failures I had thought of.

The pattern this PR adds to method rule 4: **when a guard compares two lists, plant a change to
each side separately.** A tautology passes every plant aimed at the thing it is supposed to be
comparing, and fails only a plant aimed at the comparison itself.
