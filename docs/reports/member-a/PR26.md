## 3. The decision you should push back on if you disagree

**A missing image fails the seed load, loudly and by name, behind a build-time guard.**

The runtime question ("what does the loader do when the file is absent?") is the wrong place to
spend the guarantee. The real fix is making the state unreachable at build time. `SeedImagesTest`
resolves every flagged question's image **through `getResourceAsStream`, the same call the loader
makes** — resolving through the classpath rather than checking the filesystem is the point, since
a filesystem check passes from a working copy and proves nothing about the jar, and "worked
locally, missing from the jar" is the failure that drove your ruling 2.

Behind that guard the runtime branch refuses rather than loading NULL, because a seed that quietly
ships without illustrations is the gap B-8 was filed about.

### What the guard does NOT do

**It does not check that a committed PNG is what the generator would draw today.** I intended
byte-equality and dropped it after measuring: four of the ten carry text, and Java2D maps
`SANS_SERIF` to whatever physical font the host has, so bytes differ between a Windows author and
CI's Linux. That test would pass for whoever generated the images and fail for everyone else.
**Consequence to accept knowingly:** edit a drawing, forget to regenerate, and nothing catches it.

**A limit found by planting.** Deleting `q11007.png` and running *without* `clean` failed only the
source-tree test — Maven had copied the old file into `target/classes`, so the classpath lookup
found a stale copy and passed. After `clean`, both fail. The classpath half answers "will the
packaged jar have this?" and is trustworthy on CI, which runs `clean verify`; on an incremental
local build it may be reading yesterday's resources. Both halves are kept; the javadoc says which
is which.

## 6. B-13 — the document made to say what the loader stores

### 6.1 What landed

**Twenty stored strings**, across §7, §8, §8.2, §9.1, §10, §10.1, §10.2 and §11, now read exactly
as the loader writes them. Every replacement was read out of the Java rather than derived from the
rule, and that mattered: the loader is not uniform. It uses a **colon in titles** (`Midterm:
Algebra`, `Study assistant: Algebra`) and a **comma inside sentences** (`A draft, not yet checked
against the marking scheme.`), which is exactly what §4.1 licenses and what `followsHouseRule`'s

**The sentinels are untouched.** `SeedDocument` reads `—` in a cell as *"no row at all"* — §4's

**The note in the rules table** records why the stored form differs, so the next reader does not
refile this. It also does something the ticket did not ask for and I think earns its place: it
lists **which values a test actually compares and which it does not**, because after §6.3 and §6.4

### 6.3 The plant that went through ⚑

Per the method rule, a two-list comparison gets a plant on **each side**. I changed the document to
say `Midterm. Algebra` while the database said `Midterm: Algebra` — a still-legal house-rule form,
so it should have been caught the moment the dashes were gone.

**The suite stayed green.**

`examsMatch` compares `displayId`, `courseCode` and `author`, and its `@DisplayName` says exactly
that. `ev.name` was read by precisely one thing in the entire test tree: the em-dash sweep, which
asks whether a *character* is absent and never whether the string is the documented one. **No test
compared a seeded exam name to the document.** All six were unchecked text.

So B-13 as filed — correct the names — would have been worth very little. A value nothing compares
does not stay corrected. `SeedLoadedDbContract.examNamesMatch` now compares them, and the same
plant fails it naming both sides.

This is the general form worth keeping: **a count is not a list, and neither is a character
class.** A guard asking "is there a dash in this column" agrees with every string that has no dash,
including the wrong one.

## 10. The lesson

**A guard is only as good as the list it reads.** §4.1 was not a wrong assertion — every assertion
in that class was correct. It was a correct assertion about the wrong list, and the name, the
javadoc and this report all described the list I meant rather than the one in the code. Planting
would have caught it, and I planted the resource-missing case and the v2 case and not the
flag-moved case, because I was planting the failures I had thought of.

The pattern this PR adds to method rule 4: **when a guard compares two lists, plant a change to
each side separately.** A tautology passes every plant aimed at the thing it is supposed to be
comparing, and fails only a plant aimed at the comparison itself.

**B-13 is the same lesson from the other end, and it is the reason the rule is worth the cost.**
Here the plant was aimed correctly, at the comparison — and it went straight through, because
there was no comparison. B-8's defect was a guard reading the wrong list; B-13's was a value with
no guard at all, and from the outside the two are indistinguishable. Both look like a green suite.
So the plant does not merely test the check. **It is the only thing that discovers whether a check
exists**, and the ticket that finally proved it was a documentation ticket nobody expected to find
anything.

The corollary that generalises past this PR: when a ticket says *"the document and the code
disagree"*, the interesting question is never which one is wrong. It is **why nothing noticed** —
and three times in this one pass the answer was that the disagreeing value was the one value no
test read. Fixing the values without fixing that would have left the document just as free to
drift, and the next person just as sure it could not.
