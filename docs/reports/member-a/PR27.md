# PR27 — E18.5: the builder's edit lock, and the door it was leaving open

Closes the **exam builder half of E18.5**. Two teachers on one exam version: the server already
refused the second save, and she found out at the end. Now she is told at the start, by the same
banner the question editor and the bot manager have had since E6.14.

It also installs the **`exam-version` entity scope**, which is not lock wiring and is in here
deliberately — §4 is the argument, and it is the part of this PR I would most like you to
disagree with if you are going to.

Two cold reads. The second found a bug that had survived four plants and a green suite, and §3 is
the whole story because the shape matters more than the fix.

## 3. The bug four plants did not catch ⚑

`onHide` released the lock and took it straight back.

`close()` publishes an IDLE snapshot. IDLE is not OWNED, so `renderLockState` set the session
locked-out, which fired `onChange`, which ran `onSessionChanged`, which called `syncLock` — and
`syncLock` found `examVersionId` still set and `locks.entity()` just nulled, so it opened the lock
again. Release and re-acquire on the same pulse, then the heartbeat renewed it for the life of the
process. **The hold outlived the TTL that was supposed to be its backstop**: every exam Dana opened
stayed "being edited by Dana" until she logged out.

**My test could not have failed on it.** It asserted:

```java
assertThat(verbsSentOn(held[0])).contains(Verb.LOCK_RELEASE);
```

which stayed true throughout. A test that names a behaviour and survives its inversion — P-6's
shape, written by me, in the same PR where I planted four other mutations.

**Why the plants missed it.** All four asked whether the lock was *taken* correctly: wrong type,
wrong id, gate removed, close removed. Not one asked whether it was ever *given up*. The fourth
came closest and still passed, because deleting the `close()` call and having the close undone by
its own side effect look identical from outside — both end with the lock held, and only one of
them fails an assertion about a verb being sent.

The rule this adds to method 4: **when a plant and the real defect produce the same observable
state, the plant proves nothing.** Ask what the assertion would say if the code were wrong in the
way you are not thinking of.

Fixed with a `showing` flag consulted by `syncLock`, and the test now asserts nothing acquires
after the last release. Planted: removing the flag reproduces it exactly, `[LOCK_RELEASE,
LOCK_ACQUIRE]`.

## 4. The scope, which is not lock wiring ⚑

**`EntityScopes` is unfiltered for any type nobody installs, and only `question` was installed.**
So `LOCK_ACQUIRE` on `("exam-version", n)` answered any teacher: the version exists, and here is
the author's name. She could then hold that author's builder read-only for as long as she kept
renewing, because `ExamService` consults `heldByAnother` before every write.

Every other E7 verb refuses this by design, and the contract says why in as many words: *"Naming
the exam would tell a caller probing ids that it exists and who owns it, which is the existence
oracle P-5 is about."* `LOCK_ACQUIRE` was the one door left open on the same rows.

**It was theoretical until this PR.** No client took exam-version locks. The builder's lock is what
makes it reachable, so it is closed in the change that opens it rather than filed behind it. That
is the judgement call — the alternative was a smaller diff and a stated contract violation live in
`main` until someone picked it up.

**`E18-SCOPES.md` §1.6 is stale and I did not edit it.** It says "`acquire` is not scoped … this is
the one item in this report that is still open". `EditLockService.acquire:197` consults
`scopes.reaches` and refuses out-of-scope callers as free, taking nothing and naming nobody. It
closed at some point after that report and the document did not follow. Yours to correct or leave.

**Author only, and that is the whole rule.** `EXAM_VERSION_GET` answers only `authoredHeader`, so
the builder is a screen nobody but the author can open, and the approval path reads through its own
verbs and takes no lock. The set who can reach an exam-version lock and the set who can author the
exam are the same set. If a later feature gives a coordinator a lockable view of someone else's
exam, `ExamLockScope` is the one place that changes and nothing will remind whoever writes it.

**The install is one line, in your file:**

```java
locks.scopes().install(EntityRef.EXAM_VERSION, ExamLockScope.of(sessionFactory));
```

beside `question`'s. Built-not-installed for the reason `questionLockScope` is: so a test runs that
exact lambda against a real database. **Until you add it, the scope is dead code and the exposure
is still live** — that is the one thing in this PR that does not work on merge.

### 4.1 The test that was disarmed by its own fixture

`theExamIdIsNotTheVersionId` failed on its first run with `expecting 3L not to be equal to 3L`. One
exam plus one version put both sequences on the same number, so a predicate comparing the exam id
would have passed **every assertion in the file** — including the test written to catch exactly
that.

Fixed by inserting a decoy exam in the helper so the sequences never march in step, which
immunises the whole class rather than the one test. Same lesson as PR26's §6.3 in different
clothing: **a check that reads the right thing from a fixture where two different things happen to
be equal is not a check.**

## 9. The lesson

**A plant only proves what it can distinguish.** §3's defect and the plant I aimed at it produce
the same end state — the lock still held — and differ only in how they got there. So the plant
passed, the assertion passed, and the feature was broken in the one direction nothing was looking.

The four plants were not careless. They were four ways of asking the same question: *is the lock
taken correctly?* None asked *is it ever released?*, because by the time I was planting I had spent
an hour thinking about acquisition. The cure is not more plants. It is to write down what the
feature promises — takes the lock, shows who has it, **gives it back** — and check that some plant
can falsify each clause. Two of three had one. The third had a test that could not fail.
