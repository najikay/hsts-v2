## 3. The tasks

### 3.1 E7.12 — the picker, and the field it waited on

The selected list, points editors, reorder and live Σ landed in #52. What completes E7.12 is the
add path, unbuildable until BANK A1 because `QuestionPin` keys on a version id and the bank wire
carried none.

The row is pinned at `latestVersionId`, so the paper carries the exact version she was looking at
when she clicked, which is what makes E7.7's badge a drift detector afterwards rather than a
coincidence. Points start at `MIN_POINTS` rather than a share of 100: an even split would silently
rewrite numbers she had already set, and §5.1's indicator is what tells her how far off she is.

**T-3.9 is refused on the click**, on `displayId5` and never on a version id, so 11005 v1 beside
11005 v2 is one question here exactly as it is to `uq_exam_version_questions_question`. The server
still checks and is still the guarantee; what this adds is that the refusal arrives on the click
that caused it rather than ten minutes later on save.

Scoped to the exam's own course, filtered client-side over one load rather than a round trip per
keystroke, with four distinct empty states because an empty bank, a filter matching nothing, a
failed load and a truncated one are four different things to be told.

**The picker lives inside `ExamBuilderView`** rather than in a screen of its own. A separate thin FX
class would need its own JaCoCo exclusion and the pom is not mine; every decision it makes is in the
session regardless, so the split would have bought a file and a coverage argument.

### 3.2 E7.13 — the auto tab

A segmented switch, a criteria grid whose first row is always the course-wide quota, and **counts
rather than sliders**: `TopicQuota` carries integers and a slider is a control that cannot express
what the wire does.

**The live rule is `ExamValidator.quotaProblem` itself**, the method the handler refuses with,
exactly as the Σ indicator is `pointsProblem`. §7.3a's refusal must name both legal shapes and
`ExamBuildMessages` owns that wording, so this client composes none of it (ruling 4).

A feasible answer **replaces the paper and lands her on it**, which is what makes F3.3's "editable
before save" true rather than claimed: the proposal goes into the same `lines` list the manual tab
edits, and there is no second composition anywhere in the session. An infeasible one changes
nothing at all — §7.2's report is the useful outcome, and a refusal must not cost her the paper she
had.

**The infeasibility sentence is composed once, in `ExamBuildCopy`**, per ruling 4, and PRD F3.3's
own string is pinned by a copy test beside §7.1's other three shapes:

```
Topic 'Algebra': requested 5 Hard, bank has 2
```

Where §7.1's table and the PRD disagree on quoting, the PRD wins: it is the acceptance artefact.
Grades render title case, parameterised over the enum, because `Difficulty.HARD.toString()` is
`"HARD"` and "requested 5 HARD" is the kind of thing that ships because nobody read it out loud.

### 3.3 E7.14 — the update action, and §4 amendment A1

**Attribution stated so it can be disagreed with:** the *version history* half is E7.10's exam list,
which already lists every version with its state, question count and duration. Nothing new was built
for it. The *badges* have rendered since #52. What PR24 adds is the action.

The whole vertical is here under your opening of 2026-08-26: the DTO component, the dated §4
amendment on BANK A1's template, the repository subquery, the service population, the DTO shape
rows.

Re-pinning takes no verb of its own. The composition saves by full replace, so it is a change to the
list like a reorder and reaches the database through the `EXAM_VERSION_SAVE` she was going to press
anyway. A dedicated verb would be a second write path into one composition, which §5.6 exists to
prevent.

**The row keeps the old wording until she saves, and says so.** The wire carries the newer version's
id and none of its text. See §4.1 for what that cost before it was caught.

### 3.4 E7.16 — the integration test

`ExamBuildRoundTripIntegrationTest`: the assembled stack against real MySQL, walking all five
journeys the row names — manual, duplicate, Σ≠100, auto-feasible, auto-infeasible, versioning.

**MySQL only, and not out of laziness.** The H2 schema is generated from the entities and reproduces

unrelated to what the class claims.

**Nothing is asserted against what a write returned.** Every check is a second call in a new
transaction, so it sees committed state rather than the first-level cache.

## 4. The audits, and what they found in my own work

**Two cold reads, ten confirmed defects, every one mine.** The second pass was run because the first
had a suspicious shape: I gave it five specific claims plus one free-hunt prompt, **all five
targeted claims came back sound, and all three defects came from the free hunt.** Steering it cost
findings, so the second pass was framed the opposite way — no claims list, pointed instead at the
areas the first had not reached and at the fixes the first had prompted.

### 4.1 Saving a re-pin left the old wording on screen permanently ⚑

The paper rebuilds only when its *shape* changes, and the shape was the list of pinned version ids.
A re-pin changes an id, so the card rebuilt at the click carrying the old wording by design. The
save's re-read then returned rows with those same ids, the shape matched, nothing rebuilt.

She presses the button precisely because the wording was corrected, saves, gets "Saved", and the
question still reads the old way with no badge, no notice and no control left to press. **The saved
pin was correct throughout**, which makes it worse: the screen and the database disagree silently
and the only available conclusion is that the update failed.

Fixed by putting the stem, both version numbers and the staleness marker into the key, with the rule
the key follows written down: every term a server re-read can change and the cards draw from, and
nothing she can be halfway through typing.

### 4.2 A compose in flight landed on whichever exam was open when it arrived ⚑

`resetLoaded` bumped the load counter and, via `closePicker`, the picker counter. It never touched
the compose counter, and `settleCompose` guards on that and nothing else. The screen is cached and
reused across navigations, so: press Compose, answer is slow, go back and open another draft — that
draft's paper is cleared, filled with the first exam's questions, and announced with a success
toast. If the two exams share a course it saves cleanly.

**The more valuable half is the javadoc.** `resetLoaded`'s own comment stated the invariant that was
false — "bumping the generation is what makes an answer already in flight land on nothing" — and it
was written to record the *load* version of this defect. The compose instance was never added to it.

### 4.3 The auto tab stranded a read-only version ⚑

`tab` survived `open()`. Land on a finished version from the auto tab and the manual pane is hidden
because the tab is AUTO, while the tab switch is hidden because a read-only version is not editable.
She navigated in to read a paper and the paper is not on screen, with no control that brings it
back, for the rest of the app session. The existing read-only test opens the finished version first,
so it structurally could not see this ordering.

`criteria` survived too, so a report could name a topic from another exam's course — against §7.2's
promise of a number she can reproduce by filtering her own bank.

### 4.4 The infeasibility report outlived the criteria it answered

`INFEASIBLE_TITLE` says "the bank cannot satisfy **these** criteria" and points at the grid above it.
T-3.5 and T-3.6 are two shots with a criteria edit between them, so on the demo path she edits three
down to two and the red block still says three.

Same class as 4.6 below, one round apart: a stored artefact outliving the state it describes.

### 4.5 The picker appended a page it had not asked for

The paging loop appended whatever came back without checking it was the page requested. A server
answering page 0 twice would show page 0's questions twice and page 1's never, with a full-looking
list, no error and nothing failing. Found because a test fixture did exactly that by accident.

### 4.6 Four smaller ones, all confirmed and fixed

- **The re-pin notice outlived its rows.** Composing replaced every line with server rows and the
  notice stayed above them. `hasRepinned` is now derived from the rows rather than stored, on the
  same argument `Mode` already makes in that class: a fact derived from the rows cannot disagree
  with the rows.
- **The picker's retry was clickable while the picker was shut.** Hiding a panel does not hide the
  controls inside it as far as a scene lookup is concerned.
- **`parseMinutes` parsed bucket counts.** Its fallback is justified by "zero is out of range",
  true of a duration and false of a count where zero is the default every row starts at. A mistyped
  count became a silent legal zero while the box went on showing what she typed. Split into
  `parseCount`, falling back to `-1`, which the server's own negative-bucket rule refuses.
- **A comment claimed a general tripwire** the seed test only provides for the pairs the dataset
  happens to contain. Reworded to its actual reach.

### 4.7 Two defects in the tests themselves, found by planting

Both are worth more than the code fixes, because a test that cannot fail is worse than no test.

- **`reviseKeepsThePredecessor` never asserted what version 2 carried.** A plant writing the carried
  composition onto the predecessor left version 1 looking untouched — it already held those rows —
  and version 2 empty, and every assertion passed.
- **The TestFX visibility helper reported nodes inside hidden panes as visible.** Harmless while the
  screen hid single controls; the moment E7.13 hid whole panes, the manual tab's assertions started
  finding the auto tab's headings. It never *failed* — it only ever made `doesNotContain` weaker
  than it read, and one test was passing while asserting a screen had no tabs when it plainly did.

Also: a click landed off-screen once the screen outgrew the test window, and the symptom was not a
crash but a total that had not moved. Every click in that file now goes through one helper that
scrolls the node into view first, and the harness sizes the window to what a headless screen can
show.

### 4.8 R2's widened pool found a defect on its first run

Your R2 ruling asked for Hebrew and accented topics in the composer's property generator. It failed
immediately — and the defect was in **the test's own oracle**, not the composer. It counted matching
questions with `equalsIgnoreCase`; the composer counts them with `sameTopic`. `Récursivité` and
`Recursivite` are one topic to MySQL, to the composer and to a teacher filtering her bank, and two to
`equalsIgnoreCase`. The oracle was calling the right answer wrong, invisibly, for as long as every
generated topic was unaccented ASCII.

Pointed at `sameTopic`, with why that is not circular written down: this property now tests that
`available` counts the right rows *under the project's topic equality*, and the fidelity of that
equality to MySQL is #48's bidirectional test — which R2 itself named as the tripwire. One guard per
seam.

### 4.9 What the audits confirmed sound

The duplicate rule cannot be walked around (re-checked at click time, on a `CHAR(5) NOT NULL UNIQUE`
column, so no collation or whitespace variant exists). `latestVersionId` carries no newer-version
content anywhere. The auto tab composes no sentence `ExamBuildMessages` owns. The nested subquery
names no key column and is single-valued by constraint. The correctness boundary is untouched:
`PinnedQuestion` and `ComposedQuestion` still have nowhere to put `correct_answer`. Hebrew and RTL
add no truncation, no width measurement and no locale-sensitive folding of user data.

## 5. The correction to your ruling, and it is load-bearing

You wrote that selecting `latestVersionId` "rides the same subquery" as `latestVersionNo`. **It does
not.** `max(later.versionNo)` yields a number, and the id of the row holding that number is a second
question. So this is a nested correlated subquery selecting the id *at* the maximum.

The shortcut the wording implies is `max(later.id)`. I planted it: it compiles, it runs on both
engines, and it **passes 37 of the 38 repository cases**. The only thing that catches it is
`latestIdIsTheIdAtTheLatestNumber`, on a fixture that writes a question's versions out of order
(3, then 1, then 2) so the newest version holds neither the newest id nor the oldest. On a question
whose versions were written in sequence every implementation agrees, which is why the obvious fixture
proves nothing.

If it had shipped, the update button would have silently re-pinned questions to the wrong version of
themselves. No points rule, duplicate rule or constraint stands in the way, because a wrong version
is still a valid pin.

Your design intent holds — it rides the same **read**, no second pass, no extra round trip. It costs
one more subquery inside that read, not zero.

## 8b. Filed with this PR

**`docs/PROBLEMS.md` P-13 — a cache or a reset keyed on a subset of what can change.** Four of this
PR's defects were one shape: something decides whether to redo work by comparing a key, and the key
omits a term the work depends on. Nothing throws, the model stays correct, and the screen does not.
The entry names the redraw key, the two halves of `resetLoaded`, and the stored report, and states
the rule both ends need: a key holds every term the work reads, a reset covers every answer that can
still be in flight, and both are lists that grow when the feature does.

It also records why the suite could not see any of them: every one is a property of a *transition*,
and the tests were rich in states and thin on pairs of them.
