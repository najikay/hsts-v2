## 3. The tasks

### 3.1 E7.10 — the list

Master and detail rather than an expandable tree, and the reason is not preference: there is no
`TreeTableView` anywhere in this client, `DataTable` is flat, and an expandable row would mean a new
shared component under `client/ui`, which is not mine to write. The exams on the left, the selected
exam's versions as cards on the right, which is the shape `BankView` already uses.

**Actions come from the frozen contract and nowhere else.** `canSubmit` is `isEditable()`, which is
`DRAFT` and nothing else (§5.4, matching `ExamService.java:580`); `canRevise` is its negation (§5.4,
matching `:478`). The audit checked both against the service independently and confirmed no state is
offered a button the server refuses on state grounds, nor refused one it would accept.

**No release button** (§9: E9 owns that). **No Edit button** — see §5.2.

### 3.2 E7.15 — the confirmation, folded in here

`ExamVersionRow` already carries the question count, the duration and the version number, and the
points always total 100 because §5.1 refuses a save that does not. So the summary is exact and needs
no second call. The revise dialog deliberately **does not predict the new version number**: it is
allocated against `uq_exam_versions_no`, so any number the dialog names is one concurrent revise
away from being false. `revisedNotice` names it afterwards, off the server's own answer.

### 3.3 The guard that makes this PR red

`ExamListWiringGuardTest` has seven cases: registered for somebody at all (which is #25 on the
client side), each authoring role, the student, the principal, the end-state mapping, and the
retirement. Five pass today. Two cannot pass until the assembly lands, which is the point.

### 3.4 The exam list was in filing order, not recency ⚑

Contract §4's ruling of 2026-08-25 names this PR or PR B as where it lands, so it lands here.
`findAuthoredExams` ended `order by e.displayId`, which is `subjectCode + courseCode + serial`:
ascending sorts by subject, then course, then **oldest first within a course**, so a teacher with
exams in two courses got neither recency nor anything else. It is now
`order by v.createdAt desc, e.id desc`.

Two things worth your eye:

- **Recency is the latest version's `createdAt`**, because that is when she last touched the exam
  and `v` was already bound to that version. An exam started in March and revised yesterday is an
  exam she touched yesterday, and there is a test for exactly that.
- **`e.id desc` is a tiebreak, not decoration.** A seeded database writes many rows against one
  clock instant, and neither engine promises an order for ties. That is the defect class that
  survived a whole green suite in #50.

The old pin, `examListIsOrderedByDisplayId`, is gone. **It would have passed under the new query for
the wrong reason** — it seeded both exams at the same instant, so the id tiebreak happened to
produce the same order it asserted. Replaced by three tests that discriminate, and all three catch
their mutations on both engines.

## 4. The audit, and what it found in my own work

Run after the code was written, against the code, with named claims. **Nine findings. I verified
every one against the source before acting; all nine were real.** Three were defects the suite could
not see, two were javadoc of mine asserting properties the code did not have — P-6's class, in files
I had just written.

### 4.1 The live re-read did not exist ⚑

My javadoc said an approval push re-queries the list "without her pressing anything (NFR-18)" and
pointed at `onDecisionArrived()`. That method had **no production caller** — not on my session, and
not on `MyApprovalsSession` either, whose `listensToEvents()` returns `false`. So the behaviour I
described as inherited had never existed on the screen I was inheriting it from, and my test called
the method directly, which would pass with every wire cut.

Now genuinely wired: the session subscribes itself to the bus (`MyGradesSession`'s shape, so the
wiring sits where a test can reach it), filters `PUSH_NOTIFICATION` on the three approval types, and
the test pushes a real `NotificationDto` through a real `ClientEventBus`.

### 4.2 A double press made two drafts of one exam ⚑

The buttons are gated on `isActing()`. I cleared that flag when the **write** answered and then
re-read the list, so for one network round trip the card for the version she had just revised was on
screen, unchanged, with a live Revise on it. Nothing downstream catches it: `ExamService.revise`
refuses a version that is *itself* a draft and does not touch the predecessor's row, so the second
press passes the same lock-token check and inserts again at `findLatestVersionNo + 1`. One approved
version, pressed twice, becomes v4 **and** v5.

Fixed by holding `acting` across the re-read and releasing it in `settleList`. One rule, stated in
the code: every path that re-reads releases the buttons there; every path that stops releases them
itself.

### 4.3 A CONFLICT threw away the only sentence that helps ⚑

§6 gives CONFLICT three causes and only two are staleness. The third is **the version being
edit-locked by a colleague**, live on both these verbs, and there the server's sentence *names him*.
I was replacing it with "check the version before trying again" — which sends her to look at a
version with nothing wrong with it, and the next press says the same thing. That is the loop the
reload exists to break, reproduced by the client. The server's sentence is now kept when there is
one, and the reload still happens because staleness is still possible.

### 4.4 The wiring guard over-claimed ⚑

Its own javadoc said it fails "until they are gone" about five artifacts; it read one file. An
assembly that deleted one line of `SessionRoutes` would have gone green with the verb, the screen,
its session and the DTO all still live — the window §8 exists to close, passing a guard written to
prevent it. It now also asserts `MyApprovalsView` and `MyApprovalsSession` are off the classpath and
that `MY_APPROVALS_GET` is gone from `Verb`. The verb is checked **by name** rather than by
referencing the constant, so removing it does not break this file's compilation.

### 4.5 Five column headers were outside the em-dash guard

`ExamListCopy`'s javadoc claimed the view holds no strings of its own. It held `"Exam"`, `"Id"`,
`"Course"`, `"Versions"`, `"Latest"` — user-visible text the reflection-based house-rule check could
not see. Moved into the copy class, which makes the claim true and the guard complete.

### 4.6 `ExamService.revise`'s comment claimed a guard it does not have

It read "revising a draft would leave two drafts of one exam". The check is on the **addressed**
version only; nothing asks whether the exam already has a draft elsewhere. Revising v1 while v3 is a
draft passes it — reachable from this very screen, which offers Revise on every non-draft version.
§5.4 says only "`EXAM_VERSION_REVISE` refuses a `DRAFT`", so **the code matches the contract and the
sentence was what was wrong.** Comment corrected. I did not widen the behaviour: see ask 3.

### 4.7 and 4.8 — two I cannot fix, because the files are yours

- **The deep link is never delivered.** `NotificationsPanel.activate` calls
  `navigator.navigate(ref.route())`, the one-argument overload, which passes `NavParams.empty()` and
  drops `ref.entityId()`. `NavRef` carries the id and `NotificationCatalog` sets it; the panel throws
  it away. This is not specific to my screen: **every notification in this app lands with no
  context.** My half is built and tested; yours is one line. Ask 1.
- **The retirement removes the only way to read a version.** `MyApprovalsView`'s row click opened
  `ExamPreviewView`; mine selects a row. So after the swap a teacher can read a rejection reason and
  cannot open the exam it is about. Partly pre-existing — `EXAM_PREVIEW` is registered for
  coordinators only, so for a plain teacher that path already threw `IllegalArgumentException` — so
  the live regression is for a **coordinator author**. I did **not** add a View button: navigating to
  an unregistered route throws, which would be worse than the gap. Ask 2.
