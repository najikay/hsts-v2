# PR28 — M-3: the exam builder had no front door

Closes **M-3**, found by hand on 2026-08-28 during the manual round: a teacher could open, submit and revise the exams the
seed had written, and could **never start one**. `EXAM_CREATE` was frozen, registered, implemented
and tested; `ExamBuilderSession.Mode.CREATE` sent it; `ExamBuilderView.onShow` documented the door
it arrives through. The only navigation into the builder anywhere in the client carried an
`examVersionId`. Every layer worked and nothing reached the one that mattered.

The fix is small. **§3 is the part worth your time** — not the button, but why nothing in a green
suite could have told us, and what that says about the three E-rows that ticked honestly on either
side of the gap.

Found during the manual round that `docs/TODO.md` E7.17 has been waiting for. Not a regression:
this has been the state since the builder landed.

## 3. The gap three green rows and a green suite all agreed with ⚑

**Two independent causes, and neither was carelessness.**

**The task list had no row for it.** `E7.10` specified the exam list as *"teacher's exams, status
chips, versions expandable, actions per state"* — and every action a state permits operates on an
exam that already exists. `E7.11`–`E7.13` specified the builder. Both descriptions are accurate,
both rows ticked truthfully, and *the control that starts one* was in neither. The gap was not
between a row and its code; it was between two rows.

**The suite could not reach it, structurally.** `ExamBuilderSessionTest` enters `CREATE` by calling
`openNew` itself. So create-mode was thoroughly covered **while being unreachable by a human**, and
every test that touched it passed for the whole time the feature was unusable. That is
`docs/PROBLEMS.md` **P-6** in its purest form: the author wrote the code, the author wrote the
tests, and the shared assumption — *something navigates here* — was never written down anywhere it
could be checked.

**So the three tests in this PR are written against reachability, not against the mode.** Mode
`CREATE` already had coverage. What had none was the claim *a control on a screen reaches it*, and
that is the claim that was false.

The generalisable form, and the reason this section is longer than the fix deserves:

> **A feature can be complete at every layer and still not exist.** Layer-by-layer tests multiply
> to zero as happily as they multiply to one, and nothing in a green suite distinguishes the two.
> The only check that can is one that starts where a user starts.

### 3.1 What made it invisible for three days

The seeded database is never empty. The exam list always has rows, so the screen looks like a
working screen doing its job, and "no way to add" reads as "nothing to add right now". On an empty
database it would have been obvious on the first look.

## 4. The three decisions, and why each is not a style call

**The course is chosen before the builder opens.** Not a preference: the builder has no control for
a course and cannot cheaply have one. `openNew` takes the code as given, the bank picker is scoped
to it, and `ExamCreateRequest` carries it. A builder entered with no course can pick no questions
and save nothing, so the menu asks once, up front, and that state is never reachable.

**The menu offers only courses she teaches.** That is exactly the set `requireTeachesCourse`
accepts, so the menu cannot offer a choice that becomes a `FORBIDDEN`. Deliberately **not**
`BankSession.courseOptions`'s union with the browsed bank: that widening exists because the bank's
*read* scope is wider than authorship on purpose (contract §2), and borrowing it here would offer a
coordinator a course she may read and not write.

**Zero courses disables with the reason rather than hiding.** `rina.barak` reaches this screen and
holds no `course_teachers` row. A hidden control is indistinguishable from the absent one this PR
exists to fix, so hiding it would make M-3's own symptom the correct rendering for a real starred
demo account. She gets the same answer the server would give her, earlier and in a sentence.

**Courses come from the sign-in payload**, where `BankView` reads them, so this adds no verb.

### M-4, since your ruling names the cause and this report should carry it

Your thread hypothesis is right and it is measurable from this side too. `ExamEntrySession`'s only
constructor takes a dispatcher and no poster (`ExamEntrySession.java:76`), and it is one of exactly
two sessions in the client without one:

```
BankView:109          new BankSession(dispatcher(), onFxThread(), ...)
ExamBuilderView:151   new ExamBuilderSession(dispatcher(), onFxThread())
ExamListView:75       new ExamListSession(dispatcher(), onFxThread())
TakeExamView:67       new ExamEntrySession(dispatcher())                            <- none
TakeExamView:70       new ExamAttemptSession(dispatcher(), eventBus(), model, ...)  <- none
```

Which closes the loop on the one thing my trace could not explain. Hiding the three entry cards is
a `visible`/`managed` set and is not reliably rejected off-thread, so it succeeds and the screen
goes blank; `content.setCenter(formView)` is a structural change to a node in a showing scene,
which is rejected, so the form is never mounted. Blank, and silent because the throw lands in the
discarded future.

**And it explains why my probe was green.** I drove the identical form with the real seeded
illustration bytes and it rendered fine, which I reported as exonerating the images. It ran inside
`interact(...)`, on the FX thread. Same data, same widgets, different thread, opposite outcome:
that isolates the variable rather than clearing the code, and I should have said so at the time
rather than treating a green probe as a clean bill.

## 11. The lesson
**Every layer green is not the feature green, and the suite cannot tell you which one you have.**

The three E-rows either side of this gap were each accurate. The tests on both sides passed. The
contract was frozen and correct. What nobody wrote down was the sentence that spans them — *a
teacher can start an exam* — and no artifact in the repository was shaped to hold it.

So the check that found this was a person opening the screen, and the check that will keep it found
is a test that starts where that person started. Not a better unit test: a test whose first line is
a screen and whose last line is a navigation. Wherever a feature is assembled from layers owned by
different rows, that test is the only thing standing between "all done" and "unreachable".
