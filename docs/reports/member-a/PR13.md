**`BANK_LIST`, `QUESTION_GET`, `QUESTION_VERSIONS` and `QUESTION_IMAGE_GET`, wired and reachable.**
Read §3 first if you read nothing else: a cold audit found that I had moved the principal's read
scope out of `Authorization` and into a private method of my own service, which is the thing §2 of

## 2. The design worth reviewing: one reachable set

§3 requires the `BANK_LIST` filter and the three single-question guards to agree about what a caller
reaches **by sharing the query rather than restating the rule**, and requires the guard to receive a
*lookup* rather than a computed set, because a guard handed the answer cannot tell whether the caller
computed it correctly.

`Scope` is that shared answer: the union of `findTaughtCourseCodes` and
`findCoordinatedCourseCodes`, computed at most once, and it **is** the `ReachableCourses` the guard
receives.

Two things about it changed during the round and both were improvements forced by evidence.

**It stopped capturing the caller.** The first version kept the opening caller's id and refused
anyone else. That reads as defensive and was in fact unreachable — a scope built inside one call is
only ever handed that call's caller — so JaCoCo showed it as a permanently missed branch. An
uncoverable branch is a claim nothing checks.

**It became a static nested class, which is production API widened for testability.** Naming it as
such per rule 11. Every caller asks it exactly once, so the memoization §3 promises was real code no
test could reach; `asksTheDatabaseOnceHoweverOftenItIsAsked` is what makes "memoizes" a fact rather
than a sentence in a document.

## 3. The audit's finding, which is the important part of this PR

**I expressed the principal's read scope in the wrong place, and the contract names that exact
mistake.**

`ReachableCourses`'s javadoc says "the implementation switches on role: teacher and coordinator get
the union, **principal gets everything**". My `Scope` never read the role. The principal was rescued
instead by a `private static reachesEverything()` inside `BankBrowseService`, short-circuiting
*before* `Authorization.reachesCourse` was ever called. **That guard has never once run on a
principal's behalf.**

§2: *"Both guards live in `Authorization`, not in the service. Between them they are the only place
the table above is expressed. Routing scope through an ad-hoc service check instead is how two
answers to one question get shipped."*

**The failure it was setting up is yours, in E7.** The exam builder needs "may this user read this
course's bank" to populate its question picker. Its author reads that javadoc, writes the obvious
union directory — the same one `Scope` is — calls `reachesCourse` with a principal, and gets
`false`. Rina opens an empty picker. That is §9's *"a starred demo account would have opened an
empty bank at the defense"*, re-armed one seam downstream, and it fails to a blank screen rather
than an error, so nothing shouts.

**Fixed by moving the rule to where §2 says it lives.** `Authorization.reachesEveryCourse(caller)`
is now the single expression: `reachesCourse` consults it before any directory, and the browse
consults it to choose between an unrestricted query and a scoped one. Any future directory inherits
the rule by not being asked about it. `onlyThePrincipalSkipsTheDirectory` exists because otherwise
the new test would pass equally well if the short-circuit were `return true` for everyone.

### Three more, all real

**`useReachableCourses` was write-only, and its javadoc said the guard read it.** `REACHABLE_COURSES`
was assigned and never consulted; `reachesCourse` takes its directory per call. Two tests looked like
they covered the seam and asserted only that a constant lambda returns an empty set, so both would
have passed with the field and the setter deleted. Deleted, with the javadoc corrected to say why
there is no installer.

**The wiring guard's universal was false about the file it scans.**
`everyBankHandlerInTheSourceIsListed` matched `new (Bank\w*Handlers)\(`, which cannot see
`LegacyQuestionHandlers` — a bank handler in that same method whose `Question.answer` is a real key
the leak scan also cannot see (§1). Widened to anything named for the bank or for questions,
singular or plural, which also catches the `BankTopicsHandler` §7.6 has ruled is coming. The legacy
pair is now on the list, so its retirement PR shrinks it and that diff is the proof.

**What the audit cleared, since a clean answer is worth as much:** the `IMAGE_NOT_FOUND` judgement
call holds. All four of that verb's miss routes return one empty `Optional` rendered as one
sentence, so the second message distinguishes verbs and not routes. Filter and guard cannot disagree
for teacher or coordinator. `BankDetails` is behaviour-preserving against `git show HEAD`. The role
lists match §3 and `BankQuestionRow` is structurally keyless.

## 4. One thing for you, and it is a wording problem in a ruling

**Your item-2 ruling said the message should tell her answers must "differ by more than spacing or
punctuation". The code has never folded punctuation.** Measured against the shipped validator on
JDK 21 rather than assumed:

| folds | does not fold |
|---|---|
| `1 2 3` / `123`, `red car` / `redcar` | `cat.` / `cat`, `it's` / `its` |
| `co-op` / `coop`, `e-mail` / `email` | `3+4` / `34`, `A(1)` / `A1` |

At `Collator` PRIMARY strength only whitespace and the hyphen are ignorable. I shipped **"spacing or
hyphens"** instead, because the other wording is false in the direction that costs a teacher work:
she would rewrite an answer semantically when a full stop would in fact have been accepted. §5 and
the javadoc say the same. Say the word if you want the copy to match the ruling instead and I will
change it, but then the sentence is wrong on screen.

## 5. Also fixed on the way past

**`QuestionDetail` had one mapper and was about to have two.** `QUESTION_GET` answers with the same
type as `QUESTION_CREATE` and `QUESTION_UPDATE`, so a second mapper would be two expressions of one
rule with nothing checking them — §5's recurring hazard, surfacing as a teacher seeing a different
author name depending on whether she had just saved the question or merely opened it. Extracted to
`BankDetails`, which both services hold. It is a small refactor inside a file you reviewed
yesterday, so it is flagged rather than quiet; it also left `wireDifficulty` with no callers, and I
deleted it rather than leave a dead private method.

**`strip()` does not close the gap its javadoc implied.** Found by planting a Unicode space expecting
it to be stripped and watching the test fail: `String.strip()` removes what
`Character.isWhitespace()` accepts, and the non-breaking spaces U+00A0, U+2007 and U+202F are exactly
the ones it rejects. `Authorization.reachesCourse`'s javadoc said `trim()` "would leave that gap
open", implying `strip()` closes it; it closes the breaking half. **What survives fails closed** —
the padded code equals no member of the reachable set, so the caller is refused and the filter
matches nothing, which is the opposite of the dangerous direction. Documented in both javadocs and
pinned by two tests, one per class of space. Not widened: what a course code may contain is your
call, not a read PR's.
