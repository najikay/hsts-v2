## 2. Why this test did not exist, which is the point

**No test in `server.features.bank` touched a database.** All five server-side bank test classes
declare `@Mock private Session session`. Grepping `src/test/java/server/features` for
`RepositoryTestBase` returns approval, exam, grading, notify, release, reports and results — **not
bank.** So the repositories were proven on two engines, the services and handlers against mocks, and
the seam between them nowhere.

That matters more for the bank than anywhere else, because `QuestionValidator` makes a claim *about
the database*: "never accept a pair the database will reject". Nothing in the build ever asked the
database whether that was true. It was not.

**MySQL only, no H2 leaf.** `TestDatabases`' own javadoc says the H2 schema is generated from the
entities and reproduces no foreign keys, no CHECK constraints and not the collation. Every headline
assertion here needs one of those three, so an H2 leaf would pass for reasons unrelated to what the
class claims.

## 3. The defect, measured on both sides

`ck_question_versions_distinct` is `a1 <> a2 …` on a table declared `utf8mb4_unicode_ci`, so the
comparison runs under that collation.

| pair | `sameAnswer` (jshell over the real folding) | MySQL |
|---|---|---|
| `מים` / `מימ` (final mem) | different | **same** |
| `כן` / `כנ`, `רף` / `רפ`, `ארץ` / `ארצ`, `דרך` / `דרכ` | different | **same** |
| `שלום` / `שָׁלוֹם` (niqqud) | same | same — already agreed |

Java's `Collator` at PRIMARY treats the five Hebrew final forms as distinct letters; the collation
gives them the same primary weight. **The validator was looser than the constraint**, so the INSERT
threw `SQLIntegrityConstraintViolationException` out of `QuestionService.create` and reached the
teacher as a generic internal error — the exact outcome the validator exists to prevent, on T-2.1,
in Hebrew.

Reproduced independently in a throwaway schema carrying the same constraint: **`ERROR 3819`**.

**The test was red on the commit that introduced it** — five errors, every one
`Check constraint 'ck_question_versions_distinct' is violated` — and green on the fix.

## 4. What the audit found that the fix did not close

A post-implementation audit found the same defect twice more. Both verified by me before acting.

**4.1 Every character above the BMP has one weight.** `utf8mb4_unicode_ci` is a UCA 4.0.0 table:
`U+1F600` and `U+1F601` are one string to the constraint, and so are an emoji and a mathematical
bold letter. Two different emoji in two answer boxes reproduced `ERROR 3819` against a real schema.
**This is worse than the original** — emoji reach a `TextField` by paste, and a school question bank
is a plausible place for them.

Measured before choosing the fix: they are **equal-weight, not ignorable** (one emoji ≠ the empty
string, `a` ≠ `a` + emoji, one emoji ≠ two). So the fold substitutes one sentinel per code point and
**preserves count**, iterating by code point rather than by `char` so a surrogate pair does not
become two sentinels.

**4.2 Three Yiddish digraphs**, `U+05F0`–`U+05F2`, which the collation *expands* and NFKD does not
decompose, so nothing in the fold reached them. Folded by expansion.

**4.3 The agreement test stopped testing agreement once it went green.** Every row was a pair the
fixed validator refuses, so the branch that actually asks the database never executed again. It now
asks the database **directly, with the validator bypassed**, and asserts the two verdicts are equal
**in both directions**. Rows the validator calls *different* are in the table for exactly this
reason.

That restructure paid immediately: the sentinel-to-deletion plant fails with *"validator says same,
database says different"* — the **stricter** direction, which the old one-directional assertion
could not have caught.

## 5. The two behaviour changes, stated rather than discovered

**5.1 Hebrew final forms are now one answer.** A teacher writing `מים` and `מימ` as two options is
refused with "two answers are the same". Correct: the database already refuses to store them, so
the alternative is the internal error she gets today. It is a real change in what the add-question
form accepts, in the language the system is demoed in, which is why it is here rather than in a
footnote. **Reversal: one line in `foldedForm`** — and the round-trip test then fails, which is the
point.

**5.2 Two different emoji are now one answer.** Same argument, wider blast radius, same reversal
cost. The over-strictness this buys is that an answer containing a literal `U+FFFD` folds like one
containing an emoji; that is the safe direction the class javadoc already accepts.

## 6. P-9, and the correction that matters

P-9 was written in part 1 and **read as though the class was closed.** It is amended here to say
plainly that the Hebrew fold did not close it, and that **hand-enumerating the dimensions was the
wrong method** — it produced a false all-clear the first time.

Two things recorded because they generalise past this defect:

- Rows the validator calls *different* have to be in the table, or the branch that asks the database
  stops executing the moment the fix lands.
- The probe's `catch` has to name the constraint it expects. A bare `catch (RuntimeException)`
  reported a malformed query as a collation result and sent me looking at the wrong thing for a run.

**Still open, and stated rather than implied:** nothing asserts the columns are still
`utf8mb4_unicode_ci`. This whole fold is correct for that collation and wrong for
`utf8mb4_0900_ai_ci`. That deserves a one-row `information_schema` assertion in the MySQL leaf, and
it is not in this PR.

## 8. What the 25 assertions cover

Each is a **re-read in a new transaction**, never the write's own return value — `QuestionService`
answers a detail assembled in memory, so asserting on it proves nothing about the INSERT. The
question always arrives through `QUESTION_CREATE`; only the delete-blocking rows are seeded
directly.

- **The validator/database agreement**, both directions, 15 cases
- **The answer key still points at the text she marked** after `int → byte → TINYINT → byte → int`
  and the positional rebuild in `BankDetails` — asserted as text, not as `isEqualTo(3)`
- **The soft delete observed from outside its transaction**, and the serial not reused afterwards
- **Image bytes byte-for-byte across a `KEEP` edit**, then `REMOVE` on v3 leaving v1 and v2 serving
- **The three independent expressions of `latestVersionNo`** agreeing
- **Hebrew in all six bearing fields** through `QuestionDetail`, `QuestionVersionDetail` and
  `BankQuestionRow` — every existing bank fixture's answers are ASCII
- **Browse by each filter, asserted by identity**, with two near-miss negatives
- **A refused create leaves zero rows**, counted before and after
