## 2. What it does

Three files. `ExamBuildMessages` (every sentence, each interpolating its constant rather than
spelling the number), `ExamValidator` (every rule in §5.1 to §5.3, session-free), `ExamService`
(create, get, save, revise, submit; one transaction each).

**`ExamValidator.pointsProblem` is public for E7.12's live indicator**, which is the cross-tier
call you accepted twice for `QuestionValidator`. The other three entry points are server-side.

**The composition rules take `List<PinCandidate>` as a parameter rather than a session.** Four of
§5.2's rules need what only the database knows - does this version exist, which question owns it,
which course, is it deleted - and one `findPinCandidates` call answers all four, with a row absent
from the result being the fifth. The service fetches; the validator stays a pure function. That is
what lets the soft-delete rule, the one with no schema backstop anywhere, be planted and watched
to fail in milliseconds.

## 3. The audit, which found that the write path did not work

Run after the code existed, against the code. **Six confirmed, two of which changed code rather
than prose.** The headline is P-8 and I have opened it in `PROBLEMS.md`.

**3.1 Every create and every save wrote `question_id = 0` and would have died on the foreign
key.** ⚑

`exam_version_questions` carries a composite FK onto `question_versions (id, question_id)` plus a
unique key on `(exam_version_id, question_id)`. A zero matched no parent row, and had it inserted,
a second question would have collided at `(versionId, 0)`. **T-3.1, the first acceptance case in
the epic**, arriving as `INTERNAL` and a stack trace.

My comment above the line said `questionId` was "the store's to resolve". `replaceComposition`
persists it verbatim. That is the third time I have shipped a comment asserting a safety property
that is not there, and the third time a cold read rather than a test has caught it.

**Why nothing failed:** `ExamBuildRepositoryContract` proves the store on two engines with real
resolved ids; `ExamServiceTest` proves the service with the store mocked and asserted the call with
`any()`. Two green suites either side of one seam, neither crossing it. `revise` was already
correct, so one of three writers was right and nothing compared them.

**3.2 `EXAM_SUBMIT` notified nobody, on the happy path, every time.** ⚑

`JpaApprovalStore.inTx` goes through `Transactions.inTx(factory, ...)`, which opens a **fresh
session**. So the hook ran on another connection, could not see the uncommitted status flip, took
its own `if (!version.isPending())` guard, read the row as still `DRAFT`, and returned
`Superseded.none()` **before either notification**. The coordinator's queue is never told. F4.1
dead, E8.2's contract dead, and the only trace is a WARN line.

E7 is the hook's first production caller - every existing call is a test invoking it standalone,
already committed - which is why nothing had exercised it.

**My javadoc described a milder and different hazard**, that "its notifications are not rolled
back". There were no notifications to roll back. Worse, I wrote that calling it last made the
window "as small as this method can make it", which is backwards: later means more certainly
uncommitted. See section 6.

**3.3 `create` compared questions against the wire's course code, not the stored one.** The
validator's own `@param` says "from the stored exam rather than the wire", and `save` obeys it
while `create` did not. That matters because the *other* course check on the same path runs in SQL:
`requireTeachesCourse` compares under `utf8mb4_unicode_ci`, which is case-insensitive. A client
sending `ma` for a stored `MA` passed the scope guard and was then told **every question in her own
course belongs to a different course**. Now `equalsIgnoreCase`, with the residual difference stated
(the collation also folds accents; this does not, and that fails closed).

**3.4 `revise` carried soft-deleted questions onto a new version.** `ARCHITECTURE.md` §5 assigns
that rule to this validator **by name** - "adding a soft-deleted question to a new exam version is
a service-rule rejection (E7 validator)" - and a revision is a new exam version. Copying the
composition forward walked past it, and nothing underneath refuses: soft delete is an `UPDATE`, so
no foreign key fires. A teacher revising an approved exam weeks after a question was retired would
have put it back on the paper. **The other four rules survive the copy** - points, course and
duplicates are preserved by construction, hard deletion is blocked by `ON DELETE RESTRICT` - which
is exactly what made this one easy to miss.

**3.5 and 3.6, both mine and both prose.** A javadoc block for `stateOf` sat above `rejectionOf`,
so Java attached it to the wrong method and a reader was told a null-bridge was an exhaustive enum
switch. And the plant family was incomplete again, in the same shape as last time: see section 4.

## 5. The contract question that came out of writing the code ⚑

**§7's `available` can produce a sentence a teacher can disprove, which is the failure §7.2
property 2 calls the worst one available here.**

§7.3 defines `available` as the true count in her bank, "the number she would see by filtering the
bank screen to the same topic and difficulty". It says nothing about questions already consumed by
an earlier quota, and for the demo case that is exactly right: `("Recursion", HARD, 1, 0)` renders
"requested 1 Hard, bank has 0".

Now: her bank has 10 Java questions, 3 of them Recursion. She asks for **3 Recursion** and **8
course-wide**. Eleven from ten, so it genuinely cannot be done. Most-constrained-first fills
Recursion, leaving 7 for a quota that wants 8, and the shortfall is `(null, null, 8, 10)`:

> **Requested 8 questions, bank has 10.**

Both numbers are true and the pairing is incoherent. `available` answers "how many match this
filter" while she reads it as "how many were left for this quota". **It is reachable on stage** -
the thin-topic seed is precisely the setup that makes a teacher combine a narrow quota with a
course-wide one.

Three shapes, and it is yours because the client composes the sentence: keep the count and change
the wording; keep the wording and report the count still available to that quota; or carry both
fields. **This is the reason the freeze waited** - the auto-compose shapes were the ones no code
had exercised, and your note said to say so now.

## 6. Deviations, and what was volunteered

**6.1 The one deviation: `submitForApproval` does not call the hook.** §5.5 says
`ExamService.submitForApproval` calls `ApprovalService.versionSubmitted`. It does not, because from
inside the caller's transaction that call notifies nobody (3.2). The transition stays E7's and the
hook becomes the handler's, after commit - one of the two fixes §5.5's own text allows. **The
alternative is the hook joining the caller's session, which is inside E8 and yours.** Either way E7
owns the transition and E8 owns everything the queue sees; only the moment moves. Reversal is one
line in tomorrow's handler.

**6.2 `revise` refuses a retired question rather than dropping it.** Dropping would leave the
points short of 100 and hand her a sum she did not cause on a screen she has not edited. Refusing
names the question. If you prefer the drop it is one method and one sentence.
