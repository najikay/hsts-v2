# E6: the one line, and a test that notices when it is gone

**Wires `BankHandlers` into `HSTSServer.defaultRouter`, closing the gap #25 shipped with.** One
production line, its imports, a guard test that fails when the line is removed, and two TODO boxes
that are now true.

## 1. Why this is its own PR

#25 merged at 06:59Z with the gap open, before the wiring line could go into it. So the line needs a
commit of its own, and it should not wait for the read PR: `main` currently holds a question bank
that no running server can reach. That was honest while #25 was open and §1 said so in the body. On
`main` it is just a gap, and every hour it sits there is an hour where "the bank is done" is a
sentence somebody could say and be wrong about.

Kept separate from the E6 read PR deliberately, for three reasons. It is reviewable in under a
minute against a rule that is one sentence long. It makes E6.1 and E6.4 tickable today rather than
at the end of the read work. And it means the read PR branches off a `main` that already has the
wiring, so two branches never edit `defaultRouter` in the same window — the read PR then adds its
own line to a method that already has a bank block, which is a clean append rather than a merge.

## 2. Where the line went

After `registerApprovalFeature(...)`, immediately before `return router;`.

**Your ruling had two readings and I picked one. Tell me if it was the wrong one.** The message says
both "one line **beside the legacy registration** per PR" and "insert **after the existing
features** and touch nothing else". Those name different places. I took the second.

My first draft of this paragraph justified that by claiming the other placement "would insert it
between existing features, which is the edit the ordering rule protects against". That reasoning is
wrong and the audit said so: putting a line between two existing lines reorders neither of them, and
the diff is +N/−0 either way. The honest position is that I preferred assembled-last on the merits
and there was no ordering argument forcing it. It is one line to move, now; two after the read PR
appends its own line to the same block. If you meant beside the legacy pair, say so and it moves in
the read PR.

On the merits: assembled last is right because the bank uses only the `sessionFactory` and `clock`
locals, and its guards ask the open transaction's own data through a repository lambda rather than
the process-wide `COURSE_TEACHERS` seam, so it holds no snapshot that an ordering change could make
stale.

**One deviation from PR11 §1's sketch, in our favour.** That sketch passed `Clock.systemUTC()`. The
method already has a `Clock clock` local, built for `AuthService`, and the line now uses it. One
clock per process instead of two instances that agree by coincidence, and it matches how every other
feature in the method takes its clock.

Nothing else in the file changed: `git diff --stat` on it is **24 insertions, 0 deletions** (one
statement, three imports, and a comment that grew after the audit). No existing line moved, no
ordering comment touched.

## 3. The part worth reviewing: a guard test, its first version, and why that version was thrown away

The line itself is trivial. The *reason it was missing* is not, and my first attempt at guarding it
was a decoration test that the cold audit caught. Both halves are below, because the second is only
credible if you can see the first.

**The defect class.** #25 was green with the wiring absent and no test could have told us.
`BankHandlersTest.registersTheThreeWriteVerbs` calls `registerOn` against a real `MessageRouter` and
asserts all three verbs land. It passed while the production server never constructed the class:
from inside its own unit test, a handler nobody instantiates is indistinguishable from one that is
wired. That blind spot is not the bank's — **every feature in `defaultRouter` has it**.

### 3.1 The version I wrote, and how it failed

It scanned the compiled constant pool of `HSTSServer.class` for `BankHandlers`, `QuestionService`
and `QuestionIdAllocator`. I planted a defect against it — deleted the whole statement and its three
imports — watched it go red, restored, watched it go green, and wrote that up as evidence.

**One mutation out of a family, and I picked the one that worked.** All three of those names reach
the constant pool from the `new` expressions. So this:

```java
new BankHandlers(sessionFactory, new QuestionService(...));   // never registered
```

passes every assertion while the bank is exactly as unreachable as it was in #25. Seven tokens
removed. **I planted it and confirmed: BUILD SUCCESS, guard green, bank dead.** A second mutation
does it too — extracting the block into a `registerBankFeature` helper and not calling it, which is
the shape the four neighbouring features already use, so a janitor normalising this block re-opens
the hole silently.

Bytecode cannot answer this cheaply, which is the part I should have checked before choosing it. The
only pool entry encoding registration is a `Methodref` to `BankHandlers.registerOn`, and a
`Methodref` is a pair of indices, not text. I confirmed with `javap -v`: `registerOn` occurs as
**exactly one** `Utf8` entry, shared through one `NameAndType` by all eight registering features.
There is no byte sequence a crude scan can look for that means "the bank registers" rather than
"somebody registers".

Two further findings on that version, both P-6 shaped and both real. Its `@DisplayName` and failure
message said it checked registration in `defaultRouter`; it checked neither — any method, any field
initialiser would satisfy it — while the javadoc twenty lines above correctly said it did not prove
`registerOn` was reached. The file contradicted itself, and the sentence a reader sees when it goes
red was the wider one. And its "teeth test" could not fail from any defect in the code under test:
the scenario it named (a path typo) makes `Files.readAllBytes` throw, so the control was defending
against something structurally impossible.

### 3.2 What replaced it

It reads `HSTSServer.java` itself, extracts the body of `defaultRouter`, strips comments, and
asserts that a `BankHandlers` is constructed **and** `registerOn(router)` called on it **within one
statement** — the same-statement check matters because every other feature in the method also calls
`registerOn(router)`, so two independent searches would pass on a stray construction.

Planted in the real file, compiled, run:

| Mutation | Result |
|---|---|
| Statement deleted outright (#25 as it merged) | **3 of 3 tests fail** |
| Constructed, never registered (`.registerOn(router)` → `.toString()`) | **3 of 3 tests fail** |
| Commented out, imports removed — compiles clean | **1 of 3 tests fails** |
| Extracted to an uncalled helper | rejected by the mutation harness |

The second row is the one that matters: it is what the old version let through.

The mutations also run in-process, applied to the real source text, so the check is exercised
against all four on every build rather than only when somebody remembers to plant one. A third test
asserts each mutation actually changes the source — without it, a mutation whose pattern went stale
would quietly become a no-op and the harness would be asserting against unmutated text.

## 4. What this does not prove, said plainly

It proves the registration is **written in the method**. It does not run it. `defaultRouter` calls
`HibernateUtil.sessionFactory()`, which boots a HikariCP pool against the real `hsts_db` on first
call — the ordering rule in that method's own javadoc, and the reason every existing test of
`HSTSServer` uses the bring-your-own-router constructor, which is also exactly why none of them
exercises the production wiring. Nothing automated here can show a teacher can add a question; the
manual pass covers that.

It is also deliberately literal: extracting the block into a helper fails this test **even if the
helper is called**. That is the safe direction and it is intended. The failure is loud and is fixed
by pointing the test at the helper, which is better than a check that permits the one refactor that
hides an uncalled method.

**One thing for you that this PR does not cause.** `MessageRouter.register` throws
`IllegalStateException` on a duplicate verb rather than overwriting — the right choice — but it
throws inside `defaultRouter`, inside the `HSTSServer(port)` constructor, which no test calls and
which JaCoCo excludes. So a verb collision is not a red build; it is a server that will not boot,
found by a human. Verified the current verbs are disjoint (`GET_ALL_QUESTIONS` / `UPDATE_QUESTION`
against `QUESTION_CREATE` / `QUESTION_UPDATE` / `QUESTION_DELETE`), and noted it in the comment,
because the E6 read PR adds the second bank line to this method and that is the realistic trigger.
