## 3. The tasks

### 3.1 E7.11 — one screen, three modes, derived and never assigned

`Mode` is a pure function of two facts: was the screen opened with a version id, and what state did
that version come back in. `CREATE` sends `EXAM_CREATE`; a `DRAFT` sends `EXAM_VERSION_SAVE`;
**anything else renders read-only**, which is §8's read path, ruled 2026-08-25.

Read-only is the rule rather than a list of three states, so a fourth state added later is
read-only by construction. And the pre-answer case fails closed: an opened version with no state
yet is read-only, so nothing is editable in the gap.

### 3.2 E7.12 — the paper, and the live Σ that is the server's own rule

Reorder, repoint and remove are live. `pointsProblem()` calls
`ExamValidator.pointsProblem` — the same method `ExamService` refuses a save with, which E7.3 made
public for exactly this. **There is no arithmetic in the client**, so the indicator that turns green
and the rule that lets the save through cannot drift, and the sentence she reads is the server's.

`ord` is written in one place, on the way out, as the list index. The `Line` record deliberately
does not carry one: an ordinal inside a row beside a list that also has an order is two expressions
of one fact.

### 3.3 The one-draft rule (§5.4 as you amended it)

`ExamService.revise` refuses when the exam already has an open draft, answering `CONFLICT` naming
it. The check sits **after** the addressed-version check and **before** the lock consult, and there
is a test pinning that order: both refusals can be true at once, and the draft sentence tells her
where to go while the lock sentence tells her to wait for a colleague editing a version this revise
was never going to touch.

`findOpenDraftVersionNo` uses `max` rather than a query with an order: the rule makes one draft the
maximum from here on, but data written before it can hold two, and a caller picking one should not
depend on row order. Four two-engine tests, three mutations caught.

**The client predicts it too.** `ExamListSession.canRevise(exam, version)` is false for every
version of an exam that has a draft, so the button is absent rather than present and refused. That
broke seven existing tests, correctly: the midterm fixture has a draft at v3, so nothing on it is
revisable any more. Rather than weaken the fixture I added an exam with no draft, so the suite can
tell the amended rule apart from a screen that renders no Revise button at all.

### 3.4 Edit and View, and what they deliberately do not carry

Both buttons send **only the version id**. Which of the two opening means is the builder's to decide
from the state `EXAM_VERSION_GET` answers with. The list holds an `ExamVersionRow` a push could have
made stale; the builder has the fresh answer. That is what stops a stale row opening an approved
exam in an editable form.

## 4. The audit, and what it found in my own work

Nine findings, six confirmed defects. **All six were mine and all six are fixed.** Two were
serious.

### 4.1 Opening B while A was loading edited A under B's identity ⚑

`open()` committed the new id and then returned early because a load was running, dropping the
request. A's answer landed, was adopted, and the form showed A's paper — editable if A was a draft,
with Save writing to A using A's token, while she believed she was editing B. No error anywhere.

`openNew` had the same hole and a worse outcome: a stale answer landed on the new-exam form with a
full composition already summing to 100, one click from writing a duplicate of an existing exam
under a fresh display id.

**What makes this a bad miss rather than an unlucky one:** `ExamListSession`, in the same package,
has carried a generation counter since the day it was written, for precisely this. I did not carry
the pattern across. Both entry points now bump one generation and clear every loaded field; four
tests and three mutations.

### 4.2 A two-digit points value could not be typed ⚑

The paper was cleared and rebuilt on every `onChange`, and `session.points(...)` fires one, so each
keystroke destroyed the `TextField` being typed into. The focus owner goes with the removed node and
the second digit never arrives. **This is the control T-3.2 is demonstrated on.**

The same file already defended the metadata against the milder form of this (a caret jumping to the
end) and said so in a comment; the paper got the stronger version of the bug and no treatment. It
now rebuilds only when the paper's *shape* changes — which questions, in what order — and points are
deliberately not part of the shape. The FX test types two characters, and the mutation that restores
the old behaviour is caught.

### 4.3 Four smaller ones, all confirmed and fixed

- The read-only banner said "sent for approval" **before any answer landed**, on every open of a
  draft, and permanently on a failed load beside "could not be opened", which says the opposite.
  Failing closed is right for a guard; a sentence stating a fact should not inherit that caution.
- `LOAD_FAILED`'s javadoc promised it was shown "above a retry". There was none. There is now, and
  it doubles as the exit from a stale-token `CONFLICT`, which was otherwise terminal: the token is
  dead, so pressing Save again re-sent it forever while the server's own message said "open it
  again" and nothing did.
- `openNew` left `examVersionId`, `lockVersion`, `displayId6`, `courseName` and `saved` behind, so
  a "New exam" heading carried the previous exam's 6-digit id and course.
- The missing-picker apology rendered on read-only versions, which already say nothing can be
  changed.

### 4.4 A comment this PR made stale

`ExamListSession` said the server had no guard against a double revise. True when I wrote it in
PR22; false three hours later when §5.4's amendment landed in this PR. Rewritten to say why holding
the flag still matters — the database is now safe and the screen is not, which is a different and
smaller reason.

### 4.5 What the audit confirmed sound

The mode rule as a function, the lock token on the happy path, the one-draft rule's placement and
its HQL, the shared points validator, `ord` handling, **READ_ONLY closing every one of the nine
state-changing methods**, the client's prediction matching the server's two conditions, and PRD
§4.1 across every string.
