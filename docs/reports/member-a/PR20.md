## 1. What a teacher gets

She opens the bank, and the row itself says **"Editing · Ron Levi"** before she clicks. Today she
clicks Edit, waits for the editor, and only then meets the read-only banner — the click and the
screen transition are both wasted, and on a shared course that is the common case rather than the
edge one. The column is live: it appears and disappears as colleagues open and close questions,
with no refresh, which NFR-18 requires and which is what the two E18.8 verbs exist to make possible.

A question she has open herself reads **"Editing · you"**, not her own name. Her name against a row
is the shape that means *somebody else has this*, so printing it would read as being blocked from
her own editor.

Words, not a colour or an icon, on the ruling already settled for E6.12's change summary: it
survives a screenshot, a printout and a screen reader, and it is read exactly when she is deciding
whether to click.

## 3. The defect the suite could not reach ⚑

**`BankRowLocks` asked for the state before registering for the news.** Snapshot first, watches
second — which reads as the natural order, paint then subscribe.

The server resolves push recipients by reading its watcher set **at the instant the lock changes**
(`EditLockService.publish` returns early on an empty set, and `watch` registers only when the
server handles that message). So the window is real: the server answers "11005 is free", a
colleague acquires before this client's `LOCK_WATCH` is handled, `publish` finds a set this client
is not in and writes no push at all. The snapshot already said free. **The row shows the question
as free for the entire duration of his edit session** — the one case the column exists to prevent.

**Why nothing caught it.** It needs a second actor acquiring inside a window measured in the
server's own message-handling order. No test driving one client can reach it, the suite was green,
coverage was complete, and seven planted mutations passed. It was found by an adversarial read that
started from the server's recipient resolution rather than from my code — the direction I had not
looked.

**It falsified two durable claims**, which is the part worth carrying past this epic. Mine: *"one
snapshot plus the pushes is the whole picture."* And `Verb.LOCKS_SNAPSHOT`'s: *"one snapshot at load
plus the pushes afterwards is the complete picture."* Both are true only if the watch is registered
first, and neither says so.

**Fix:** two lines swapped, with the reasoning at the call site. The reversed order has no matching
hazard — both messages travel one ordered socket and cross to FX through the same poster queue, so
an acquire in the window now publishes a push written *before* the snapshot answer, and the
snapshot, newer and already containing the acquire, lands last and wins. Pinned by
`watchesBeforeAskingWhoHolds`; planted, and it fails when the order is put back.

**P-11** records the generalisation: *whenever a subscription and a state read are both needed,
subscribe first and read second, so the overlap duplicates rather than drops.* A duplicate is
idempotent here and wherever this shape recurs; a gap is silent.

## 4. The other three the audit found, all mine, all fixed

**4.1 A repaint that nothing pinned.** Every test in the file runs the FX hop inline, so the chips
were already in place when the page drew. In production the hop is `Platform.runLater`: the page
draws first with no holders, and one `onChange.run()` in `settleSnapshot` is the **only** thing that
paints the column on first load. Deleting it left every test green. Now pinned by
`theSnapshotRepaintsOnItsOwn`, which delivers the snapshot by hand *after* the page has rendered —
the production ordering the direct poster otherwise hides.

**4.2 A javadoc claim my own file disproved 140 lines further down.** I documented that a malformed
display id throws deliberately, "and it should be loud". The same file records, from measurement,
that throws on this path are captured into an unobserved future. Traced: the throw stops
`settleList` before its own render, leaving the teacher on a permanent spinner with no error and
nothing to retry — one bad id out of forty takes the whole browse screen down. Now logged and
skipped, the rest of the page unaffected, pinned by `aMalformedIdDoesNotTakeThePageDown`.

**4.3 A test that could not fail for the thing it was named after.** `stopUnsubscribes` asserted
"stop, push, nothing arrived" — but `stop()` also empties the rows and the push handler bails on an
unknown reference anyway, so deleting the `unregister` left it green. The real consequence is the
*second* visit to the screen, where greenrobot throws `Subscriber already registered`. Rewritten to
leave and re-enter; planted, and it now fails with exactly that exception.

**Plus one suspected issue closed cheaply.** After a reconnect that does not go through logout, the
client's cache of "rows already watched" disagrees with the server, which drops registrations
silently on disconnect — the column would paint once and never update again. `stop()` now clears
it. Re-watching is idempotent and raises no push, so the cost is one message per row per visit.

## 5. Three things that are yours, each verified before being raised

**5.1 `Verb.LOCK_WATCH` instructs callers to drop a live lock. ⚑ E7 reads this next.**
`Verb.java:271-273` says *"to stop watching, send `LOCK_RELEASE` for the same entity: it drops the
registration and, since the watcher holds nothing, changes no lock."* The premise is not a property
of anything. `release` (`EditLockService:241-259`) keys on `userId` alone and drops the hold **and**
the watch in one call. One user being both watcher and holder of the same `EntityRef` is exactly
the state E6.14 creates, because the list and the editor key identically through `QuestionLockKey`.

`BankRowLocks` refuses to follow it, documents why, and `neverReleasesAnything` walks every path on
the screen and fails if the verb ever appears. **But the contract was not corrected**, so the next
list screen reads the instruction and not my workaround. *Cost now:* three lines of javadoc, plus a
decision on whether E18 wants a watcher-only unwatch. *Cost later:* an intermittent lost lock on
E7's exam list, during a demo.

**5.2 `Verb.java:239-241` says no lock payload carries a user id.** `LockHolder(long userId, String
displayName)` is the payload of every `LockResponse` and every `LocksSnapshot` entry, and this PR's
`isSelf` depends on that id. The true statement is `EditLockService`'s rule 1: *requests* carry no
identity. *Cost:* one word. It is the kind of sentence a reviewer quotes to wave through a payload
that should not carry an id.

**5.3 `LOCKS_SNAPSHOT` is role-gated but not course-scoped.** `handleSnapshot` applies
`requireRole(TEACHER, COORDINATOR)` and nothing else; `snapshot()` walks the raw ids. So the "not an
existence oracle" claim holds in one direction only: absent is safely ambiguous, but a **present**
entry proves a question exists, is being edited, and names who — for a course the caller cannot
read, while every bank read verb answers `NOT_FOUND` out of scope "indistinguishable on purpose".
No correctness is reachable and students are gated out, so this is not a P-5 repeat. Either narrow
the sentence or scope the query.

**And one tension I am flagging on myself:** `handleSnapshot` refuses an oversized request rather
than truncating, and your javadoc argues truncation is "a wrong answer dressed as a right one". My
client-side cap truncates, because the alternative is a refusal that blanks the column on every
row. It is unreachable under the current page size and logs an ERROR naming both numbers, but it
does sit against your stated reasoning. Your call.
