# HSTS v2 — Problems Log

Running log of design/coding problems we hit and how we solved them. The assignment's submission doc requires one written up ("תארו בעיית תכן או קידוד שנתקלתם בה... וכיצד פתרתם אותה") — keep this honest and specific so the best story writes itself at E22.2.

Format per entry:

```
## P-<n> — <short title>            (date, who)
**Problem.** What went wrong / what was hard, with the symptom.
**Investigation.** What we tried, what we learned.
**Solution.** What we did, and why that over alternatives.
**Evidence.** Test/commit/PR that proves it.
```

## P-1 — Non-ASCII (Hebrew) Windows username breaks the forked test JVM    (2026-08-19, Naji + lead)
**Problem.** `mvnw clean verify` on Windows died before running a single test: `FileNotFoundException: C:\Users\????\...\jacoco.exec` and "The forked VM terminated without properly saying goodbye".
**Investigation.** The username נאגי appears in the repo path. Surefire launches the test JVM via `cmd.exe`, and the JaCoCo `-javaagent` options string gets decoded with the Windows ANSI code page — the Hebrew characters become `????`, so the agent cannot create its output file and the fork crashes at startup. WSL builds and Linux CI were unaffected (UTF-8 paths native there), which is why it only surfaced on the first full Windows test run.
**Solution.** Team rule: clones live on an ASCII-only path (`C:\dev\hsts-v2`). Moving the folder fixes it completely; no build config change needed (and no fragile encoding flags to maintain).
**Evidence.** Failing run 2026-08-19 13:25 (jvmRun1 dumpstream); green `clean verify` after the move.

## P-2 — Invisible toast layer swallowed every mouse click and scroll    (2026-08-19, found by Naji's manual gallery test)
**Problem.** In the E4 gallery (and, via the shared AppShell plumbing, the whole future app) no mouse interaction worked — clicks dead, wheel scroll dead, only keyboard navigation alive. The user could only ever see the top of the gallery.
**Investigation.** A TestFX probe reproduced it headless; a scene-level event filter showed every MOUSE_PRESSED landing on the full-scene `ToastStack` overlay. The code correctly called `setPickOnBounds(false)`, but the stylesheet gave the layer `-fx-background-color: transparent` — and in JavaFX picking, a Region with **any** background fill (transparent included) is pickable geometry; only a *null* background is truly click-through. 729 unit tests and rendered screenshots could not see it: the bug exists only in real input dispatch.
**Solution.** Removed the background declaration from `.hsts-toast-stack` (with an explanatory comment) and added `GalleryInteractionTest` — a permanent TestFX regression test that robot-clicks a palette swatch (asserting the accent stylesheet actually changes) and delivers a wheel event through the scene graph (asserting the viewport moves). Policy takeaway adopted: UI smoke tests must include at least one *real input* assertion, not only "nodes exist" checks.
**Evidence.** Failing probe run → target-chain log naming ToastStack → green `GalleryInteractionTest` + full `verify` after the one-line CSS fix.

**Recurrence (2026-08-20, E17):** the same trap was reintroduced by `.hsts-popover-layer` carrying `-fx-background-color: transparent` and was caught by the failing TestFX interaction test rather than by review, which is exactly the guard working. Standing rule: overlay layers in the shell set no background property at all.

## P-3 — The login throttle was a password oracle (spec-level bug, caught in security review)    (2026-08-19, lead review of E5)
**Problem.** The E5 brief specified: while an account is locked out, a wrong password answers "Incorrect username or password" but a correct password answers "Too many attempts". The implementation followed the spec faithfully — and the spec was wrong: the message difference lets an attacker keep guessing during the lockout and learn exactly which guess was correct. The throttle confirmed the very password it existed to protect.
**Investigation.** Found in the line-by-line review of AuthService before commit (the implementation itself was excellent — constant-time BCrypt, dummy-hash against user-enumeration timing, generic errors; the flaw was inherited from the written spec). A second review finding: failure records are kept per submitted username — the uniformity that prevents user enumeration — which made the throttle map unboundedly growable by spraying random names.
**Solution.** While locked, every attempt is refused with the same throttle message BEFORE any lookup or verification (no oracle, no free BCrypt work, still truthful for the real owner). The throttle map self-purges stale entries past a 10,000-entry threshold, keeping live locks. Both behaviors pinned by tests, including "unknown usernames throttle identically" and the spray-bounded test.
**Evidence.** AuthServiceTest throttle nest (8 tests) + LoginIntegrationTest, all green; the lesson recorded: specs get security-reviewed like code, because implementations faithfully reproduce spec bugs.

## P-4 — Two invisible build-environment traps: stale IDE terminal env, poisoned MAVEN_OPTS    (2026-08-19, found by Member B)
**Symptom.** `mvnw clean verify` fails on a machine that has a perfectly good Temurin 21 install, with errors that point nowhere near the real cause.
**Investigation.** Two independent causes, neither guessable from the error text: (1) IntelliJ's built-in terminal inherits the environment from when the IDE process started, so JAVA_HOME/PATH changes made after launch are silently absent in every "new" terminal tab; (2) a user-level MAVEN_OPTS carrying JDK 24+ only JVM flags stops a JDK 21 JVM from booting at all, before Maven prints anything useful.
**Solution.** Team rules: after changing JAVA_HOME/PATH, restart the IDE (a new tab is not a new environment); check MAVEN_OPTS (`$env:MAVEN_OPTS` in PowerShell) when a build dies before Maven prints, and clear flags targeting a newer JDK. Recorded because both will bite again on any fresh machine, including the defense laptops.
**Evidence.** Member B's local `mvnw clean verify` green on Temurin 21 after both fixes.
**Addendum (2026-08-20, found by Naji):** a third trap in the same family — jar copies living outside `target/` (repo root, Desktop, USB stick for the demo). A manual test against a stale copy reports bugs that are already fixed, and "I don't see the change" burns real debugging time on code that is correct. Team rule: manual tests run ONLY against `target/` jars from a build you just ran, and any jar copied elsewhere gets the build date in its folder name. At the defense, the jars in the submission zip are rebuilt LAST, after the final commit.

## P-5 — Legacy bank verbs had no role gate: any student could read and rewrite answers    (2026-08-20, found by Member A's E2.12 red-team)
**Symptom.** None visible — that is the problem. `GET_ALL_QUESTIONS` returned the legacy list with plaintext answers and `UPDATE_QUESTION` accepted writes for ANY authenticated session. The client only offers the screen to staff, but that check runs on the attacker's machine.
**Investigation.** `MessageRouter` gates on `isAuthenticated()` only; it has no role dimension. Both legacy handlers accepted a `CallerContext` and never read it. The handler javadoc even recorded the reasoning: the course-scoped guard (`requireTeachesCourse`) was waiting on E2's repositories — but a blanket role gate needs no course data at all, and the wait shipped an exposure. Pre-existing since the E1/E5 prototype port; found by an adversarial pass that asked one question: can a correct answer reach a student?
**Solution.** `Authorization.requireRole` at the top of every gated handler: bank reads are TEACHER/COORDINATOR/PRINCIPAL (PRD F2 gives the principal read-only), bank writes TEACHER/COORDINATOR, and all three lock verbs TEACHER/COORDINATOR (a student who could acquire locks could pin entities read-only for the TTL, repeatedly). Negative tests pin each refusal, including "the DAO is never touched". Standing rule for every epic: a verb is registered WITH its role gate in the same commit, and the reviewer treats a `CallerContext` parameter that is never read as a finding.
**Evidence.** New FORBIDDEN tests in `LegacyQuestionHandlersTest` and `LockConcurrencyIntegrationTest`; the full suite green. Course-scoped guards still arrive with their epics (E6+) on top of this blanket gate, not instead of it.
**Addendum (2026-08-24, legacy retirement PR):** both verbs and both handlers are now deleted, so `LegacyQuestionHandlersTest` no longer exists and the exposure is closed by removal rather than by a gate. The standing rule this finding produced is what outlived it and still binds every epic: *a verb is registered WITH its role gate in the same commit, and a `CallerContext` parameter that is never read is a review finding.* The bank's seven replacement verbs were written under it — every one is staff-only with per-role scope resolved server-side, and `LockConcurrencyIntegrationTest.studentsAreRefusedLockVerbs` still pins the lock half of the original fix.

## P-6 — When the code and its test share one misunderstanding, the suite goes green and proves nothing    (2026-08-21, found by Member A's post-implementation audit of E6)
**Problem.** `QuestionValidator` decides whether two of a question's four answers are "the same" (C-8, ADR-016). Its javadoc claimed it was **never weaker than the database constraint it fronts**, so a duplicate pair could never reach the `INSERT` and come back as a raw constraint violation with a generic internal error instead of a sentence naming the offending box. **The claim was false.** Measured afterwards against the running database, `utf8mb4_unicode_ci` calls all of `Strasse/Straße`, `oeuvre/œuvre`, `file/ﬁle`, `A/Ａ`, `τέλος/τέλοσ`, `resume/résumé` and `שלום/שָׁלוֹם` **equal**; the validator agreed on two of the seven, and every mismatch ran in the dangerous direction — service accepts, database rejects. The symptom was invisible in every way that normally works: 3,464 tests green on two engines, 100% coverage on the class, CI green, PR merged. The lead's approval comment then quoted that very property as what earned the merge, turning a private error into a durable public claim.
**Investigation.** The tests did not miss those cases by accident. They were written from the implementation's idea of the rule rather than from the requirement: the code folded canonically (`Normalizer.NFD`), so the test used `résumé` and `Ångström`, which canonical decomposition handles. The collation additionally performs *expansions* (ß → ss, œ → oe) and *compatibility* folding (ligatures, fullwidth forms), which no canonical normalisation does. **Author and test agreed, and both differed from the requirement, so there was nothing left to fail.** This is the same disease as PR 3a §4 one level down: there the tests were written to the code rather than to the seed document, so a transcription error would have been copied into both; here they were written to the code's *semantics* rather than the specification's, so a misunderstanding was copied into both. More testing by the author cannot reach it, because the author is the shared cause; a second engine cannot either, since H2 and MySQL both ran the author's assertions.
**Solution.** A **cold post-implementation audit is now a gate on opening a PR** (`.claude/skills/pr-ready`): an adversarial reader with no knowledge of the author's reasoning, handed the requirement and the schema and asked one question — *where do the code and its test agree with each other and both differ from the specification?* Not a style or coverage review; specifically that. It is the only check standing outside the correlated pair. Two occurrences earned the rule rather than one: E2 PR 3b skipped it until prompted, E6 PR 1 skipped it and shipped. Chosen over the alternatives deliberately, because each of them had already failed here: more tests by the same author, a second database engine, and a reviewer reading a diff. The rule itself is now stated **one-directionally** instead of as an equivalence — NFKD, strip combining marks, upper-then-lower for Greek final sigma, then a `Collator` at primary strength for the expansions — because exact parity with MySQL's UCA table is not achievable in Java, and claiming it is what caused this. Over-folding is the safe error: the worst case is a teacher told that two confusingly similar answers are too similar.
**Evidence.** `QuestionValidatorTest` now pins all seven collation pairs and six deliberately-distinct ones (`2x + 1`/`2x - 1`, `yes`/`yes!`, Hebrew words differing by one consonant), so the rule cannot drift in either direction. The same audit found four more defects in the same green suite, all fixed in the E6 service PR: free-text bank search treated `%` and `_` as LIKE wildcards, so searching `100%` matched every stem containing `100`; the blocked-delete message discarded the exam display id, so two exams sharing a name printed "2 exams use it: Algebra Midterm, Algebra Midterm"; a Hebrew test asserted nothing because both its strings were unpointed, so deleting the code under it would not have failed it; and an empty blocker list rendered "0 exams use it: .". **On the search bug the precise sentence matters, and the inflated one is worse:** it was *injection-shaped but not injection* — the value was a bound parameter throughout, so the query's structure was never reachable; what went wrong is that user input was read as LIKE's own mini-language rather than as data. `BankBrowseContract` pins `%`, `_` and the escape character itself. The lead posted a correction to the merged PR crediting the audit, which is the other half of the fix: **a false claim in a durable record stays a defect until the record is corrected.**

## P-7 — A requirement with a read path everywhere and a write path nowhere, hidden by its own seed data    (2026-08-23, found by Member B)
**Problem.** S-22 says a teacher may write a comment to the student on a grade. `teacherComment` was a column on `grades`, a component of `StudentGradeRow`, preserved by both student containers, rendered as a column on My Grades and under a heading on the checked form, and documented in the frozen wire contract. **Nothing could write one.** No request payload had a comment field and no service called `setTeacherComment` — the only caller in the whole product was the seed loader. Acceptance case 8.4 ("change a grade with a justification, and add a comment to the student") could not pass, and had never been run.
**Investigation.** The gap survived a frozen contract review, an epic's worth of tests and two screen reviews, and the reason it survived is worth more than the fix. **The seed masked it.** `yael.azulay`'s seeded grade carries a comment, so every screen that reads one had something to show: the My Grades column was populated, the checked form's note box rendered, the DTO tests asserted the comment travelled, and the demo walked through all of it looking finished. Every test involved was green and every one of them was testing the read. Grepping for the field hit a dozen main-source files and made it look thoroughly built; grepping for `setTeacherComment` hit exactly one, `GradesSection`. What nobody asked until Member B did was *which of these writes it* — and a seeded value answers "can this be displayed?" while looking exactly like an answer to "can this be produced?".
**Solution.** `teacherComment` becomes an optional fourth component of the existing `GradeOverrideRequest` (contract amendment A3, lead's ruling): commenting rides the adjustment, no new verb, blank collapses to null, and **null preserves an existing comment rather than clearing it** so a second correction cannot silently erase what a teacher wrote to a student. Chosen over a standalone `GRADE_COMMENT_SET` because the two acts happen at one moment in front of one paper; the separate verb is the v2 shape and is recorded as such. **The lesson is the durable part: a demo cannot distinguish "renders data" from "can produce data", and seeded data is what makes the two look identical.** Standing rule adopted: a requirement is only walked when the walk *creates* the thing it asserts — the acceptance case for a write starts from a database where that value does not exist yet. The new `TeacherCommentFlowContract` does exactly that, on both engines, and the case fails the build if the write path goes away.
**Evidence.** `TeacherCommentFlowH2Test` / `TeacherCommentFlowMySqlTest` walk 8.4 from an uncommented grade to the student's checked form; `OverrideServiceTest$Comment` pins the null-preserves rule by overriding twice, which is the only way it can fail; `GradingDtoTest$OverrideComment` and `DtoSerializationTest` pin blank-to-null on both sides of the wire.

## P-8 — Two green suites either side of one seam, and neither crosses it    (2026-08-24, found by Member A's post-implementation audit of E7)
**Problem.** `ExamService` wrote every exam composition with `question_id = 0`. `exam_version_questions` carries a **composite** foreign key onto `question_versions (id, question_id)` and a unique key on `(exam_version_id, question_id)`, so every create and every save would have failed on the foreign key, and had one somehow inserted, a second question would have collided at `(versionId, 0)`. That is T-3.1, the first acceptance case in the epic, and the failure arrives as `INTERNAL` and a stack trace in front of whoever is being shown the exam builder. The comment above the line said the store resolved the id; the store persists the field verbatim. **A comment asserting a safety property that is not there is worse than no comment**, and this is the third time that shape has been caught here by a cold read rather than by a test.
**Investigation.** The interesting part is not the zero, it is *why nothing failed*. The seam between a repository and the service above it has a test on each side and neither one crosses it. `ExamBuildRepositoryContract` proves the store against two real engines and builds every pin with a genuine resolved id, because a contract test that used a wrong id would be testing nothing. `ExamServiceTest` proves the service with the store mocked, and asserted `replaceComposition` was called with `any()`. So the store was proven correct for inputs the service never sends, and the service was proven to call a store that does not exist. Both suites green, both correct about what they check, and the schema disagreeing with both. **This is P-6 one layer out:** there the code and its test shared a misunderstanding, here two test suites share an *absence*, and the absence is structural rather than accidental — mocking the collaborator is what makes a service unit-testable, and it is the same act that stops anything checking the values crossing. The same pattern hid three more defects in the same class, all found in the same audit: the two enum mappings were entirely unpinned (every fixture used one constant), the ordinal was unpinned (a 0-based one violates `ck_evq_ord` on every write), and a revision's carried-forward composition was asserted by `hasSize(2)`, which passes with every field scrambled.
**Solution.** **Where a method translates between two type systems, the test asserts what crossed, never that a call happened.** `ArgumentCaptor` on the collaborator plus `extracting(...)` over every component, rather than `verify(x).method(any())`. The rule is narrow on purpose: it applies to the mapping methods — a projection to a wire record, a wire record to a store type, an enum to its counterpart — and not to every interaction, because the cost of the strict form is real and most calls do not carry a translation. Three questions identify the places: does this method build a value of a type it did not receive; does anything downstream have a constraint on that value; and does the test say `any()`. All three yes is where the defect lives. Chosen over the alternative of an integration test spanning service and store on a real database, which would have caught this one but is slow enough that it would not be written for every mapping, and the gap would reopen at the next one.
**Evidence.** `ExamServiceTest$Translations` captures the pin list and asserts version id, question id, points and ordinal for `save` and for `revise`; `everyEnumArmIsPinned` walks all four statuses and all three difficulties through the real mapper rather than asserting one; `revisionCarriesEveryFieldForward` replaces the cardinality check. Twelve planted mutations are caught, including the ordinal one and the two enum swaps, none of which moved a test before this entry. The audit that found it was the second on the same branch and was run because it is a gate, not because anything looked wrong: **the suite was green and the coverage was 98.92% on the class that could not write a row.**

## P-9 — A service-side comparison drifting from the collation it promises to match, in the one language nobody tests in    (2026-08-25, found by Member A's pre-build audit of E6.16)
**Problem.** `QuestionValidator.sameAnswer` promises, in its own javadoc, "never accept a pair the database will reject", because a pair it accepts and `ck_question_versions_distinct` rejects becomes a raw `SQLIntegrityConstraintViolationException` and a generic internal error — exactly the outcome that naming the field was meant to replace. On Hebrew **final forms** it did the opposite. Java's `Collator` at PRIMARY strength treats ם and מ as different letters; `utf8mb4_unicode_ci` gives them the same primary weight. So a teacher entering `מים` and `מימ` as two answers passed validation and the INSERT then failed the CHECK. Measured on both sides rather than argued: jshell over the validator's exact folding steps says `false` for all five final-form pairs, `SELECT 'מים' = 'מימ' COLLATE utf8mb4_unicode_ci` says `1`, and a throwaway schema carrying the same constraint answers `ERROR 3819`. It reaches the teacher on the add-question screen, in Hebrew, which is T-2.1 — the first case in the acceptance script.
**Investigation.** The validator was **not** careless: it already folded further than ADR-016's literal words, with a documented four-step normalisation and a table of pairs — resume/résumé, Strasse/Straße, τέλος/τέλoς, and Hebrew unpointed-vs-pointed — chosen precisely because the collation folds more than case. Every one of those still holds. The gap was one dimension nobody thought to enumerate, and the reason it survived is structural: **no test in `server.features.bank` touched a database.** All five server-side bank test classes declare `@Mock private Session session`; the repositories are proven on two engines and the services against mocks, and the seam between them was proven nowhere. Grepping `src/test/java/server/features` for `RepositoryTestBase` returned approval, exam, grading, notify, release, reports, results — every feature except the one whose validator makes a claim *about the database*. So the javadoc's "Verified against the running database rather than assumed" described a session somebody once had, not anything the build re-checks. This is P-6's shape aimed at an external system: the code and its test shared an understanding of MySQL that MySQL does not share. It is also **P-8 one turn further out** — there two suites sat either side of a seam, here the suite and the database do.
**Solution.** **A rule that makes a claim about another system must be executed against that system by the build, in the alphabet the users actually type.** Two tests, deliberately not one: `QuestionValidatorTest` gets the five final-form cases as fast pure-Java checks that run on every machine and in every profile, and `BankRoundTripIntegrationTest` gets the *agreement* — it asks the validator, then asks MySQL the same question by actually inserting, and fails if the two answer differently. Neither replaces the other: the first pins the folding, the second pins that the folding still matches a database nobody in this repo controls the version of. The fix itself is one step added to `foldedForm`, folding the five final forms onto their base letters, applied at every position rather than word-finally, because the collation weighs the character and not where it sits. Chosen over widening the constraint or comparing in SQL: the service must be able to refuse before it writes, and being *stricter* than the database is the safe direction — the worst case is a teacher told two confusingly similar answers are too similar, where the other direction is a stack trace.
**Evidence.** The five parameterised cases in `QuestionValidatorTest$Distinctness` and the six in `BankRoundTripIntegrationTest$ValidatorAgreesWithTheConstraint`, which was **red on the commit that introduced it** — five errors, all `Check constraint 'ck_question_versions_distinct' is violated` thrown out of `QuestionService.create` — and green on the fix. Removing the fold as a planted mutation fails both suites, 5 errors and 5 failures. The generalisation worth carrying: the same folding is reached by `QuestionValidator.sameTopic` (landing with the E7 handlers PR, #46), which E7's auto-composer will use to decide what counts as one topic pool, so the identical divergence would have produced an infeasibility report a teacher could disprove by filtering her own bank — a second feature inheriting one unexecuted promise, and inheriting the fix for free because it delegates rather than duplicating.

**Addendum, same day, and the part that matters most.** **The Hebrew fold did not close this class.** A post-implementation audit found the identical defect twice more, and the first is worse than the original. ① `utf8mb4_unicode_ci` is a UCA 4.0.0 table, and that table gives **every character above the BMP the same weight**: to the constraint, U+1F600 and U+1F601 are one string, and so are U+1F600 and U+1D400. Two different emoji pasted into two answer boxes reproduced `ERROR 3819` against a real schema. ② Three Yiddish digraphs, U+05F0 to U+05F2, which the collation *expands* (U+05F1 equals vav followed by yod) and which NFKD does not decompose, so nothing in the fold reached them. Both are folded now — astral characters onto one sentinel **preserving count**, because measurement showed they are equal-weight rather than ignorable (one emoji does not equal the empty string, `a` does not equal `a` plus an emoji, and one emoji does not equal two), and the digraphs by expansion.

**The lesson is not "we missed two characters".** It is that enumerating the dimensions by hand is the wrong method, and it produced a false all-clear the first time: the original entry read as though the class was closed. The test now asks the database **directly, with the validator bypassed**, and asserts the two verdicts are equal **in both directions** — so a divergence in either direction fails the build instead of waiting for somebody to think of the character. Two things that made the difference and are worth copying: rows the validator calls *different* have to be in the table, or the branch that asks the database stops executing the moment the fix lands; and the probe's `catch` has to name the constraint it expects, because a bare `catch (RuntimeException)` reported a malformed query as a collation result and sent me looking at the wrong thing.

**Still open, stated rather than implied:** nothing asserts the columns are still `utf8mb4_unicode_ci`, and this whole fold is correct for that collation and wrong for `utf8mb4_0900_ai_ci`. That assumption deserves its own one-row `information_schema` assertion in the MySQL leaf.

## P-10 — A screen that subscribes to the event bus but can never be called, and nothing that fails    (2026-08-25, found by Member A while building E6.14's list chip)

**Problem.** greenrobot's EventBus invokes an `@Subscribe` method reflectively, from its own package. A subscriber whose **method** is public but whose **class** is not is therefore unreachable: `EventBus.invokeSubscriber` throws `IllegalAccessException: class org.greenrobot.eventbus.EventBus cannot access a member of class client.features.bank.BankRowLocks with modifiers "public"`. Nothing about that surfaces. `register` succeeds, because the subscriber-method scan only looks at the method. The throw then happens on **every** push, inside `PushEventBridge`, inside `RequestDispatcher.deliverPush`, which catches `RuntimeException` and logs it deliberately, so that a broken subscriber cannot take the socket and every other screen down with it. The result is a screen that renders its first paint correctly and then never updates again, with a green suite and one ERROR line in a log nobody reads during a demo. Measured, not reasoned: `BankRowLocks` was package-private first and its push tests were what found it.

**Investigation.** The catch in `deliverPush` is right and should stay - one screen's bad subscriber must not drop the connection. What is missing is that the two failure modes it merges are not alike. A subscriber that throws *while handling* an event is a bug in that handler and the rest of the app should survive it. A subscriber that can never be invoked *at all* is a wiring defect that will never once succeed, and swallowing it silently is what turns a five-minute fix into a defect found on stage. The distinction is available at registration time: whether the bus can actually reach the method. Every subscriber in the tree today is `public final class` (audited at the same commit: `ClientEventBus`, `ConnectionWatcher`, `LockAwareEditor`, the four exam and results sessions, the three views, `NotificationsSession`, `ReleaseManagerSession`, `BankRowLocks`), so **nothing is broken right now** - which is exactly the moment to write the guard, because the next one to be introduced will look like a style choice.

**Solution.** Two things, neither of them "remember to make subscribers public". ① The reason is recorded on the class itself, in the file where somebody would tidy it: `BankRowLocks`'s javadoc says the class is public *only* because the bus reaches it reflectively, that every member is package-private, and that narrowing it back produces a screen that silently stops updating. ② The property is pinned by a test that observes the mechanism rather than a proxy - `BankScreenInteractionTest.editingColumnPaintsAndFollowsPushes` drives a push through the app's **real** `ClientEventBus` and asserts the table repaints, so the mutation "make the class package-private again" fails the build. Planted: it does. The suite-wide version, which belongs with whoever owns `ClientEventBus`, is for `register` to assert the bus can reach each discovered method and fail loudly at registration, where a wiring defect is cheap, instead of at the first push, where it is invisible.

**Evidence.** The stack trace above, captured from a real run before the fix. Both plants confirmed after it: reverting `BankRowLocks` to package-private fails `editingColumnPaintsAndFollowsPushes`, and so does removing the column from `BankView`. The generalisation worth carrying past this epic: **a `catch` that exists to contain one failure mode will silently contain every other failure mode that reaches it**, so it is worth asking, of each one, which of the things it swallows should never have been survivable.

## P-11 — Asking for the state before registering for the news, so a change in the gap is in neither    (2026-08-25, found by the cold auditor on Member A's E6.14)

**Problem.** A live list screen needs two things: the state now (`LOCKS_SNAPSHOT`) and the changes after (`LOCK_WATCH` plus `PUSH_LOCK_CHANGED`). `BankRowLocks` asked for the snapshot first and registered the watches second, which reads as the natural order - paint, then subscribe - and opens a window in which a change is captured by neither. The server's `publish` resolves recipients by reading its watcher set **at the instant the lock changes** (`EditLockService.publish`), so: the server answers "question 11005 is free", a colleague acquires it before this client's `LOCK_WATCH` is handled, `publish` finds a watcher set this client is not yet in and writes no push at all. The snapshot already said free and the news never comes. The row shows the question as **free for the entire duration of the colleague's edit session** - the precise case the column exists to prevent, and the failure mode is invisible on any machine fast enough that the window rarely loses the race, which is every developer machine.

**Investigation.** Not reachable by any test that drives one client. It needs a second actor acquiring inside a window measured in the server's own message-handling order, so the suite was green, coverage was complete, and seven planted mutations all passed. It was found by an adversarial read that started from the *server's* recipient resolution rather than from the client's code, which is the direction the author had not looked. Two durable claims were falsified with it: the class's own "one snapshot plus the pushes is the whole picture", and `Verb.LOCKS_SNAPSHOT`'s "one snapshot at load plus the pushes afterwards is the complete picture". Both are true **only if the watch is registered first**, and neither said so.

**Solution.** Watch first, then snapshot, and the reason recorded at the call site rather than in a commit message. The reversed order has no matching hazard, which is what makes it a fix rather than a trade: both messages travel one ordered socket and cross to the FX thread through the same poster queue, so an acquire inside the window now publishes a push written **before** the snapshot answer, and the snapshot - newer, and already containing the acquire - lands last and wins. Pinned by `BankSessionTest.EditingColumn.watchesBeforeAskingWhoHolds`, which asserts the snapshot is the last of the two verbs on the wire; planted, and it fails when the order is put back.

**Evidence.** `EditLockService.publish` returns early on an empty watcher set; `watch` calls `addWatcher` on entry, so the registration is not in place until the server handles that message. The generalisation, which is the reason this is a P-entry and not a commit note: **whenever a subscription and a state read are both needed, subscribe first and read second, so the overlap duplicates rather than drops.** A duplicate is idempotent here and everywhere else this shape occurs; a gap is silent. E18.8 was built to be reused by every list screen in the product - E7's exam list next - and each of them will write these two calls in some order.

## P-12 — A validator stricter than the constraint it stands in for, refusing rows the system had already stored    (2026-08-26, found by Member B's acceptance pre-walk of scenario 2)

**Filed as a P-entry deliberately, and the argument against is worth stating first.** P-9 already covers `QuestionValidator.sameAnswer` drifting from `utf8mb4_unicode_ci`, and one could read this as its fourth addendum — a fourth character class nobody enumerated, in a section that has already had three. **The reason it is its own entry is that P-9's *solution paragraph* is what failed here, not its problem.** P-9 closed by arguing that "being *stricter* than the database is the safe direction — the worst case is a teacher told two confusingly similar answers are too similar." That sentence was written into the class javadoc as a design principle, and it is false. Recording the falsification underneath the entry that asserted it would bury the one thing a reader needs.

**Problem.** `QuestionValidator.sameAnswer("1", "-1")` answered **true**. So did `("2, 3", "-2, -3")`, `("cos(x)", "-cos(x)")` and `("x = 1", "x = -1")`. MySQL under `utf8mb4_unicode_ci` answers **different** to every one of them. The validator was therefore **stricter** than `ck_question_versions_distinct`, the constraint it exists to make unreachable — the opposite direction from P-9, and the one P-9 declared safe. It was not safe: **five seeded questions could not be written back through `QUESTION_UPDATE` at all** (`11005`, `11006`, `11008`, `12005`, `12007`), because the seed loads through SQL and so bypasses the validator. A teacher opening `11005`, changing only the stem and pressing save met *"Answers 1 and 3 are the same"* — about two answers she had not touched, on a row the system had stored itself. Acceptance case 2.4's own first step is "open 11005, change its text, save"; it could not pass.

**Investigation.** The mechanism is one line of Java's collation data: `Collator` at `PRIMARY` strength treats the hyphen-minus as *ignorable*, so it contributes no weight and `"-1"` folds to `"1"`. The first instinct — "punctuation is ignorable at PRIMARY, so fold all of it" — was wrong in an expensive direction, and measuring instead of reasoning is what caught it. **Measured, both sides.** Every defined non-mark, non-whitespace, non-control BMP code point was asked of `Collator` at PRIMARY: exactly **eight** are ignorable, and all eight are dashes (`U+002D`, `U+2010`–`U+2015`, `U+2212`). The whole ASCII punctuation family was then asked of MySQL: **none** of `! " # $ % & ' ( ) * + , - . / : ; < = > ? @ [ \ ] ^ _ ` { | } ~ ± × ÷ ° · ≤ ≥ ≠ √ ∞ € §` is ignorable to the collation. Brackets and commas were never the problem, and a fix that had "stopped punctuation being ignorable" wholesale would have changed nothing for them and looked like it had. A second measurement then contradicted a second guess: all 28 pairs among the eight dashes were put to MySQL, and 27 answered *different* — but **exactly one, `U+2010 HYPHEN` against `U+2011 NON-BREAKING HYPHEN`, answered equal.** A first draft giving each dash its own sentinel failed on that one row and nothing else, which is `BankRoundTripIntegrationTest`'s bidirectional assertion doing precisely the job P-9 built it for.

**Solution.** Each collator-ignorable dash is substituted with a sentinel before the comparison — the same technique the supplementary-plane fold already uses, aimed the other way: there the collation was blunter than Java and the fold made Java blunter to match, here Java is blunter than the collation and the fold gives each character a body the collator will weigh. **Seven sentinels for eight dashes**, because the table encodes the collation's measured equivalence classes rather than a loop handing out consecutive values. Private-use `U+E000..U+E006`, checked on six properties rather than assumed: non-ignorable at PRIMARY (so count and position survive, which MySQL also requires — `a` ≠ `a-` and `a-` ≠ `a--`), mutually distinct, distinct from the astral sentinel, and unchanged by NFKD, mark-stripping and the case round trip. Chosen over raising the collator's strength, which is not the same dial: SECONDARY or TERTIARY would stop folding case, accents and niqqud, which the collation genuinely does fold, so it would fix one divergence by creating four.

**And the javadoc was corrected rather than quietly amended.** The "stricter is safe" paragraph is kept in place, marked, and answered: the invariant is agreement in **both** directions, and P-9's asymmetry is about which direction is caught *soonest*, not which is acceptable. Looser still has a stack trace in it; stricter has a teacher who cannot save her work and no error anywhere that explains why.

**That sentence was true of one javadoc and not of the codebase, and a cold read found the rest on 2026-08-26.** The retracted formulation — "at least as strict as `utf8mb4_unicode_ci` in every dimension" — was still stated as current in four more production files, including the same `QuestionValidator` javadoc **eleven lines above the two-consumer invariant that contradicts it**. `AutoComposer` was the dangerous one: it did not merely repeat the premise, it *derived* from it that "a bucket here can never be wider than the rows the bank screen would show", reassuring the reader about the harmless direction while staying silent on the one that broke five seeded questions. All four are corrected in place and dated, each saying what it used to claim. **`common/protocol/Verb.java:161` carries the same phrasing and is the lead's path, not Member A's — raised rather than edited.** The lesson is P-13's neighbour: a correction filed against the file the defect was found in leaves every copy of the sentence elsewhere reading as current, so the sweep is part of the fix rather than follow-up work.

**Evidence.** Twelve new `@CsvSource` rows in `BankRoundTripIntegrationTest$ValidatorAgreesWithTheConstraint` — the sign-differing pairs, the count-and-position pairs, and the two dash-versus-dash pairs that pin the equivalence classes — plus a five-case parameterised round trip that creates and then stem-only-edits each of the five seeded answer sets through `QUESTION_CREATE` and `QUESTION_UPDATE` against real MySQL. 30 green in that nest, 91 in the two bank classes together. Filed in `docs/ACCEPTANCE_TESTS.md` as **B-7**.

**The generalisation worth carrying.** P-9's lesson was "execute the claim against the system it is about". This one is narrower and sharper: **a one-directional promise deserves a two-directional test, and an argument for why one direction is harmless is a hypothesis, not a licence.** The bidirectional assertion existed and was green throughout — the gap was in the *data*, not the assertion, and it was the data an author chooses by enumerating cases he can think of. The rows that catch this class are the ones a fix is not expected to change.

## P-13 — A cache or a reset keyed on a subset of what can change    (2026-08-26, found by two cold reads of Member A's PR24)

**Problem.** Four defects in one PR, three of them user-visible, all the same shape: something
decides whether to redo work by comparing a **key**, and the key omits a term the work depends on.
Nothing throws. The model is correct throughout. The screen, or the next screen, is not.

- **A redraw key.** The exam builder rebuilds its question cards only when the paper's *shape*
  changes, and the shape was the list of pinned version ids. Pressing "Use the newer version" then
  saving returned rows with those same ids, so the key matched, nothing rebuilt, and the corrected
  wording never reached the screen — while the notice that had promised it would was hidden,
  because the save had "kept the promise". **The saved pin was correct**, which is what makes it
  expensive: screen and database disagree with no marker, and the only conclusion available to the
  teacher is that the update silently failed. The same key was still missing `latestVersionNo` after
  the first fix, so a version published by a colleague mid-edit left the badge unpainted.
- **A reset.** `resetLoaded` bumped the load counter and the picker counter and not the compose
  counter, because it was written when there were two. A slow compose then landed on whichever exam
  she opened next: paper cleared, filled with another exam's questions, announced with a success
  toast. Two clicks away, because the screen is cached and reused across navigations.
- **The same reset's field half.** The auto tab and the criteria grid survived `open()`. Landing on
  a read-only version from the auto tab hid the paper she had navigated in to read, and withheld
  the tab switch because a finished version is not editable — unrecoverable for the rest of the app
  session.
- **A stored answer.** The infeasibility report outlived the criteria it answered, under a heading
  reading "the bank cannot satisfy **these** criteria" pointing at a grid she had since edited.

**Why the tests could not see it.** Every one of these is a property of a *transition* — click then
save, open then open again, answer then edit. The suite was rich in tests of each state and had
almost none that crossed two. `reviseKeepsThePredecessor` is the sharpest instance: a plant that
wrote the carried composition onto the predecessor left version 1 looking untouched, because it
already held those rows, and version 2 empty — and every assertion passed, because the test asserted
what must *not* change and never what must.

**The rule.** A key that decides whether to redo work must hold **every term the work reads**, and a
reset must cover **every asynchronous answer that can still be in flight**. Both are lists that grow
when the feature grows, and both are invisible when short: the omission looks exactly like a
deliberate optimisation. Write the rule beside the key — *"holds every term a server re-read can
change, and nothing she can be halfway through typing"* — so the next person adding a term knows
there is a list to add to.

**The tell.** A comment near one of these that quantifies. `resetLoaded`'s paragraph said bumping
the generation retires an answer in flight, and it was true when written and false for two of the
three counters by the time it mattered. See method rule 5's note on comments that decay.
